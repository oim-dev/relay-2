# Организация тестов Relay

Тестовый runner — **Bun test**.

Правила написания, критерии качества и карта покрытых сценариев находятся в
[материалах для разработки](../docs/development/README.md). Здесь описаны размещение,
запуск и изоляция наборов.

CLI проверяется через `runCli`, интеграцию с локальными сценариями и запуск собранного
бинарника. Git Sync проверяет обмен через локальный bare Git и жизненный цикл процессов.
Core, Storage и Project Runtime проверяют свои правила и работу с реальными
изолированными данными. Корневой сквозной набор соединяет команды в пользовательские
маршруты. `--pass-with-no-tests` допускается только у ещё пустого набора;
после появления первого теста флаг удаляется из script его владельца.

## Владельцы и размещение

Тесты приложения находятся внутри приложения, тесты библиотеки — внутри пакета.
Корневой `tests/` содержит это руководство и небольшой набор сквозных маршрутов продукта.

| Набор          | Размещение                                               | Команда из корня                       |
| -------------- | -------------------------------------------------------- | -------------------------------------- |
| Модульный      | `src/**/*.unit.test.ts` у владельца                      | `bun run test:unit` или `bun run test` |
| Интеграционный | `tests/integration/**/*.integration.test.ts` у владельца | `bun run test:integration`             |
| Процессный     | `apps/{cli,git-sync}/tests/process/**/*.process.test.ts` | `bun run test:process`                 |
| Сквозной       | `tests/e2e/**/*.e2e.test.ts` в корне                     | `bun run test:e2e`                     |

Например, модульные проверки CLI находятся в `apps/cli/src/`, процессные — в
`apps/cli/tests/process/`, интеграционные — в `apps/cli/tests/integration/`.
Правила Core проверяются в `packages/core`, механизмы хранения — в `packages/storage`.

Интеграционные тесты CLI разделены по предметным областям и общим механизмам:
вызов команды, выбор проекта, ввод/вывод, пагинация, знания, документы, задачи,
планирование, история и запросы. Общие fixtures и декодеры ответов находятся в
`apps/cli/tests/integration/helpers/`. `withCliFixture` создаёт отдельное окружение
для каждого теста и очищает его после завершения, включая отказ.

Необходимые данные готовятся через Runtime/Core; проверяемое действие вызывается
через CLI. Сущность, страница и ошибка имеют отдельные проверяемые формы ответа.
Ожидаемая ревизия берётся из подготовленной или прочитанной записи. Составной тест
разделяется, когда его части проверяют независимые гарантии; полный пользовательский
маршрут принадлежит сквозному набору.

## Выбор уровня проверки

- **Модульные:** чистые правила, преобразование аргументов, представление результатов
  и ошибок. CLI вызывается через `runCli()` внутри процесса. Небольшая подмена сервиса
  Core допустима для проверки преобразования запроса на границе CLI.
- **Интеграционные:** реальные сценарии Core с SQLite, транзакции и миграции Storage,
  выбор проекта в Project Runtime, подключение CLI к этим компонентам. Данные и файлы
  изолированы; для WAL, блокировок и повторного открытия используется файловая SQLite.
- **Процессные:** запуск собранного бинарника, stdin/stdout/stderr, коды завершения,
  сигналы, большой вывод и завершение дочерних процессов по мере появления этих механизмов.
- **Сквозные:** небольшой набор законченных пользовательских маршрутов через бинарники,
  например создание проекта, запись документа и чтение после перезапуска.

Подробные варианты предметного правила проверяются у его владельца. CLI подтверждает
собственное преобразование ввода и представление результата. Например, Core проверяет
отказ устаревшей ревизии и сохранность данных, а CLI — сообщение и код завершения.
Повтор на другом уровне оправдан дополнительным риском: упаковкой, потоками или процессом.

Процессный и сквозной наборы имеют разные цели; один маршрут не копируется в оба набора.
Проверка конкурирующих записей относится к функциональной корректности. Обязательная
приёмка использует 2–3 независимые реплики. Штатный командный сценарий `apps/git-sync`
соединяет двух активных писателей и offline-return третьей реплики, сохраняя реальные
SQLite, Git и отдельные окружения. Детальные non-FF, whole-batch, late-write, crash,
ID/причинность и отсутствие echo проверяются у владельцев и не требуют более двух реплик.
Измерение массовых клиентов и задержек относится к [ручной нагрузке](../benchmarks/README.md).

## Запуск и сборка

Модульные и интеграционные наборы работают с исходными модулями, без предварительной
сборки бинарников. Процессные зависят от Turbo-задачи `build` своего приложения.
Git fixtures подготавливают свежий минимальный helper Runtime той же source-композицией,
что исходный entry Git Sync. Этот helper владеет только процессами; Core, Storage и сценарий
обмена остаются source-модулями. Сборка выполняется один раз на fixture, а её каталог удаляется
после остановки engines и guarded commands; ранее собранный `dist` не используется.
Сквозной вход через `build:cli` подготавливает `relay` и `relay-git-sync`.
Зависимость `@relay/cli#build` → `@relay/git-sync#build` задана в Turbo DAG и сохраняет
проверки типов и сборки библиотек; package-зависимость между приложениями не требуется.
Успешные сборки переиспользуются из кеша.
Turbo кеширует модульные проверки. Процессные, интеграционные и сквозные результаты
сейчас не кешируются.

Корневые команды `test:unit`, `test:integration`, `test:process` и `test:e2e` выбирают
соответствующий набор. `test` — сокращение для модульного набора, `test:all` выполняет
штатные функциональные наборы. `check` дополнительно проверяет форматирование, lint, типы и сборку.

Адресный запуск:

```bash
bun run --filter @relay/cli test:unit
bun --bun turbo run test:unit --filter=@relay/core
bun --bun turbo run test:integration --filter=@relay/storage
bun --bun turbo run test:process --filter=@relay/cli
bun --bun turbo run test:process --filter=@relay/git-sync
```

Для одного файла или теста можно вызвать Bun напрямую, без Turbo:

```bash
bun test --cwd apps/cli ./src/app/run.unit.test.ts
bun test --cwd apps/cli .unit.test.ts -t "пустой вызов"
```

Прямой запуск процессного набора требует уже собранного бинарника; Turbo-команда выше
сама обеспечивает эту зависимость. В обычном цикле разработки выбирается затронутый набор.

Процессные проверки CLI с автодополнением используют Bash и POSIX-группы процессов
(Linux/macOS): deadline завершает всю группу, включая потомков оболочки. Проверка
реального отказа stdout через `/dev/full` запускается при наличии этого устройства.

### Отдельная нативная приёмка служб

`bun run test:native-service` — отдельный opt-in маршрут для настоящих пользовательских
служб на одноразовом runner; в CI его вызывает job `native-services` для Linux/macOS/Windows.
Он не входит в `check`, `test:all` и штатные функциональные наборы. Условия запуска,
opt-in параметры, preflight, cleanup и границы проверки login/reboot имеют один источник —
[паспорт native-набора](../packages/project-runtime/tests/native/README.md).

### Расширенная проверка репликации

50-репличные сценарии Core и Git Sync — отдельный ручной функциональный набор
`tests/extended/*.extended.test.ts` у владельцев. Он сохраняет исходные предметные
assertions и deadlines, но не входит в обязательный CI, `check`, `test:all` или обычный
`test:integration`. Большое число участников служит дополнительным масштабом проверки
сходимости; оно не задаёт SLA и не измеряет производительность одновременных пользователей.

Для явного запуска из корня репозитория:

```bash
bun run test:extended-replication
```

Команда последовательно выполняет Core, затем Git Sync. Для одного владельца используйте
`bun run --filter @relay/core test:extended-replication` либо
`bun run --filter @relay/git-sync test:extended-replication`.
Оба package script запускают `bun test ./tests/extended`. Штатные unit/integration/process
patterns и корневой E2E этот каталог не выбирают; `tests/**/*.ts` сохраняет его в проверке типов.

Перед таким запуском достаточно подготовки зависимостей как для integration;
сборкой свежего process helper Git fixtures владеют по правилам выше.

## Изоляция и подготовка данных

- У теста собственные данные, каталоги, БД, порты и процессы. Рабочие каталоги создаются
  под `.artifacts/YYYY-MM-DD/<понятное имя>` с уникальным именем и очищаются в `finally`.
- Базы и Git-репозитории создаются специально для теста. Пользовательские данные,
  origin и Playground не используются как fixtures.
- У каждой Git-реплики свои HOME и RELAY_HOME даже при одинаковом projectId.
  Сквозное окружение сохраняет PATH для настоящего Git и передаёт RELAY_GIT_SYNC_BIN
  на `apps/git-sync/dist/relay-git-sync` (`.exe` на Windows). Фоновые процессы принадлежат fixture;
  проверка автоматического режима не устанавливает пользовательские системные службы.
- Подготовка минимальна: тест документа создаёт нужные ему сущности. Общие helpers
  имеют владельца и появляются при повторении конкретного сценария подготовки.
- Рабочий каталог, окружение и потоки передаются явно. Параллельные внутрипроцессные
  тесты не вызывают `process.chdir()` и не меняют глобальные `process.env` и `console`.
- Соединения закрываются, процессы имеют deadline и завершаются при очистке, включая
  собственных потомков. stdout и stderr читаются во время исполнения, stdin закрывается
  после передачи данных.
- Конкурентные сценарии согласуют участников по событиям или барьерам. Ожидание
  произвольным `sleep` и автоматический повтор упавшего теста не заменяют синхронизацию.
- После отказа записи проверяется отсутствие частично сохранённых изменений.

## Параллельность и скорость

**Сейчас:** межпакетный запуск организует Turbo. В scripts наборов нет глобальных
`--parallel` или `--concurrent`; автоматическое распределение файлов по Bun workers
ещё не включено. Параллельный вызов внутри отдельного теста CLI проверяет его изоляцию.

**По мере роста наборов:**

- `--parallel=N` запускает тестовые файлы в отдельных worker-процессах и включает
  изоляцию файлов. Это основной способ ускорять независимые файлы, в том числе
  синхронные вычисления и работу с SQLite.
- `test.concurrent` разрешает конкурентные async-тесты внутри файла. Его применяем
  адресно после подтверждения изоляции. `--max-concurrency` ограничивает их число;
  это другой лимит, чем количество workers.
- У Turbo и Bun общий бюджет CPU и памяти. При параллельном запуске нескольких пакетов
  каждый пакет не должен занимать все ядра. Для процессных наборов учитывается также
  число запускаемых бинарников. Лимиты выбираются по измеренному времени и ресурсам среды.
- Ускорение начинается с минимальной подготовки данных и внутрипроцессных проверок.
  Бинарник собирается перед набором, а не перед каждым тестом.
- Таймаут функционального теста обнаруживает зависание; пороги p95 и сравнение скорости
  принадлежат отдельным измерениям.

Пример адресного запуска нескольких файлов с четырьмя workers, не настройка по умолчанию:

```bash
bun test --cwd apps/cli --parallel=4 .unit.test.ts
```

При исследовании зависимости от порядка доступен `--randomize`; seed сохраняется
в `.artifacts/` и передаётся через `--seed` для воспроизведения. Успех проверки не требует
постоянных повторов всего набора.

## Полезность и сопровождение тестов

Перед добавлением теста ответьте: какую ошибку он обнаруживает, почему выбран этот
уровень и есть ли уже проверка той же гарантии.

- Проверяется наблюдаемое поведение, инвариант или отказ. Изменение внутренних функций
  при сохранении контракта не должно требовать массовой переписи тестов.
- Тесты заглушек, импортов и очевидных обёрток ради процента покрытия не добавляются.
- Существующий набор расширяется регрессионным случаем, когда отдельный стенд не нужен.
- Табличные тесты подходят для самостоятельных вариантов ввода одного правила.
- Небольшие эталоны справки или карточки допустимы. Большие snapshots с меняющимися ID,
  датами и путями затрудняют проверку смысла изменения.
- Миграции, конфликты, потеря ответа и аварийное завершение покрываются при реализации
  соответствующих механизмов. Браузерные проверки появятся с реальным Web-сценарием.

## Покрытие и производительность

Покрытие модульного набора можно измерить адресно:

```bash
bun run --filter @relay/cli test:unit --coverage --coverage-reporter=lcov \
  --coverage-dir "../../.artifacts/$(date +%F)/coverage/cli"
```

Это Bash-команда из корня; test script выполняется из `apps/cli`, поэтому путь к отчёту
содержит `../..`. Явный reporter сохраняет файл `lcov.info` в указанном каталоге.
Покрытие измеряется отдельным запуском, помогает искать пробелы
и не заменяет проверки атомарности, изоляции и сохранности данных.

Нагрузочные сценарии разрабатываются отдельно по необходимости, а измерения
выполняются **только вручную по явному запросу**, вне CI, `check`, `test:all`
и остальных штатных тестовых команд. Методика и метрики — в
[руководстве по нагрузке CLI](../docs/development/CLI-PERFORMANCE.md), размещение
будущего стенда — в [benchmarks/README.md](../benchmarks/README.md).
