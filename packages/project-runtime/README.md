# @relay/project-runtime

Project Runtime определяет, с каким локальным проектом работает вызов Relay и где
лежат его данные. Он нужен CLI и другому локальному вызывающему коду, чтобы одинаково
находить конфигурацию, создавать проекты и выбирать их из workspace.

Для Bun-кода внутри монорепозитория пакет доступен как `@relay/project-runtime`
после [подготовки репозитория](../../README.md#быстрый-старт). Это приватная библиотека
с исходным TypeScript; пользовательские команды описаны в
[руководстве CLI](../../docs/CLI.md#проект-и-размещение-данных).

Если рабочий каталог — корень инициализированного проекта, открыть его для локального
сценария можно так:

```ts
import { openProject } from "@relay/project-runtime";

const { location, database } = openProject({ cwd: process.cwd() });
try {
  const project = database.snapshot(() => database.get(location.projectId));
  console.log(project);
} finally {
  database.close();
}
```

`openProject` находит конфигурацию, открывает базу один раз, проверяет её совместимость
и совпадение постоянного ID. Успешное рабочее соединение передаётся вызывающему,
который обязан закрыть его в `finally`. При отказе новое соединение закрывает Runtime
либо [Storage](../storage/README.md). Снимок или транзакция сценария задаётся отдельно.
Отсутствующая база считается ошибкой, а не поводом создать пустой проект.

Когда требуется только проверенное расположение, используйте `resolveProject(options)`.
Он возвращает `ProjectLocation` и сам закрывает проверочное соединение, не удерживая
снимок для последующей работы. Проверка при регистрации в workspace сохраняет такое же
поведение. Оба API используют единые правила выбора конфигурации и путей.

## Как задаётся контекст

Без `config` проверяются только `relay.config.json` и `relay.workspace.json` в `cwd`.
Явный `config` выбирает файл напрямую;
явные относительные пути внутри файла разрешаются от его физического каталога, включая
символьные ссылки. Для workspace передайте `project` — имя регистрации. Workspace
хранит регистрации `{ name, path }` с путями каталогов независимых проектов;
каждый каталог должен содержать собственный `relay.config.json`. Удаление регистрации
сохраняет данные проекта. `listProjects` возвращает абсолютные пути каталогов,
не открывая сами проекты: недоступные регистрации можно перечислить и удалить.

`initializeProject` создаёт базу в `<home>/projects/<id>/project.sqlite` и затем
публикует конфиг с `version` и `projectId`. `openProject` и `resolveProject` используют то же размещение,
если в конфиге не задан явный `databasePath`. `home` по умолчанию — `~/.relay`;
нестандартный корень передаётся и при создании, и при выборе или регистрации проекта.
Относительный `home` разрешается от `cwd`; явно пустое значение отклоняется до файловых операций.
Значение `RELAY_HOME` передаёт вызывающая CLI через параметр `home`:
библиотека сама не читает эту переменную окружения. Правила переопределения и смены
расположения описаны в [руководстве CLI](../../docs/CLI.md#проект-и-размещение-данных).

## Локальный запуск Git Sync

`createGitSyncClient(environment)` создаёт ленивый процессный порт для CLI. Контекст
содержит явные `cwd`, `env`, `executablePath`, `version` и `userHome`; отдельный `binary`
передаёт извлечённый вызывающим `RELAY_GIT_SYNC_BIN`. Сам Runtime переменные Relay не читает.
Обнаружение проверяет выпуск компонента, затем `request` передаёт версионированный
`GitSyncRequest` через stdin бинарника `--request` и проверяет точную форму envelope вместе с exit code.
Машинный stdout требует корректного UTF-8 без замены повреждённых байтов. Потоки читаются
параллельно; лимит накопления применяется к исходным байтам stdout и stderr отдельно.
Любой exit короткой команды очищает принадлежащих ей потомков; deadline и отмена имеют
ограниченные этапы graceful shutdown, принудительной остановки и drain. Удержанный потомком
pipe или отказ helper не превращают ожидание в бесконечное; неподтверждённая очистка
возвращается ошибкой. Владение обеспечивают Linux
subreaper и Windows Job Object; на macOS граница — управляемая foreground process group,
без обещания удержать произвольно демонизирующиеся helpers.
До запуска проверяются конечные JSON-значения без скрытого `toJSON`, getters, циклов,
`undefined` и потери свойств. Полный UTF-8 запрос ограничен общим Contracts
`GIT_SYNC_REQUEST_MAX_BYTES` (16 MiB); отдельный лимит источника CLI остаётся 8 MiB.

Защищённый запуск использует доверенную private-роль собственного приложения, а не
проверяемый Git Sync binary. В исходном Bun-коде Runtime находит свой helper автоматически.
В compiled-приложении передайте в `environment.runner` результат
`createNativeProcessRunner([путьКСвоемуБинарнику])`; этот бинарник должен направлять
`--guarded-command` в `runGuardianEntry`. Без явного helper Runtime возвращает
`GIT_SYNC_GUARDIAN_REQUIRED` до запуска проверяемой команды.

`service(enable|disable|status, options)` управляет user-systemd, LaunchAgent или Task
Scheduler. Установка явно сохраняет exact executable/home и запускает native manager;
удаление затрагивает только свою службу. `supervise(options)` — foreground-прокси для
внешнего supervisor, с явно подключёнными потоками и `AbortSignal`. Git и сеть остаются
ответственностью компонента Git Sync. Правила входа пользователя и linger описаны
в [паспорте CLI](../../apps/cli/README.md#кто-запускает-supervisor).
Foreground запускается с приватным `--parent-lease`: Runtime удерживает stdin pipe
до конца прокси, а аварийная смерть CLI даёт kernel EOF и shutdown ребёнка. Обычный
`--request` закрывает stdin сразу после передачи JSON. Native service запускает
компонент напрямую с `supervise --home`, без такого lease.

`probeGitSyncSupervisor` проверяет опубликованный control endpoint через loopback health:
сверяет выпуск, вид процесса, физический home и ID экземпляра. PID и readiness-файл сами
по себе не означают готовность. `waitForGitSyncSupervisor` ограниченно ждёт такого ответа
после явного native start; прежний foreground-instance не подтверждает запуск службы.
`service status` хранит native-состояние отдельно от этого
наблюдения; несовместимый или неотвечающий экземпляр не выдаётся за работающий.

`readGitSyncWorkspaceStatus` читает все регистрации, выполняя независимый запрос для
каждой; недоступный проект сохраняется как ошибочный элемент, а не прерывает весь набор.
Этот путь не открывает проектные базы в CLI.

## Восстановление реплики

`restoreProject(options, projectId, writeDatabase)` публикует новую локальную реплику
из уже полученного и проверенного приложением материала. Синхронный callback получает
путь отдельной staging-БД, создаёт её и закрывает все соединения. Runtime проверяет
совместимость и ID, эксклюзивно публикует БД и конфиг. До начала публикации отказ убирает
приватный staging; после неё рабочая БД никогда не откатывается удалением: через другой
конфиг или Storage уже могла быть принята локальная запись, даже если WAL/SHM исчезли.
Асинхронный callback недопустим. Готовая БД или оставшиеся WAL/SHM не заменяются.
Существующий конфиг того же ID с утраченной БД можно восстановить без обычного
`resolveProject`, который закономерно отклоняет отсутствие базы.
При ошибке после начала публикации или обнаружении её незавершённого маркера Runtime
сохраняет рабочую БД, staging и intent и возвращает `RESTORE_RECOVERY_REQUIRED` (exit 4).
Для распознанного намерения в `details` находятся `location`, `stagingPath`, `publicationPath`,
`reason: publication-failed | pending-publication` и `materializedInCurrentCall`.
При текущем отказе `sourceError` сохраняет исходные code/message; полная причина доступна
как `Error.cause`. При повторе materializer не вызывается, старые файлы не удаляются
и не выдаются за результат нового fetched snapshot. Это относится и к staging без рабочего
пути: он может содержать последнюю ссылку на БД с уже принятыми изменениями.
Повреждённый или не соответствующий выбранному расположению маркер даёт тот же код
с `details.path`; данные такого маркера не считаются проверенным recovery-контекстом.

Автоматического resume/adoption у этого API нет.
Успешный `ProjectLocation` возвращается только после materializer текущего вызова;
`materializedInCurrentCall: true` в ошибке не подтверждает отсутствие поздних записей.

### Явно продолжить публикацию

`resumeProjectRestoration(options, projectId, validateDatabase)` подключает сохранённое
локальное состояние без новой материализации. `projectId` можно передать как `undefined`,
если выбранный config уже содержит ID; без config нужен явный постоянный ID. `options.project`
по-прежнему означает имя регистрации workspace, не projectId. Home не сканируется.

Resume проверяет совпадение intent с ID/config/путём БД, исходную физическую идентичность
datafile и hardlink пары маркеров. Уже опубликованная БД проверяется **только по публичному
пути**, в том числе при живом WAL: staging не открывается под вторым именем. Если target
отсутствует, требуются единственный staging-hardlink, отсутствие публичных SQLite journals
и закрытые соединения validator. Storage завершает private WAL средствами SQLite и удерживает
эксклюзивную блокировку в DELETE-режиме до создания публичного link; наличие закрытого
persistent WAL само по себе не означает живое соединение.
Validator строго синхронно проверяет предметные данные через Core, ничего не пишет,
не создаёт БД и закрывает свои соединения. Ошибка сохраняет все recovery-материалы.

Совпадающий config сохраняется дословно; отсутствующий публикуется эксклюзивно. Чужой target
или config, другой `--config`, неизвестный hardlink, скопированный/повреждённый marker
и ранний intent v1 дают отказ без удаления файлов. Новые публикации сохраняют intent v2
с идентичностью datafile: старый reader v1 обязан отвергнуть его до своего прежнего recovery.
ФС должна поддерживать hardlink и надёжные BigInt inode/File ID и birthtime; отсутствие
этих сведений не заменяется сравнением усечённых чисел или содержимого файла.

Результат: `{ location, resumed: true, preservedExisting: true, sourceCheckpoint: null, recovery }`.
Он означает «сохранённый локальный проект подключён», **не** соответствие новому remote HEAD.
Runtime не выполняет fetch/ack и не выдумывает Git SHA; дальнейшие connect/now — отдельные действия.
`recovery: null` подтверждает полную уборку только доказанных private links/intent. При
неизвестных companion-файлах или ошибке уборки возвращаются `publicationPath`/`stagingPath`
и `failure: { code, message }` с причиной незавершённой очистки;
привязка уже успешна, эти материалы нельзя удалять вслепую. Публичный datafile не удаляется.
Повтор после полной уборки даёт `RESTORE_NOT_PENDING` (exit 3) без validator и без записи;
при сохранённых целых материалах повторная проверка и привязка безопасны.
