# @relay/git-sync

Git Sync обменивает независимые SQLite-реплики через общую Git-ветку **`relay-data`**.
Проекты используют служебный linked worktree `data/` рядом с SQLite внутри `RELAY_HOME` и настройки
Git своего проекта. История данных начинается с orphan-коммита, независимо от истории кода.

Пользовательский вход — `relay git-sync`. CLI автоматически подхватывает созревший обмен
при предметных обращениях. Server использует тот же CLI через процессный порт,
но владеет автоматической попыткой в фоне и не задерживает HTTP-ответ.
Каждый обмен ограничен временем жизни своего владельца — CLI-вызова либо Server;
постоянный отдельный worker и supervisor для него не требуются.
Нужен установленный Git с поддержкой `git worktree add --orphan`.

## Начать работу

Из корня Git-проекта:

```bash
relay init --name "Мой проект"
relay document create --name "Начало" --body "Рабочие договорённости" --actor human
git remote add origin <URL-репозитория>
relay git-sync now
relay git-sync status --format json
```

Подставьте URL своей общей Git-площадки. До появления `origin` данные и outbox сохраняются
локально. Перед очередным обменом CLI/Web читается текущий `origin` из Git-настроек проекта.
`now` обходит задержку автоматического обмена, сохраняя взаимное исключение процессов.
Подключение заданного remote/ветки, конфликты и восстановление независимой реплики
описаны в [руководстве CLI](../../docs/CLI.md#git-синхронизация).

## Локальные файлы и владение

```text
проект/
  relay.config.json            # version и projectId, коммитируется в Git
RELAY_HOME/                    # по умолчанию ~/.relay
  projects/<projectId>/
    project.sqlite             # данные, outbox и расписание
    state/                     # подключение, checkpoints и исходы запросов
    data/                      # linked worktree ветки relay-data
```

SQLite/WAL/SHM и локальная диагностика находятся вне дерева файлов ветки данных.
Worktree создаётся при первом обмене. Его принадлежность проекту фиксируется маркером
в собственном Git worktree metadata; технические refs имеют namespace локального replicaId.
Основные HEAD и index проекта не переключаются. Чужие ветки, немаркированные worktree,
ручные и ignored-изменения служебного дерева отклоняются с сохранением файлов.

Все кодовые worktree одного Git-репозитория используют одну SQLite и один служебный worktree.
Владение транспортом проверяется по общему физическому Git-каталогу, а не по пути checkout.
У независимых Git-клонов отдельные `RELAY_HOME`; независимую реплику получают через `restore`.
Копирование работающей SQLite не создаёт новый replicaId.

Удаление кодового worktree или `git clean -fdx` в нём не удаляет внешнее хранилище Relay.
Неподтверждённые локальные изменения требуют сохранной SQLite; удаление общего `.git`
сохраняет её, но лишает служебный worktree Git-контекста.

## Ленивое расписание

Storage атомарно с новым changeset сохраняет начало серии и время последней мутации.
Расписание и режим `auto`/`manual` находятся в SQLite. Чтения и приём remote не продлевают
задержку. Общую формулу срока предоставляет Runtime, окончательное решение принимается
под межпроцессным mutex владельца обмена.

По умолчанию учитываются две секунды после последней записи и десять секунд от начала
непрерывной серии. Пустая очередь также допускает получение remote при обращениях:
обычный интервал — пять секунд. Продолжение незавершённого окна допускается через 500 мс;
отказы используют ограниченный backoff. Эти значения не являются таймерами доставки:
**после наступления срока нужна следующая предметная команда или HTTP-операция**.

Автоматический запрос уступает уже активному обмену. Явный `now` ждёт владельца в пределах
своего бюджета и выполняет собственный цикл. Блокировка реализована отдельным SQLite mutex;
сеть не удерживает транзакцию записи проектной базы. Аварийное завершение освобождает mutex.
Успех локальной мутации отделён от диагностики автоматической доставки.

Справка, версия, status/doctor, чтение квитанции, `batch --check`, SSE и health не запускают
автоматический обмен. `auto disable` работает и до подключения remote; `now` остаётся явным
запросом.

## Формирование публикации

Одна внешняя предметная транзакция создаёт один неизменяемый changeset. Core выбирает окно
до 64 источников / 8 MiB исходного JSON; один oversized changeset остаётся неделимым.
Конфликтный пакет удерживает зависимости, независимые пакеты могут публиковаться.
Итоговый canonical snapshot содержит согласованное состояние общей ветки и включённых
эффектов. Размер этого снимка не ограничен бюджетом исходного окна.

Транспорт получает и проверяет историю, создаёт коммит поверх remote HEAD и выполняет
обычный fast-forward push. При конкуренции кандидат пересобирается на новом HEAD; при
потерянном ответе проверяется фактическая история. Пользовательские команды не повторяются.
Core принимает только доказанную публикацию и сохраняет поздние локальные записи.
Один успешный `now` не обещает пустой outbox: актуальный остаток находится в `pending`.

Writer выпускает `layoutVersion: 3`, `formatVersion: 1`, `modelVersion: 2`.
Каждая переносимая таблица новой схемы представлена папкой, каждая строка —
одним JSON-файлом со всеми её полями и текстами. Например, документы находятся
в `documents/`, задачи — в `tasks/`, критерии — в `task_criteria/`,
назначения адресов — в `object_keys/`. Состав таблиц и колонок принадлежит Storage.
`manifest.json` определяет проект и версию формата. Имена файлов однозначно выводятся
из постоянного первичного ключа; смена семантического ключа не меняет идентичность объекта.
Прежние layout 1/2 отклоняются как несовместимые.
Предыдущие публикации сохраняются историей Git.

Чтение и запись переносимых данных идут напрямую через Git objects. Checkout использует
контролируемый профиль без hooks/глобальных filters и нормализации CRLF. Преобразующие
локальные `info/attributes` отклоняются. Предметные переходы, receipts, immutable source
и решения конфликтов проверяет [Core](../../packages/core/README.md#переносимое-состояние-и-обмен).

## Использование из CLI

`@relay/git-sync` — внутренняя Bun-библиотека с единым входом `executeGitSyncRequest`.
CLI передаёт явный снимок среды и signal; предметная репликация принадлежит Core,
а владение Git/SSH процессами — механизмам Runtime.

```ts
import { executeGitSyncRequest } from "@relay/git-sync";

const result = await executeGitSyncRequest(
  { version: 1, action: "auto", options: { cwd: "/путь/к/проекту" } },
  { env: { ...process.env } },
);
```

Запрос копируется и проверяется до I/O; поздняя правка исходного объекта не меняет
принятое обращение. Параллельные вызовы имеют независимые среды и сигналы. При source-запуске
guard helper создаётся лениво. Compiled CLI подключает private guardian и SSH-probe роли
в собственном entrypoint; отдельного исполняемого приложения синхронизации нет.

Server вызывает совместимый `relay --git-sync-request`. Этот вход принимает один JSON
до EOF и возвращает один JSON; он вызывает ту же библиотеку без рекурсивного debounce.
Схемы envelope принадлежат Contracts:

```json
{
  "version": 1,
  "action": "auto",
  "options": { "cwd": "/путь/к/проекту" }
}
```

Успех — `{version:1,ok:true,data}`, отказ — `{version:1,ok:false,error}` с
`code/message/exitCode/details?`. Общий wire budget — 16 MiB.
`auto` проверяет расписание; `now` выполняет явное окно; `status` без refresh читает
локальную диагностику. `status` с `refresh:true` получает сведения remote без push
и импорта. `request.get` читает ранее назначенный ID, не создавая нового обмена.

Явные now/refresh сохраняют bounded исходы queued/running/completed/failed/unknown.
Истечение ожидания и unknown не означают отсутствия эффектов; гарантии доставки
по-прежнему обеспечивают outbox и подтверждения Core. Правила ожидания и разрешения
конфликтов имеют основной источник в руководстве CLI.

## Разработка

Корневая [сборка CLI](../../README.md#быстрый-старт) включает пакет в бинарник `relay`.
Адресные проверки: `bun run --filter @relay/git-sync typecheck`, `test:unit` и `test:integration`.
Процессный набор использует собранный CLI и запускается через Turbo с зависимостью от его сборки.
Проверки используют изолированные SQLite/Git/HOME по [правилам наборов](../../tests/README.md).
Source-запуск создаёт свежий Runtime helper в `.artifacts/<дата>/git-sync-source-runtime`;
standalone CLI использует собственную guardian-роль. Git/SSH процессы имеют конечные
deadline и cleanup; пользовательские SSH credentials и overrides сохраняются.
