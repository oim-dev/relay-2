# Работа над Core

Перед изменениями прочитай [README](README.md), [архитектуру](../../docs/ARCHITECTURE.md)
и общие правила из [корневого AGENTS.md](../../AGENTS.md).

## Предметная ответственность

- Core владеет сценариями, предметными фильтрами, составами и проверкой сохранённых
  вложенных данных. SQL и механизмы транзакций принадлежат Storage; контекст каталогов —
  Project Runtime; синтаксис команд и представление — CLI.
- Публичный API выражает предметные операции. Универсальная мутация, обходящая правила
  сервисов, остаётся внутренним примитивом; не экспортируй её ради тестов.
- Разрешение ID, ключей, алиасов и типизированных ссылок использует общего владельца.
  Повторяющееся правило сначала ищи в существующих модулях; предметные различия
  валидаторов сохраняй явными.
- Переносимые данные относятся к Contracts, внутренние проверенные входы и расчёты —
  к контрактам рядом со сценарием. После декодирования работай с предметными типами.

## Структура и зависимости

- `src/index.ts` — единственный публичный вход и единственный файл в корне `src`.
  Внутренние модули импортируют конкретного владельца, а не публичный barrel пакета.
- `knowledge/`, `tasks/`, `planning/`, `history/` содержат свои сценарии, декодеры,
  правила, типы, сообщения и unit-тесты. Разделы документов принадлежат `knowledge/`.
- `entities/` содержит общие адреса, JSON-проверку, CAS, примитивы записи и пагинацию;
  этот нижний слой не импортирует предметные сервисы или составные проекции.
- `projections/entity-reader.ts` собирает предметные декодеры для общего чтения.
  Он импортирует нижние codecs и правила разделов напрямую; декодеры не зависят
  от проекций или оркестрации своих сервисов.
- `queries/` владеет общим поиском, обзором, status и doctor. История и запросы
  используют проекции, планирование — чтения задач; обратных зависимостей к этим
  оркестраторам у нижних модулей быть не должно.
- Межобластные импорты направляй в конкретные read/codec-модули или нужный сервис.
  Не создавай промежуточные `index.ts`, общий `types/utils` или DI-слой ради каталогов.
  Интеграционные тесты и их fixtures остаются в `tests/integration/`.

## Инварианты сценариев

- Проверка состояния и запись выполняются в общей транзакции. Ревизия принадлежит
  изменяемому агрегату и проверяется до no-op; составная операция проверяет всех
  затронутых владельцев. Отказ откатывает записи, алиасы, счётчики и поколение.
- Комментарии задачи дописываются в независимый журнал. Запись содержания задачи
  не должна заменять комментарии устаревшей проекцией или менять их историю.
- Составное чтение, вычисляемый результат и поколение относятся к одному снимку.
  Чистые правила и графы получают данные аргументами, а не читают БД самостоятельно.
- Общий граф или индекс строй один раз на снимок операции. Прослеживай чтения внутри
  циклов; ограничение выдачи после полной загрузки не ограничивает стоимость запроса.
  Сохраняй ограниченные SQL-страницы там, где они доступны; кеш требует правил актуальности.
- Декодер отличает допустимое отсутствие значения от повреждения. Снятые связи,
  исторические снимки и пустые допустимые значения сохраняют свой предметный смысл.

## Выбор проверок

- Чистые алгоритмы проверяй без SQLite; транзакции, конкурентность и составные чтения —
  с реальной БД. При отказе мутации проверяй сохранность затронутых данных.
- Адресные наборы из корня: `bun run --filter @relay/core test:unit` и
  `bun run --filter @relay/core test:integration`. Выбирай файлы по изменённой области
  и зависимостям; [карта сценариев](../../docs/development/TEST-COVERAGE.md) помогает их найти.
- Для риска повторных чтений допустима небольшая функциональная проверка их числа.
  Она защищает стоимость сценария, а не произвольный порядок внутренних SQL-команд.
