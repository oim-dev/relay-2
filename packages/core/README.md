# Relay Core

Core отвечает за правила работы с данными Relay: знаниями проекта, задачами,
планами и историей работы. Он проверяет допустимость изменений и обеспечивает
согласованное выполнение связанных операций.

Пакет предназначен для разработчиков интерфейсов Relay. Через него приложение
создаёт и изменяет предметные данные, получая одинаковое поведение независимо
от способа взаимодействия с пользователем. Например, завершение задачи учитывает
её обязательства, а изменение плана проверяет согласованность его состава.

Core работает с открытой базой выбранного проекта. Выбор проекта и представление
результата выполняет вызывающее приложение.

## Использование в приложении

`@relay/core` — внутренний пакет монорепозитория. Он подключается как workspace-зависимость
и используется из TypeScript-исходников; отдельный процесс или сборка библиотеки не нужны.
Предметные изменения выполняются асинхронно через `CommandStore`; открытая
`ProjectDatabase` предоставляет его как `db.commands`. Поставляемый адаптер
из [Storage](../storage/README.md) работает с SQLite в Bun. Обычные предметные чтения
остаются явно локальными и синхронными через `ProjectStore`.
PostgreSQL-адаптер и серверный API пока не реализованы.

Пример сохраняет документ в уже инициализированном проекте. Замените путь к базе
на вычисленное значение `meta.databasePath` из результата `relay config get --format json`:

```ts
import { KnowledgeService } from "@relay/core";
import { ProjectDatabase } from "@relay/storage";

const db = ProjectDatabase.open("/путь/к/project.sqlite");
try {
  const knowledge = new KnowledgeService(db);
  const document = await knowledge.create(
    "document",
    { name: "Договорённости", body: "Все изменения проходят ревью." },
    "developer",
  );

  const updated = await knowledge.update(
    "document",
    document.id,
    { body: "Изменения проверяются тестами и проходят ревью." },
    { actor: "developer", ifRevision: document.revision },
  );
  const saved = knowledge.get("document", updated.id);
  console.log(saved.data.body);
} finally {
  db.close();
}
```

Запись сохраняет автора создания и автора последнего изменения. `CommandWriteOptions`
принимает прочитанный локальный `ifRevision` либо переносимый `expectedVersion` владельца.
Можно передать оба условия — проверяются оба, включая no-op. Если данные уже изменены,
операция завершится конфликтом.
Вызывающее приложение должно перечитать состояние и согласовать изменение с пользователем.

Методы изменения `KnowledgeService`, `TasksService`, `PlanningService` и `HistoryService`
возвращают Promise: их нужно `await` до освобождения соединения в `finally`, включая
отказ операции. Внешняя `db.transaction(async () => …)` не нужна и недопустима:
callback SQLite-транзакции строго синхронен. Исполнитель сам выполняет асинхронную
загрузку, чистый расчёт и короткий атомарный commit с проверкой исходного контекста.

Одна предметная операция проверяет и сохраняет связанные изменения атомарно.
Неверный ввод, повреждённые данные и конфликт ревизии возвращаются как ошибки;
стабильный код ошибки позволяет приложению выбрать способ представления результата.
Точные условия отдельных операций описаны в документации их публичного API.
Предметные изменения для публикации проходят через этот executor. Обычная низкоуровневая
Storage mutation без именованной ленты model 2 не считается публикуемой предметной
командой; закрытый initial/legacy контракт описан в
[разделе changeset ТЗ](../../GIT-SYNC-IMPLEMENTATION-SPEC.md#6-changeset-и-durable-outbox).

Обычные `get`, `list`, `listPage` и расчёты прогресса возвращают результат синхронно.
`QueryService.getMany` читает выбранные адреса из одного снимка,
возвращая полные записи либо краткие проекции с ошибками отдельных элементов.
Асинхронный `QueryService.getManyVersioned(refs, options)` возвращает Promise с
`{ data, versions }`: прежней full/summary-проекцией и версиями успешных ID из одного
согласованного anchor. Порядок, повторы, адресные ошибки, generation и effective-содержание
сохраняются; summary остаётся узким чтением. CLI использует этот API для
`get --with-versions`, помещая `versions` в `meta.versions`. Смена anchor прерывает
чтение вместо публикации смешанного результата. Соединение закрывается после `await`.
`BatchService.execute` асинхронно объединяет предметные действия в атомарную запись
с локальными ссылками и квитанцией безопасного повтора. `getResult` читает первоначальную
квитанцию локально и синхронно; соединение должно оставаться открытым.
Сценарии вызова описаны в [руководстве CLI](../../docs/CLI.md#применить-связанный-пакет);
правила мутаций остаются у предметных сервисов.

Для визуализации без полных текстов доступны синхронные
`readHistoryTimeline(db, {offset, limit, generation?})` и
`readRelationNeighborhood(db, {ref?, depth?, direction?, offset, limit, generation?})`.
Окна и их границы принадлежат одному snapshot; продолжение требует исходного поколения.
Они не ограничивают размер проекта, но пока сканируют узкие metadata для хронологии и
входящих связей: размер страницы ограничивает ответ, а не всю работу SQL.
Подробные формы и стоимость описаны в контрактах
[истории](../contracts/src/history/history-timeline.types.ts) и
[соседства](../contracts/src/queries/relation-neighborhood.types.ts).

`CommandExecutor.execute(command, options)` выполняет одну именованную операцию из
`BATCH_OPERATIONS` тем же async-исполнителем, что точечные сервисы и `BatchService`.
Для одиночной команды ключ квитанции необязателен. Метод
`executor.executeCommands(commands, options)` принимает атомарный массив с теми же
`$ref`/`$revision`. Функциональный вход имеет форму
`await executeCommands(db.commands, commands, options)`. Можно передать самостоятельный
`CommandStore` конструктору `CommandExecutor`; локальное `getResult` доступно при
создании исполнителя с `ProjectStore`.

`options.expectedAddresses: [{ref, expectedId}]` проверяет сохранённую привязку
прочитанного адреса к ID; устаревший ввод даёт `ADDRESS_CHANGED`. Точечные сервисы
принимают тот же набор через второй аргумент конструктора:
`new KnowledgeService(db, { expectedAddresses })`.
После локально известного переназначения запись или новая ссылка по этому ключу
без guard отклоняется с `ADDRESS_GUARD_REQUIRED`, включая точечные сервисы.
Для сохранённых ссылок предпочтителен постоянный ID.

`CommandExecutionContext.expectedVersion` задаёт токен владельца по умолчанию;
явный `expectedVersion` параметров метода имеет приоритет. Он не подставляет
локальный CAS и не отменяет отдельно переданный `ifRevision`.

Для переносимого предусловия используйте
`await executor.readVersioned(ref, kind?)` либо
`await readVersionedEntity(db.commands, ref, kind?)`. Результат содержит `entity`
и отдельные `versions.recordVersion`/`versions.aggregateVersion` из одного контекста.
В `NamedCommand.expectedVersion` и `CommandWriteOptions.expectedVersion` передаётся именно `versions.aggregateVersion`
изменяемого владельца: он учитывает нормализованные части, но не независимый журнал
комментариев. Можно передать его вместо `ifRevision` или вместе с ним; тогда
проверяются оба условия, в том числе перед no-op. Обычные синхронные чтения и форма
`EntityRecord` этим API не заменяются. Raw `readVersionedEntity` не подменяет
пользовательскую проекцию `QueryService.getManyVersioned`. Подробности — в
[контракте команд](../contracts/src/batch/command.types.ts) и
[versioned read](src/commands/command-versioned-read.ts).

## Переносимое состояние и обмен

`ReplicationService` получает открытый `ReplicationStore` и работает с ним синхронно,
без собственных файлов, процессов или сети. Это отдельный локальный API репликации,
а не асинхронный предметный writer. Приложение вызывает `prepare(remoteSnapshot, history?, options?)`,
публикует подготовленный snapshot и только после доказанного принятия общей веткой
вызывает `accept(publishedSnapshot, history?)`. `null` вместо remote обозначает первую
публикацию; `history` передаёт контекст промежуточных публикаций, необходимый для проверки
переходов.

`prepare` возвращает `BoundedPreparedReplication`. В `options` можно передать
`afterSequence` и меньший `budget`; `selection` описывает рассмотренное окно,
отложенные зависимости, pending на момент подготовки и следующий курсор. После accept
актуальный остаток читается через `status()`. Ограничение источников
действует до декодирования их JSON, но не ограничивает весь canonical snapshot,
полный witness выбранного решения или overlay при `accept`/`resolve`. Конец окна не означает
подтверждение всей очереди; правила курсора и бюджетов описаны в
[TSDoc `prepare`](src/replication/replication.ts).

`capture()` возвращает первичные сохраняемые записи и нормализованные части, адреса,
отдельные неизменяемые комментарии и первоначальные batch-квитанции. Снимок не подменяет
сохранённые данные эффективной пользовательской проекцией. Переносимая SHA-256 версия
не зависит от локальной CAS-ревизии; часы не определяют победителя слияния.

Каждая внешняя предметная транзакция, включая связанные изменения и квитанцию,
попадает в durable outbox атомарно. `prepare()` объединяет готовую часть очереди;
конфликтный changeset блокирует зависимые от него пакеты, сохраняя доставку независимых.
`accept()` вызывается только после подтверждения общей веткой и сохраняет более
поздние локальные записи. Повторный приём не создаёт echo-outbox.

`status()` показывает счётчики, `conflicts()` — весь сохранённый журнал реальных
конфликтов; `prepare().conflicts` относится только к рассмотренному окну.
`blocked()` отдельно возвращает причины ожидания dependencies с `state: "pending"`:
это полная диагностическая выборка графа очереди, не дешёвое чтение одного окна.
`resolve(id, decision, actor, {budget?})` проверяет актуальность решения на полном
overlay и возвращает ограниченный preview первого окна; cursor у resolve не принимается.
Допустимы `local`/`remote` и custom v1 только для исходных текстовых эффектов документа.
Закрытые записи, неизменяемые source/receipt и межзаписные правила сохраняют силу.
`bootstrap(snapshot, options?)` восстанавливает новую базу, созданную через
`ProjectDatabase.createReplica(path, projectId)`, с исходными ID и квитанциями.
Точные условия проверки цепочки, результаты и ошибки описаны в
[контрактах API](src/replication/replication.ts). Полные требования обмена и границы
последующих адаптеров заданы в [ТЗ синхронизации](../../GIT-SYNC-IMPLEMENTATION-SPEC.md).

## Работа над пакетом

Core используется локальной CLI и развивается вместе с её сценариями. Общий
порядок подготовки исходников описан в [быстром старте Relay](../../README.md#быстрый-старт).
Чистые правила проверяются модульными тестами, а сохранение и согласованность данных —
интеграционными тестами с SQLite.

- [Архитектура Relay](../../docs/ARCHITECTURE.md) объясняет место предметных правил в системе.
- [Организация проверок](../../tests/README.md) помогает выбрать и запустить нужный набор.
- [Локальные инструкции](AGENTS.md) фиксируют границы и инварианты при изменениях Core.
