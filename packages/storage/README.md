# @relay/storage

Storage сохраняет локальные данные Relay и защищает их от частично выполненных
операций и перезаписи устаревшей версии. Каждый проект имеет собственную SQLite-базу.
Пакет нужен Core для выполнения сценариев и приложению — для открытия и закрытия
соединения с выбранным проектом.

Пакет приватный, использует `bun:sqlite` и экспортирует исходный TypeScript.
Окружение готовится по [корневому быстрому старту](../../README.md#быстрый-старт).
Для предметных изменений приложение вызывает Core; Storage предоставляет механизм
хранения и возвращает сырые собранные карточки, содержимое которых проверяет Core.

## Прочитать страницу задач

Этот фрагмент предназначен для Bun-кода приложения внутри монорепозитория.
Рабочий каталог должен быть корнем инициализированного проекта с `relay.config.json`
([создание проекта](../../docs/CLI.md#проект-и-размещение-данных)).

```ts
import { resolveProject } from "@relay/project-runtime";
import { ProjectDatabase } from "@relay/storage";

const location = resolveProject({ cwd: process.cwd() });
const database = ProjectDatabase.open(location.databasePath);
try {
  const page = database.listPage("task", { offset: 0, limit: 20, sort: "key" });
  console.log(
    page.items.map((task) => task.key),
    page.total,
  );
} finally {
  database.close();
}
```

Результат — до двадцати ключей задач и их полное число из одного снимка. `listPage`
загружает только выбранное окно; `list` загружает весь набор с содержанием.
Для связанных записей `listByField` отбирает карточки по строковому полю содержания,
а `getMany` читает пакет постоянных ID в порядке запроса. `getManyIdentities` читает
идентичности того же пакета без содержания и комментариев. Контракты выборок описаны
в [`ProjectDatabase`](src/database/project-database.ts).

## Представление данных и версии

Критерии, этапы, включения задач, связи, участия и назначения адресов хранятся
первичными частями отдельно от записи владельца. Идентичность части —
`(ownerId, kind, id)`; у неё собственные версия, предки, позиция и признак снятия.
Коллекции не дублируются в owner payload. Чтения `get`, `getMany`, `list`, `listByField`
и `listPage` собирают привычные агрегаты: запрос владельцев/журналов и один пакет
частей только выбранных владельцев. Число запросов не растёт с числом карточек;
`listPage` дополнительно читает total, а пустой набор владельцев не загружает части.
Идентичности читаются одним запросом без JSON-декодирования. `hasArrayItemByField`
проверяет наличие сразу в primary parts и raw fallback одним SQL без выдачи содержания.
`getComponents(ownerIds?)` отдельно возвращает первичные части, включая tombstones.

Собранная локальная `EntityRecord` содержит `revision` для CAS этой БД.
Переносимое состояние сохраняет первичные записи и части с их версиями, без локального
CAS в `PortableEntityRecord` и без effective-проекций UI. Исторические ревизии внутри
неизменяемых квитанций и материалов остаются дословными. Предусмотренный `CommandStore`
возвращает версии записи и агрегата отдельно от `data`; их использование описано
в [Core README](../core/README.md#использование-в-приложении).

Журнал комментариев остаётся append-only. Непарные UTF-16 surrogate в `title`/`body`
сохраняются через внутренний JSON-string carrier вместо потери при UTF-8-кодировании;
соответствующий plain TEXT слот не содержит второй копии текста. Публичная форма
`TaskComment` и исходные code units восстанавливаются без нормализации. Выбор carrier
и его содержание защищены той же неизменяемостью, что и обычный текст комментария.

## Открытие, запись и обмен

`ProjectDatabase.open` требует существующую совместимую базу и не создаёт пустую
вместо утраченной. Совместимые схемы v1/v2/v3 автоматически обновляются до **v4**
с сохранением карточек, scoped ID частей, адресов, журналов, квитанций и поколения.
Исходные payload/ID/digest уже имеющегося outbox v3 не переписываются; для v1/v2
создаётся baseline после нормализации. Невозможная сохраняющая миграция, включая
повреждённые исходные UTF-8 bytes, отклоняется без исправления истории и частичного DDL.
Соединение принадлежит вызывающему и закрывается в `finally`.
Связанные записи объединяются через `transaction`, составные чтения — через `snapshot`;
оба callback строго синхронны. WAL допускает чтение при активном писателе, но запись
в один файл выполняется последовательно.

`ProjectDatabase.openReadonly` проверяет только текущую схему без миграций и переключения
журнала; читает также живой WAL по переданному имени. SQLite запрещает запись через это
соединение. Для публикации принадлежащей вызывающему **private** staging-БД предназначен
`withProjectDatabasePublication(path, publish)`: он завершает WAL и удерживает эксклюзивную
SQLite-блокировку до синхронного создания hardlink. К уже публичной БД этот API неприменим;
точные ограничения владения и callback описаны в его TSDoc.

`ProjectDatabase` предоставляет локальные синхронные `ProjectStore`/`ReplicationStore`
и реальный асинхронный `CommandStore` как `db.commands`. Общий исполнитель Core
использует `load` и `commit`: ожидания находятся вне SQLite callbacks, а внутри commit
проверяются guards и атомарно сохраняются подготовленные эффекты. Предметные writers
нужно `await` до закрытия соединения; async callback в `transaction` недопустим.

Одна внешняя изменяющая транзакция сохраняет один changeset затронутых владельцев,
частей, адресов, комментариев и квитанций; границы предметных шагов сохраняются
в упорядоченных переходах. Savepoint откатывает связанные очереди вместе с данными.
Импорт и технические подтверждения не порождают echo-outbox; обычный readonly snapshot
не выполняет flush. Предметное объединение и проверка снимка принадлежат Core.

`importReplication(snapshot, plan?)` принимает проверенный Core материал; sparse plan
меняет только затронутые записи и части, сохраняя готовые ID, версии и позиции.
Parts-only импорт обновляет локальный CAS затронутого владельца, даже если версия
его первичной записи прежняя. Для восстановления `createReplica(path, projectId)`
создаёт специальную пустую базу, которую нужно заполнить через
`ReplicationService.bootstrap(snapshot, options?)` до обычной работы.

`acquireLocalLock(lockFilePath, {timeoutMs: 0})` возвращает владение отдельным
межпроцессным mutex с `release()` для `finally`. Оно допускает сетевые `await`
между получением и освобождением; предметная транзакция при этом не удерживается.
Вызывающий заранее создаёт каталог и канонизирует путь самого lock-файла.
Занятость даёт `LOCAL_LOCK_BUSY`; при аварии mutex освобождает ОС. Файл не удаляется.
`withLocalFileLock` сохраняет прежний строго синхронный callback-контракт.
