# @relay/contracts

Contracts помогает компонентам Relay одинаково понимать передаваемые данные: что
считается задачей, как описать изменение и как сообщить об ошибке. Пакет нужен
разработчику CLI или библиотеки, когда один и тот же контракт используется по обе
стороны вызова.

Это приватный пакет монорепозитория, экспортирующий исходный TypeScript. После
[подготовки репозитория](../../README.md#быстрый-старт) потребители подключают его
через `@relay/contracts`. Пакет не зависит от Bun, SQLite или пользовательского
интерфейса.

Например, запрос страницы можно описать и проверить до обращения к данным:

```ts
import { validateEntityPageRequest, type EntityPageRequest } from "@relay/contracts";

const page: EntityPageRequest = { offset: 0, limit: 20, sort: "key" };
validateEntityPageRequest(page);
```

Проверка оставляет запрос неизменным; неверные границы или сортировка приводят к
`RelayError` с кодом `INVALID_ARGUMENT`. Такой запрос принимают списки Core и Storage.
Обработчики ошибок опираются на `code` и `details`, а не на текст сообщения.

Тип сам по себе не проверяет JSON. Локальная `EntityRecord` описывает сырую карточку,
собранную Storage из записи владельца и частей, с `revision` для CAS конкретной БД.
Проверенный Core результат `ProjectEntity` связывает `kind` с формой `data`.
Проверки существования ссылок, состояния проекта и допустимости изменений выполняет
Core: общие типы и чистые проверки входа не заменяют предметный сценарий.

## Команды и хранение

`NamedCommand` и `CommandOptions` задают общий ввод точечной записи и batch.
`CommandStore` — асинхронный контракт `load`/`commit`: согласованные наблюдения,
guards и `CommandCommitPlan` с уже рассчитанными эффектами и упорядоченными переходами.
Его SQLite-реализация доступна как `db.commands`; I/O отделено от чистых правил Core
и синхронных транзакционных callbacks адаптера. Контракт не делает обычные локальные
readers асинхронными и сам по себе не реализует другую СУБД.
Точные типы находятся в [command port](src/commands/command-store.types.ts),
использование и непрозрачные version tokens — в [Core README](../core/README.md#использование-в-приложении).

## Переносимые записи

`PortableComponent` описывает первичную часть с идентичностью `(ownerId, kind, id)`,
собственной версией/предками, устойчивой позицией и tombstone. `ComponentValueMap`
связывает `kind` с формой `value`: например, содержание этапа и включение задачи
являются разными частями. Декларация `collection` сохраняет различие отсутствующего
поля и пустого массива. Чистые `splitComponentRecord`/`assembleComponentRecord`
механически разделяют и собирают raw-агрегат без UI-проекций; они не заменяют
предметную проверку. Контракты частей описаны в [типах компонентов](src/components/component.types.ts).

Модель 2 `PortableProjectSnapshot` хранит первичные записи и `components`, адреса,
отдельные комментарии, первоначальные квитанции, подтверждения и контекст публикации.
`PortableEntityRecord` не содержит локальный `revision`; исторические числовые ревизии
в содержимом и квитанциях сохраняются дословно. `ReplicationChangeset` выражает одну
атомарную транзакцию с исходными/конечными версиями и эффектами; конфликт относится
ко всей транзакции. Переносимый snapshot не является пользовательской проекцией карточек.

Тексты JSON сохраняют точные UTF-16 code units, включая непарные surrogate.
Внутренний JSON-carrier комментариев SQLite не меняет публичный `TaskComment`.
Идентичности и авторство проверяются по собственному строковому контракту;
неверное значение отклоняется, а не исправляется заменой символов.

`GitSyncRequest`/`GitSyncResponse` задают процессный протокол версии 1; непроверенный
`input` запроса декодирует владелец действия, а предметные мутации проверяет Core.

и [правила разработки](../../docs/development/README.md).
