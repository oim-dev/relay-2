# ТЗ: транзакционные команды и синхронизация локальных реплик Relay

## 1. Назначение, статус и нормативные обозначения

ТЗ определяет реализацию единого исполнителя предметных команд и обмена локальных
SQLite-реплик через одну общую Git-ветку. Пользователь сохраняет изменения offline,
видит действительное состояние доставки, получает материалы конфликтов и может
восстановить опубликованные данные. Автоматическая доставка работает независимо
от времени жизни отдельного вызова CLI.

Архитектурное обоснование и примеры находятся в
[согласованном предложении](GIT-SYNC-DESIGN.md). Настоящее ТЗ — основной источник
подробных требований этой реализации. Оно описывает целевой контракт, а не отчёт
о выполнении. Все приведённые ниже новые API, форматы и команды требуют реализации
и проверки.

**MUST** означает обязательное требование; **MUST NOT** — запрет; **SHOULD** —
предпочтительное решение, отступление от которого требует явно обоснованного
эквивалентного поведения. Наличие типа, каркаса приложения или test script без
проверок не удовлетворяет MUST.

### Исходная ревизия

База: `0ec8ff8003f98ddf4d8706c652f8bf76d0c802e8`.

- `apps/git-sync` пока не реализует обмен.
- Core синхронно использует `ProjectDatabase`; batch вызывает существующие сервисы
  внутри общей транзакции.
- SQLite имеет schema v2; `transaction` и `snapshot` принимают только синхронные callbacks.
- Комментарии задач — отдельный append-only журнал, независимый от CAS содержания.
- Batch receipts неизменяемы, не имеют TTL, содержат нормализованный запрос с автором
  и первоначальный результат; повтор не проверяет заново уже изменившиеся адреса.

Эти факты относятся к базе предложения. Реализация MUST сохранять их предметные
гарантии при изменении технической структуры.

### Область

В этап входят Core/Storage ports, changeset/outbox, переносимый формат, merge,
ручной и автоматический Git-обмен, конфликты, restore, CLI управления, supervisor
и пользовательский автозапуск Linux/macOS/Windows. Реальные PostgreSQL, Server,
HTTP API, Web, MCP и перенос данных первой версии в этап не входят.

## 2. Владельцы и границы

| Владелец                   | Обязательная ответственность                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/contracts`       | Схемы команд и результатов, переносимые записи/версии/changeset, ошибки, snapshot и versioned process protocol; без Bun, SQL, FS и UI |
| `packages/core`            | Единый executor, правила переходов, авторство, адреса, агрегатные инварианты, подготовка и проверка предметных эффектов               |
| `packages/storage`         | Реальный SQLite-адаптер портов, SQL, CAS/предикаты, атомарная запись, outbox, checkpoints, миграции и дедупликация                    |
| `packages/project-runtime` | Выбор и физическая идентичность БД, пути, конфигурация, launcher/lifecycle, совместимость; регистрация systemd/launchd/Task Scheduler |
| `apps/git-sync`            | Git-транспорт, подготовка публикации, merge orchestration, conflicts, workers, процесс supervise и планирование доставки              |
| `apps/cli`                 | Gunshi-команды, ввод/вывод, преобразование пользовательского действия в общий контракт и диагностика                                  |

**BND-01.** Приложения MUST NOT импортировать исходники друг друга. CLI вызывает
публичный Runtime/Contracts и отдельный бинарник либо process protocol Git Sync.

**BND-02.** Все предметные записи, включая импорт и resolve, MUST проходить проверку
Core. Внутренние Storage-примитивы MUST NOT становиться публичным способом обойти
неизменяемость и предметные переходы.

**BND-03.** Git, сетевые обращения и команды системного менеджера служб MUST NOT
появляться в чистых правилах, переносимых контрактах и обычных предметных чтениях.
Git API, Core и snapshot API MUST иметь одинаковую семантику на Linux, macOS и Windows.

## 3. Единое исполнение предметных команд

**CMD-01.** Core MUST предоставлять `executeCommands`: одиночная мутация является
вызовом с массивом из одной команды; batch использует этот же исполнитель для
нескольких команд. Реализация MUST иметь один каталог схем/обработчиков и единые
правила формирования результатов. Обёртка над двумя независимыми реализациями
правила этому требованию не соответствует.

**CMD-02.** Предметные CLI-команды MUST сохраняться как адаптеры. Чтения MUST оставаться
отдельными оптимизированными сценариями; изменение executor не оправдывает загрузку
всего проекта для адресного чтения или ограниченной страницы.

**CMD-03.** Исполнитель MUST принимать контекст одного проекта, автора, команды,
ожидаемые версии и адресные guards, режим проверки и необязательный контекст
идемпотентности. Поля команд проверяются общей схемой; неизвестные поля отклоняются.
Внутренний контракт MUST различать отсутствие поля и явный `null`, когда это
различие имеет предметный смысл.

**CMD-04.** Порядок команд batch и семантика `$ref`/`$revision` MUST сохранять
[действующий контракт](CLI-GET-BATCH-SPEC.md#локальные-результаты-и-ревизии): ссылки
на предыдущие результаты, правильный владелец ревизии, отсутствие интерполяции
Markdown. Перенос на единый executor MUST NOT самовольно разрешать ссылки вперёд.
Настройки, workspace, сетевые операции и жизненный цикл файлов БД не входят
в предметный batch; атомарной транзакции между независимыми проектами нет.

**CMD-05.** Все явные и неявные эффекты одной изменяющей транзакции MUST сохраняться
атомарно с одним changeset. Приложение и его доска, исходный и целевой состав transfer,
участия, адреса и receipt входят в ту же границу. Внутренние savepoint не создают
дополнительных пакетов доставки.

**CMD-06.** Ошибка до commit MUST откатывать предметные записи, версии, адреса,
счётчики, поколение, receipt и outbox. `--check` MUST выполнять те же правила с откатом,
без резервирования ID, ключей и operation key. Повтор уже сохранённого batch
и чистый no-op без новых сохраняемых данных MUST NOT создавать changeset.
Новая квитанция batch является сохраняемым эффектом и требует changeset даже
при отсутствии изменения остальных предметных записей.

**CMD-07.** CAS MUST проверяться до признания no-op. Конкурентный отказ MUST NOT
устраняться подстановкой свежей ревизии вместо переданной клиентом.

**CMD-08.** Успех локального commit MUST возвращаться независимо от наличия origin,
сети и worker. Ошибка последующего вывода или уведомления worker не откатывает commit.

## 4. Порты хранения и асинхронная граница

**PORT-01.** Основной сценарий MUST выражаться как
`load context → calculate effects → atomic commit`.
Core зависит от контракта хранения, а не от конкретного `ProjectDatabase`, SQL
или `bun:sqlite`. Контракт размещается у владельца потребности; Storage предоставляет
SQLite-реализацию. Переносимые DTO принадлежат Contracts.

**PORT-02.** Внешняя граница I/O MUST допускать асинхронную реализацию чтения и commit.
Чистый расчёт MUST быть синхронной функцией проверенного контекста без скрытых запросов.
SQLite-адаптер MUST сохранять строго синхронный callback короткой SQL-транзакции.
Возврат Promise из `ProjectDatabase.transaction` MUST оставаться ошибкой.

**PORT-03.** Загруженный контекст MUST включать проверяемые версии и предикаты,
на которых основан результат: существование/отсутствие записи, состав обязательств,
единственность включения задачи, отсутствие циклов и активного другого владельца.
Commit MUST проверять их атомарно с записью, защищая от write skew и phantom insert.
CAS только изменяемых строк недостаточен.

**PORT-04.** Порт commit MUST принимать ожидаемый контекст, точные эффекты,
необязательную batch receipt и changeset. Результат MUST различать успех,
конкурентный отказ и инфраструктурную ошибку; неполный успех запрещён.

**PORT-05.** Подготовка полного snapshot MUST читать один согласованный снимок.
Сеть и Git MUST выполняться вне write transaction. Длительные расчёты SHOULD
выполняться вне блокировки записи, с короткой повторной проверкой guards при commit.

**PORT-06.** Реализация MUST поставлять работающий SQLite-адаптер и необходимые
порты. Заглушка PostgreSQL, возвращающая готовые данные или вызывающая SQLite,
MUST NOT объявляться поддержкой PostgreSQL.

## 5. Идентичность, версии и независимо изменяемые элементы

### Идентичность и контекст версии

**ID-01.** Проект, локальная реплика, сущность, независимо изменяемый элемент,
changeset, конфликт, решение и экземпляр процесса MUST иметь разные по смыслу ID.
`projectId` общий у реплик; `replicaId` постоянен для одной локальной БД;
`instanceId` меняется при каждом запуске процесса.

**ID-02.** Все предметные ID MUST выделяться до сохранения соответствующих эффектов
и оставаться прежними при retry, renumber и восстановлении. Копия backup,
начинающая независимую запись, MUST получить новый `replicaId` для новых changeset,
сохраняя IDs ранее записанных пакетов.

**VER-01.** Каждая независимо изменяемая запись MUST иметь переносимый токен `version`
и отдельный массив `parents` непосредственно предшествовавших переносимых версий.
Токен — непрозрачная строка SHA-256 по предметному алгоритму SNAP-03, а не вложенный
объект с `id`. Он не является временем, счётчиком или значением для выбора победителя.

**VER-02.** Изменение MUST ссылаться на исходную версию; создание имеет отсутствие
base; снятие сохраняет версию снятия и необходимый tombstone. При объединении
двух различающихся ветвей создаётся версия с обеими родительскими версиями.
Принятая origin версия затем сохраняется на всех репликах. Повтор неизменённого
эффекта не создаёт новую версию.

**VER-03.** Локальный числовой `ifRevision` MUST продолжать защищать локальный
прочитанный результат, включая no-op. Он MUST NOT использоваться как переносимый
арбитр между репликами. При импорте локальный CAS guard не должен возвращаться
к ранее выданному значению и допускать ABA. Технические локальные guards хранятся
отдельно от переносимой версии.

**VER-04.** Snapshot MUST сохранять переносимые версии и предметные данные точно.
Технические счётчики локального CAS не являются распределённым состоянием.
Числовые ревизии, сохранённые как исторические факты внутри receipts и checkpoints,
MUST переноситься дословно. Новый публичный переносимый write contract MUST
передавать `expectedVersion`; совместимость прежнего `ifRevision` обеспечивается
локальным адаптером, а не сравнением номеров разных реплик.

### Записи и агрегаты

**REC-01.** Критерии задач, этапы планов, включения задач, связи документов,
участия и назначения ключей MUST иметь собственные ID. Там, где элемент изменяется
независимо, он MUST иметь собственную сохраняемую запись и переносимую версию,
а не только позицию в заменяемом JSON-массиве.

**REC-02.** Независимые записи MUST сохранять агрегатные правила:

- `done` проверяет полный необходимый набор обязательств;
- `transfer` проверяет обе стороны и исключает двойное активное включение;
- `session`/`run` проверяют активное владение, автора, цепочку участия и закрытие;
- неизменяемый material истории сохраняет своё происхождение и ссылки;
- комментарий добавляется по новому ID без замены содержания задачи.

**REC-03.** Комментарии, исторические checkpoints и batch receipts MUST оставаться
неизменяемыми. Одинаковый ID с другим содержанием MUST давать конфликт/повреждение,
а не SQL upsert, выбирающий последнюю запись.

**REC-04.** Порядок коллекции MUST определяться устойчивыми позициями, хранимыми
с элементами. Вставка MUST NOT переписывать номера всех соседей. Одновременные
независимые вставки MUST иметь детерминированный tie-break по ID; несовместимые
перемещения MUST выявляться проверкой порядка. Компактация позиций, если понадобится,
MUST сохранять порядок и проверять версию состава отдельной атомарной операцией.

## 6. Changeset и durable outbox

### Формат v1

Ниже задан логический контракт. Реализация схемы MUST обеспечивать эту информацию;
SQL-таблицы могут разделять заголовок, эффекты и payload. Строковые ID в примерах —
подстановочные значения.

| Поле                     | Значение                                                          |
| ------------------------ | ----------------------------------------------------------------- |
| `formatVersion`          | `1`                                                               |
| `id`                     | Уникальный постоянный ID changeset                                |
| `projectId`, `replicaId` | Идентичность проекта и источника                                  |
| `actor`                  | Дословно проверенный автор локальной операции                     |
| `createdAt`              | Сохранённое время для истории/диагностики, не арбитраж            |
| `dependencies`           | Множество ID причинных предшественников без повторов              |
| `readContext`            | Прочитанные переносимые версии и проверяемые предметные предикаты |
| `effects`                | Упорядоченный список конкретных эффектов с постоянными ID         |
| `receiptId`              | ID явной batch receipt либо `null`                                |
| `digest`                 | SHA-256 канонического payload без самого `digest`                 |

Эффект MUST иметь `recordKind`, `recordId`, `action`, `before`, `after`
и `transition`. `action` различает создание, изменение и снятие. `before`/`after`
содержат переносимую версию и точное значение; `null` обозначает отсутствие стороны.
`transition` содержит предметный вид перехода и необходимый проверочный контекст.
Для больших текстов допустима ссылка по digest на атомарно сохранённый blob;
база трёхстороннего merge MUST оставаться доступной до подтверждения/разрешения.

**CS-01.** Changeset MUST описывать уже рассчитанные эффекты, включая неявные записи,
снятия, комментарии, адреса и квитанцию. Сохранения только имени команды и её аргументов
недостаточно. Повтор доставки MUST NOT выполнять пользовательскую команду заново.

**CS-02.** Предметные изменения, receipt, исходный changeset и запись outbox MUST
фиксироваться одной SQLite-транзакцией. После аварии присутствует весь набор либо
не присутствует ни одна его часть.

**CS-03.** Исходный payload и его digest MUST быть неизменяемыми. Подготовленный
результат merge, коллизии ключей и ручное решение хранятся отдельно с отсылкой
к исходному changeset. Новый non-fast-forward retry MUST сохранять исходные IDs.

**CS-04.** Причинные зависимости MUST учитывать создание используемых ID и прочитанные
непринятые версии/предикаты. MUST NOT добавляться зависимость от всех прежних пакетов
реплики только ради последовательности её локального счётчика. Независимая работа
должна продолжаться после конфликта другой причинной цепочки.

**CS-05.** Durable outbox MUST восстанавливаться без оперативной памяти worker.
Надёжность MUST NOT зависеть от файлового watcher, уведомления IPC или таймера CLI.

### Жизненный цикл

| Состояние         | Значение и разрешённый выход                                                                   |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| `pending`         | Сохранён локально; ждёт зависимостей либо выбора попыткой                                      |
| `prepared`        | Есть кандидат с remote HEAD, поколением и точным набором эффектов; может потребовать reprepare |
| `publishing`      | Выполняется push известного кандидата                                                          |
| `outcome-unknown` | Ответ потерян; перед повтором требуется проверка remote                                        |
| `conflicted`      | Сохранены материалы; весь changeset ожидает решения                                            |
| `acknowledged`    | Есть проверенное подтверждение в канонической истории                                          |

Ожидание зависимостей хранится как причина `pending`, а не как бесконечно выполняющийся
merge. Crash в `prepared`/`publishing` MUST восстанавливаться по checkpoint и remote,
не по предположению о завершении последнего процесса.

**CS-06.** Удаление подробного локального payload после ack допускается только при
наличии достаточного checkpoint/dedup и доступного основания для оставшихся
зависимых пакетов. Конфликтные, неподтверждённые и неопределённо опубликованные
эффекты MUST NOT удаляться как «старые» по одному возрасту.

**CS-07.** Каждый source с `modelVersion: 2`, включая `mode: "baseline"`, MUST сохранять
непустую ленту `transitions`. Обычные предметные изменения требуют именованных переходов.
Единственное техническое исключение — первоначальная материализация: одна boundary
`storage.atomic` для genesis (`mode: "mutation"`) либо `baseline` для миграции v1/v2
(`mode: "baseline"`). Обязательны `sequence: 1`, отсутствие dependencies/readContext,
predicates и именованных targets/timestamp, создание корня проекта и `before: null` всех
owners/parts. Её фактическая предыдущая canonical основа MUST быть полностью пустой,
включая адреса, комментарии, receipts, confirmations и publication. Coverage и parents
проверяются и в этом случае: создание имеет `parents: []` и согласованную содержательную
версию. Обычная model-2 Storage mutation без именованной ленты
MUST консервативно отклоняться, а не получать доверие от имени `storage.atomic`/`baseline`.
Legacy draft-v3 использует отдельную сохраняющую адаптацию; удаление modelVersion
при сохранённых model-2 parts/tape не превращает источник в legacy.

## 7. Переносимый snapshot и Git-формат

### Состав дерева

Общая ветка содержит текущий snapshot. Физическое отображение нормализованных
логических частей использует одно дерево для layout 1 и layout 2:

```text
manifest.json
entities/<entity-hash>/record.json
entities/<entity-hash>/<field>.md
components/<component-hash>/record.json
components/<component-hash>/<field>.md
comments/<comment-hash>/record.json
comments/<comment-hash>/body.md
receipts/<receipt-hash>.json
addresses.json
confirmations.json
publication.json
```

`manifest.json` MUST содержать `layoutVersion`, `formatVersion: 1`, `modelVersion: 2`
и `projectId`. Writer MUST выдавать layout 2; reader MUST явно различать layout 1
и layout 2, сохраняя прежние Core-проверки для обоих. Несовместимая версия или неверный
дескриптор не допускают fallback к другому layout. Layout описывает файлы и их wrappers,
model/format — переносимое предметное состояние и публикации. SQL schema version,
версия приложения и process protocol также независимы.

Логические части однозначно отображаются из
[`PortableProjectSnapshot`](packages/contracts/src/replication/replication.types.ts)
в следующие файлы. Формы wrappers и Markdown для каждой версии заданы в SNAP-02.

| Часть snapshot                                              | Физическое представление                                                                                             |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `formatVersion`, `modelVersion`, `projectId`                | `manifest.json` с дополнительным файловым `layoutVersion`                                                            |
| `entities[]` — raw owners без local CAS                     | По одному `PortableEntity` в `entities/<entity-hash>/record.json`                                                    |
| `components[]` — первичные scoped части, включая tombstones | По одному `PortableComponent` в `components/<component-hash>/record.json`                                            |
| `comments[]` — append-only журнал                           | По одному `PortableComment` в `comments/<comment-hash>/record.json`                                                  |
| `receipts[]` — первоначальные batch-квитанции               | По одному `{operationKey, requestJson, resultJson}` без wrapper в `receipts/<receipt-hash>.json`                     |
| `addresses[]` — карта `{ref, entityId}`                     | Массив в `addresses.json`, упорядоченный по `ref`                                                                    |
| `confirmations[]` — принятые sequence и точные proofs       | Массив в `confirmations.json`, упорядоченный по `replicaId`                                                          |
| `publication` — последняя публикация                        | Сам объект в `publication.json`; локальный capture может содержать `null`, который не является удалённой публикацией |

Идентичность и версии назначений адресов сохраняются в scoped компонентах вида
`address-assignment`; карта `addresses` не заменяет эти записи. Вынесенный Markdown
принадлежит соседнему `record.json`, а не отдельному глобальному каталогу текстов.
Тексты внутри immutable `requestJson`/`resultJson` и source/effective tape остаются
частью исходного payload: файловое разбиение не переписывает их. Это размещение MUST
сохранять требования идентичности, версий, атомарности и переходов; неизвестные пути
не могут скрывать дополнительные данные.

`<entity-hash>` и `<comment-hash>` — lowercase hex SHA-256 UTF-8 соответствующего ID,
`<receipt-hash>` — такой же хеш operationKey. Для `<component-hash>` хешируется UTF-8
`JSON.stringify([ownerId, kind, id])` без Unicode-нормализации и завершающего LF.
Логическая идентичность MUST присутствовать в записи и сверяться с её путём при импорте. Имена файлов
не зависят от ключа сущности и безопасны для регистронезависимых файловых систем,
зарезервированных имён Windows и пользовательского Unicode. Виды и имена полей
берутся из закрытой схемы. Две записи, заявляющие один путь с разными ID, неизвестные
пути и лишние поля wrappers отвергаются до применения состояния.

**SNAP-01.** Snapshot MUST строиться из сохранённых предметных данных одного снимка.
Экспорт MUST NOT использовать пользовательскую проекцию `get`, `summary`, вычисляемый
прогресс или отображение актуальных ключей вместо исторически сохранённых.

**SNAP-02.** Запись MUST включать ID, вид, переносимую версию, предметные поля,
сохранённое авторство и времена, необходимые связи/снятия. Layout 2 имеет закрытые wrappers:
`{entity, markdown}`, `{component, markdown}` и `{comment: PortableComment, markdown}`.
Внутри PortableComment сохраняется структура `{taskId, after, comment: {...}}`.
Поле `markdown` обязательно, включая пустой массив; его элементы — строго
`{field, digest}`. `digest` — lowercase hex SHA-256 точных UTF-8 байтов соседнего
`<field>.md`, включая BOM/CRLF, пустой текст и отсутствие завершающего LF.

У entity/component выносятся строковые поля `body`, `description`, `summary`
в этом порядке, у comment — только `body`. Их исходные положения в wrapper —
`entity.record.data[field]`, `component.value[field]` и `comment.comment.body`.
Well-formed UTF-16, включая пустую строку,
MUST выноситься в raw UTF-8 blob с проверяемым дескриптором. Остальные поля остаются
в JSON. Digest проверяется до предметного применения, UTF-8 декодируется строго.
Дубли дескрипторов, extra/missing поля, отсутствующий blob и неверный digest отклоняются.
Одновременное inline/blob представление одного поля запрещено.

Layout 1 читается отдельной legacy-веткой: entity/component имеют `markdown: string[]`,
comment хранится как PortableComment без нового wrapper, отсутствие `comment.body`
означает соседний `body.md`. Обязательные прежние проверки версий и публикаций Core
сохраняются; отсутствие нового дескриптора не даёт дополнительного доверия старому дереву.

Строка с непарными surrogate MUST оставаться в исходном inline JSON-поле с экранированием
UTF-16 code units: UTF-8 `.md` не обеспечивает для неё точного round-trip. Дескриптора
для этого поля нет; форму однозначно задают `layoutVersion` и закрытая схема wrapper.
Импорт MUST восстанавливать исходные code units без нормализации, удаления или замены
символов. Разбиение MUST быть обратимым: сохраняются пустые значения, переводы строк,
пробелы и отсутствие финального LF. Git line-ending conversion MUST NOT менять байты.

**SNAP-03.** JSON MUST сериализоваться детерминированно: фиксированный алгоритм
упорядочения ключей объектов, сохранение порядка значимых массивов, отсутствие
зависимости от locale, платформы и порядка SQL-выборки. Наборы канонизируются по ID.
Ключи объектов рекурсивно сортируются лексикографически по UTF-16 code units.
JSON-файлы writer layout 2 кодируются в UTF-8 с двухпробельным отступом и одним
завершающим LF. Legacy layout 1 сохраняет собственный файловый формат при чтении.
Numeric-like ключи не должны пересортировываться по числовому значению после
лексикографической сортировки. Duplicate JSON keys, включая escape aliases,
отклоняются, а не выбираются по последнему вхождению.
Строки не нормализуются по Unicode. Непарные surrogate в JSON MUST экранироваться
как `\uXXXX`, сохраняя исходные UTF-16 code units; NaN, Infinity и не-JSON значения
не допускаются. Snapshot round-trip сравнивает точные предметные данные, а не только
успешный `doctor`.

Канонические model/format fingerprints MUST оставаться независимыми от pretty JSON
файлов: Core/Storage вычисляют SHA-256 компактного канонического JSON в UTF-8,
без отступов и завершающего LF. Состав хешируемого значения задаёт предметный владелец:
версия primary record исключает local CAS/comments и включает parents;
aggregate token связывает primary version с отсортированными scoped версиями частей.
Форматирование Git-файлов и переход layout 1→2 MUST NOT менять эти формулы,
переносимые версии, исходный immutable source либо его прежний digest.
Исключения self-hash publication и состав proofs также остаются контрактом Core,
а не выводятся из физических байтов `publication.json`.
Reader MUST проверять смешанную историю layout 1→2; idle не переписывает старые
коммиты ради смены оформления. Layout 2 появляется с новой предметной публикацией,
сохраняя прежние Git bytes и неизменяемые source IDs/digests.

**SNAP-04.** SQLite/WAL, индексы, физические пути, workspace-регистрации, credentials,
PID, process leases, локальные CAS-счётчики и расписание retry MUST NOT попадать
в переносимое дерево. Метаданные исходной квитанции и исторические снимки остаются
предметными данными, даже если содержат старую ревизию или ключ.

### Публикация и проверка переходов

`publication.json` описывает только данную публикацию: версию формата, уникальный
`publicationId`, `parent: null | {publicationId, snapshotDigest}`, digest результата,
точный набор принятых changeset и необходимые контексты переходов. Транспорт MUST
сопоставить эту родительскую публикацию с непосредственным Git parent HEAD;
логическая ссылка не заменяет проверку Git-истории. Материал MUST позволять Core проверить изменение родительского
snapshot в новый без повторного пользовательского запроса. Большие неизменённые
значения могут адресоваться по родительскому Git-объекту и digest.

**SNAP-05.** Контекст публикации MUST NOT ограничиваться заявлением «snapshot валиден».
Для обычного импорта проверяются неизменяемость и допустимые переходы от принятого
предка. Если checkpoint не позволяет пропустить историю безопасно, worker MUST
прочитать необходимые коммиты/контексты. Отсутствие требуемого base не означает
разрешение произвольной замены.

**SNAP-06.** Текущее дерево MUST NOT требовать каталога полных пользовательских команд
за всю жизнь проекта. Контекст последней публикации может заменяться следующим;
исторические коммиты остаются доступны для проверяемого replay. Восстановление из
проверенного checkpoint не обязано повторять всю историю с genesis.

**SNAP-07.** Публичный `validateReplicationHistory(base, target, {chain})` возвращает
Core-owned `ValidatedReplicationHistory` с транзитивно неизменяемым `proof.snapshot`.
`prepare(proof.snapshot, proof)` и `accept(proof.snapshot, proof)` MUST переиспользовать
только действительно выданную Core capability, привязанную к точной цели и полному
содержимому фактической принятой основы либо проверенного предка.
Самостоятельный constructor, структурная/JSON-копия token, другая цель и непроверенный
prefix перед объявленной base MUST NOT давать доверие. Обычный путь без capability
проходит те же предметные проверки. Capability не является переносимым Git proof
или ack; приложение отдельно доказывает непосредственного Git parent и принятие
веткой. Локальный guard, source digests/proofs и текущий pending overlay проверяются
заново при применении.

### Подтверждения и квитанции

Ack v1 физически представлен элементами `confirmations[]`: `replicaId`, точными
интервалами `ranges` и `proofs` для принятых sequence. Proof связывает `sequence`,
`digest` исходного source, `publicationId`, `resolutionId` (`null` без ручного решения),
`effectDigest` и `outcome`. ID changeset восстанавливается как `replicaId:sequence`;
`formatVersion` задаётся snapshot. Поля `changesetId`/`sourceDigest`/`resolutionId`/
`effectDigest` также входят в `publication.accepted[]` соответствующей публикации.
Эти части MUST сохранять точную связь источника с принятым результатом. Git SHA
содержащего коммита определяется снаружи: self-reference на SHA собственного коммита запрещена.

**ACK-01.** Ack признаётся только из проверенной канонической истории правильного
проекта, содержащей соответствующую публикацию. Локальный коммит, stdout Git
и похожее итоговое состояние MUST NOT сами заменять проверку принятия changeset.

**ACK-02.** Одинаковый `changesetId` с другим `sourceDigest` MUST отклоняться.
Подтверждения могут компактироваться только с сохранением точного ответа о принятии
ID и недопущением повторного применения. Максимальный номер или диапазон с забытыми
«дырами» не является корректным dedup. V1 допускает отдельную компактную запись
на changeset без обещания постоянного размера метаданных.

**ACK-03.** Batch receipt MUST сохранять исходный нормализованный запрос с автором
и первоначальный результат. Она MUST NOT заменяться transport ack, текущими сущностями
или результатом повторного исполнения. Квитанция адресуется своим `operationKey`,
отдельно от ID changeset. Operation key сохраняет область уникальности проекта и отсутствие TTL.

**ACK-04.** Совпадающие запрос/автор под известным operation key возвращают исходную
квитанцию до новых CAS/адресных проверок. Иной запрос или автор вызывает конфликт.
Порядок JSON-свойств незначим; порядок массивов, строки, исходные адреса, наличие полей
и порядок команд значимы согласно действующему batch-контракту.
Выбор `--return`, text/JSON и признак ответа `replayed` не переписывают сохранённую
квитанцию; переименование ключа сущности также не меняет её исторический результат.

**ACK-05.** Независимо созданные offline несовместимые квитанции под одним operation key
MUST конфликтовать как часть целого changeset. Даже одинаковый запрос не позволяет
заменить отличающийся первоначальный результат. Импорт/resolve MUST NOT переписывать
уже выданную квитанцию; материалы конфликта сохраняют обе. Автоматическое глобальное
exactly-once исполнение до обмена с origin не обещается. Решение, нарушающее эту
неизменяемость, MUST быть отклонено с объяснением причины.

**ACK-06.** Pruning текущего дерева MUST NOT объявляться удалением Git-истории.
Обычная синхронизация MUST NOT переписывать опубликованные коммиты ради освобождения
места. Текущие данные, квитанции и доказательства дедупликации могут расти независимо
от отсутствия полного журнала каждой команды.

## 8. Цикл синхронизации и конкурентность

**SYNC-01.** Все реплики MUST использовать одну настроенную каноническую ветку базы.
Ветки участников и отдельный интегратор MUST NOT быть необходимыми для протокола.
Рабочий Git-каталог данных отделяется от пользовательского рабочего дерева кода.

Одна попытка MUST выполнять следующие действия:

1. Захватить единственное локальное владение попыткой данной БД.
2. Fetch remote HEAD вне SQLite-транзакции; проверить проект, формат и историю.
3. Проверить неизвестные исходы прежних push и новые acknowledgements.
4. Снять согласованный локальный контекст: поколение, outbox, base и ожидаемые версии.
5. Выбрать ограниченный набор changeset с выполненными dependencies в топологическом порядке.
6. Выполнить предметный merge, затем согласование предварительных ключей.
7. Проверить кандидат через Core, включая переходы и предикаты.
8. Сохранить checkpoint подготовки с guard поколения и точным набором ID.
9. Создать коммит непосредственно поверх полученного HEAD с snapshot и acknowledgements.
10. Выполнить обычный fast-forward push без force.
11. Установить фактический исход; зафиксировать ack ровно принятых ID и локальное
    применение с guards, либо сохранить неизвестный исход/причину отказа.

**SYNC-02.** Пока зависимости changeset не приняты или не входят в тот же кандидат
раньше него, пакет MUST ждать. Конфликт одного пакета MUST NOT останавливать
независимые пакеты этого проекта и другие проекты. Размер выборки MUST быть ограничен;
очередь MUST обеспечивать продвижение независимой работы, а не всегда выбирать
один конфликтный префикс.

**SYNC-03.** Non-fast-forward MUST приводить к fetch/reprepare с теми же исходными
IDs. Слепой Git merge/rebase текстовых файлов не заменяет предметное согласование.
Force push опубликованной истории запрещён.

**SYNC-04.** При потере ответа push worker MUST перейти в `outcome-unknown`,
проверить реальную ветку/ack и только затем решать о повторе. Продвижение HEAD после
успешного push не отменяет ack, находящийся в принятой истории.

**SYNC-05.** Подготовка MUST иметь guard локального поколения и версии источников.
Если во время сети/merge добавлены локальные изменения, установка устаревшего
snapshot MUST быть отклонена. Уже опубликованный пакет можно подтвердить по ID,
но позднейшие пакеты MUST оставаться pending и участвовать в новой подготовке.
Поколение «всё до текущего отправлено» без точного соответствия пакетам запрещено.

**SYNC-06.** Импорт MUST изменять строки рабочей БД, сохраняя локальный остаток,
а не пересоздавать её при каждом fetch. Принятые входящие эффекты MUST NOT создавать
новые исходящие копии тех же changeset и бесконечный echo.

**SYNC-07.** Обнаруженное переписывание/несвязанная подмена канонической истории
MUST давать явное состояние несовместимости. Worker MUST NOT автоматически
объявлять чужой HEAD новым base и терять старые подтверждения/резервы.

**SYNC-08.** Одна попытка MUST переиспользовать проверенный Git-контекст. Обычные
предметные команды и `git-sync status` MUST NOT запускать повторные `rev-parse`,
`worktree list`, `remote get-url`, fetch или push для получения статуса.

**SYNC-09.** `prepare(remote, history, options)` MUST ограничивать выборку source
JSON до декодирования/хеширования. `options.afterSequence` задаёт курсор (по умолчанию 0),
`budget.maxChangesets` и `budget.maxBytes` — уменьшаемые бюджеты с default/верхними
пределами 64 changeset и 8 MiB сохранённого UTF-8 JSON источников.
Один source больше байтового бюджета MUST переноситься один и целиком с `oversized: true`;
деление atomic effects/receipts или выдача новых IDs/digests ради лимита запрещены.

`selection` MUST содержать исходный/следующий курсор, `hasMore`, точные `examined`,
`deferred`/`waiting`, полный pending count того же снимка, `sourceBytes` и `oversized`.
Ожидание dependencies — pending, не конфликт и не ack. `prepared.conflicts` относится
к examined-окну; материалы остальных окон не удаляются. Полный журнал конфликтов
доступен через `conflicts()`, причины ожидающих цепочек — отдельным `blocked()`.

Транспорт MUST сохранять курсор durable, продвигать его после установленного исхода
либо завершённого окна без included и повторять исходный курсор при non-FF/неизвестном
push-исходе до его проверки. Конец обхода возвращает cursor 0, но не означает пустой
outbox. Итоговый pending после accept берётся из текущего status; бесконечные круги
по непреодолимому конфликту запрещены.

Budget относится к рассматриваемым source JSON, не к полному snapshot/effective tape.
Canonical capture, history, count и проверка предъявленных proofs имеют собственную
стоимость. `accept` использует полный актуальный остаток; выбранное ручное решение
требует полного witness. `resolve(..., {budget?})` проверяет решение на полном overlay
и возвращает preview первого ограниченного окна без пользовательского cursor.
`blocked()` сканирует полный dependency-граф и MUST NOT подменять дешёвые status/prepare
счётчики. Полный локальный guard не заменяется одним generation.

**SYNC-10.** Один `SyncEngine.run()`/`now` MUST завершать одно bounded окно;
non-FF допускает конечные повторы того же исходного cursor. Durable progress связывает
`afterSequence` одновременно с `replicaId` и физическим путём БД. Старый progress
без cursor начинается с 0; смена области сбрасывает прежнюю наблюдаемость.
Окно с `included=[]` продвигает cursor без фиктивных genesis/commit/ACK.
Неизвестный push-исход не продвигает его до фактического acceptance.
После успешного auto-окна с hasMore следующая попытка назначается через 500 мс;
после конца обхода действует обычный polling 5 с. Это интервалы планировщика,
не обещание задержки доставки или пропускной способности.

## 9. Merge, переходы и конфликт

**MERGE-01.** Merge MUST сравнивать `base`, локальный эффект и remote. Для скаляра:

- `local == base` — сохранить remote;
- `remote == base` — применить local;
- `local == remote` — сохранить одно значение;
- иначе — конфликт.

Равенство сравнивает каноническое предметное значение, не `updatedAt` и не локальную
ревизию. Разные сущности и независимые поля объединяются только после проверки
межзаписных правил.

**MERGE-02.** Append-only комментарии с разными ID MUST сохраняться вместе.
Повтор того же ID с тем же содержанием дедуплицируется; с другим содержанием
отклоняется. Старый snapshot задачи MUST NOT удалять поздний комментарий.

**MERGE-03.** Markdown MUST объединяться относительно общего точного base.
Автоматическое объединение разрешено для непересекающихся изменений; пересечение,
неоднозначный порядок вставки в одну позицию и несовместимое удаление/изменение
дают конфликт. Неправленные участки, Unicode и переводы строк сохраняются.
Маркеры Git-конфликта MUST NOT записываться в пользовательское содержание как успех.

**MERGE-04.** ID-наборы MUST учитывать добавления и снятия относительно base.
Обычный union массивов запрещён. Снятие существующего включения не теряется
из-за другой ветви с устаревшим массивом; конкурентное редактирование снимаемого
элемента требует предметного решения. Повторное включение с новым ID не выдаётся
за восстановление снятого старого элемента.

**MERGE-05.** Порядок MUST проверяться отдельно от состава. Независимые вставки
сохраняются; конфликтующие перемещения одного ID, потеря элемента и цикл порядка
не маскируются сортировкой по времени.

**MERGE-06.** Core MUST проверять не только JSON и структурный `doctor`, но и
допустимость переходов, неизменяемость и агрегатные правила. Обязательные случаи:
`done` при новом невыполненном критерии/зависимости, transfer обеих сторон,
session/run ownership, изменение immutable checkpoint, смена автора комментария,
повторное использование зарезервированного адреса.

**MERGE-07.** Changeset MUST приниматься целиком либо оставаться целиком конфликтным.
Не затронутые конфликтом эффекты этого же changeset MUST NOT публиковаться отдельно.

### Формат конфликта и разрешения

Конфликт v1 MUST содержать:

- `id`, `projectId`, `changesetId`, версию формата и стабильный код причины;
- затронутые ID, поля/переходы и полный material `base`, `local`, `remote`;
- remote HEAD, локальное поколение и релевантные переносимые версии;
- `fingerprint` просмотренного набора версий, значений, адресов и зависимостей;
- состояние конфликта и связь с решением, если оно появилось.

Запрос разрешения v1 содержит `conflictId`, `fingerprint`, автора и решение
`local`, `remote` либо `custom` с конкретными эффектами. Разрешение задаётся для
целого changeset; неполный выбор его эффектов не считается завершением.

**CON-01.** `conflicts get` MUST возвращать достаточные данные для решения без
потери длинных текстов. Краткий список может опускать payload, но не подменять его.

**CON-02.** Перед записью resolve MUST атомарно проверить fingerprint и актуальные
guards. Новая локальная запись либо новый remote, меняющие основание решения,
требуют нового просмотра. Устаревшее решение MUST быть отклонено без изменений.

**CON-03.** Решение MUST сохраняться отдельной неизменяемой записью с новым ID.
Исходный changeset и receipt остаются прежними. Проверенный итог и acknowledgement
связываются с исходным пакетом и этим решением.

**CON-04.** Принятие remote вместо исходного локального эффекта MUST NOT автоматически
удовлетворять все dependencies. Зависимые пакеты повторно проверяют существование
и версии ожидаемых ID; при исчезнувшем основании остаются блокированными/конфликтными.

**CON-05.** Режимы `local`/`custom` MUST NOT обходить неизменяемость, авторство,
запрет недопустимого перехода или резервы ключей. Ошибка resolve сохраняет прежние
материалы и не объявляет конфликт закрытым.

**CON-06.** Custom v1 MUST иметь закрытую форму решения:

```text
{ fingerprint, choice: "custom", patch: [{ transition, entityId, field, value }] }
```

`patch` непуст; `transition` — неотрицательный индекс исходной command boundary
в `changeset.transitions` (0 для legacy atomic source), `entityId` — ID существующего
документа, `field` — только `name`, `summary` или `body`, `value` — строка.
Выбранное поле MUST действительно изменяться в выбранной исходной boundary.
Повторы одной тройки transition/entityId/field, произвольные JSON paths, незатронутые
поля, записи вне исходной boundary, компоненты, история, адреса и receipts запрещены.
Остальной changeset проходит обычное согласование и shared validators целиком.
Автор и время ручной поправки принадлежат неизменяемому решению; исходные source,
digest, ID и первоначальная receipt MUST оставаться прежними.

**CON-07.** Публикация MUST связывать исходные source digests, эффективные упорядоченные
переходы, immutable resolution и принятый результат. Если origin уже принял более
раннее решение, позднее предложение MUST оставаться явным
`REPLICATION_RESOLUTION_STALE` с `pendingResolution` и `acceptedResolutionId`.
Явный `remote` принимает опубликованный результат. `local`/`custom` не переписывают
уже принятый changeset (`REPLICATION_ALREADY_ACCEPTED`); дальнейшее изменение
выполняется новой предметной командой.

**CON-08.** Публичный `conflicts.list` MUST возвращать оба массива `{conflicts, blocked}`.
Первый содержит краткие реальные конфликты `{id, fingerprint, code, message}`;
второй — `{id, state: "pending", code: "REPLICATION_DEPENDENCY", message, dependencies}`.
`conflicts.get <id>` возвращает полные стороны реального конфликта либо blocked-объект
без fingerprint/сторон; неизвестный ID даёт `GIT_SYNC_CONFLICT_NOT_FOUND`, exit 3.
Resolve blocked ID MUST возвращать `REPLICATION_DEPENDENCY`, exit 4, с `details.blocked`
без мутации и сохранения решения.

Успешный resolve MUST возвращать `{id, generation, included, conflicts, blocked,
pending, deferred, hasMore}`. Conflicts/blocked — полные оставшиеся диагностические
списки, pending — фактический полный outbox; included/deferred/hasMore относятся
только к bounded preview. Успех не является Git ACK. Полная диагностика blocked
не переносится в горячий status/prepare ради счётчиков.

## 10. Ключи и устойчивые ссылки

**KEY-01.** Назначение ключа MUST быть самостоятельной записью с ID, `entityId`,
ключом, переносимой версией и состоянием. Предварительная заявка и подтверждённое
назначение MUST различаться. Удалённое окончательное назначение сохраняет резерв.

**KEY-02.** Первое назначение, принятое канонической веткой origin, MUST оставаться
у первоначального ID. Проигравшая предварительная заявка получает следующий свободный
ключ по правилам пространства проекта. Если новый HEAD занял и его, алгоритм
пересчитывает назначение; сущность и структурированные ссылки сохраняют ID.

**KEY-03.** Обычный rename/alias и collision renumber MUST быть разными переходами.
При коллизии старый ключ MUST NOT добавляться проигравшей сущности как алиас,
поскольку он принадлежит победителю. Подтверждённый адрес/резерв MUST NOT выдаваться
другой сущности при обычном обмене.

**KEY-04.** Мутация по читаемому адресу MUST проверять переданную ожидаемую привязку
`expectedAddresses: [{ref, expectedId}]`. Guard MUST проверяться в той же границе,
что разрешение адреса и commit. Автоматическое разрешение ключа в текущий ID
при новом вызове MUST NOT считаться доказательством просмотренной клиентом привязки.
После локально известного переназначения предварительного ключа запись по этому
адресу без клиентского `expectedId` просмотренной привязки
MUST отклоняться; вызывающий может использовать постоянный ID. Сведения о таком
переназначении MUST сохраняться после повторного открытия БД. Система MUST NOT
различать «свежий интерактивный ввод» и «старый редактор» без проверяемого guard
или незаметно перенаправлять запись на нового владельца такого же ключа.

**KEY-05.** Все структурированные связи MUST хранить ID. Формат устойчивой
Markdown-ссылки v1 — `relay://<projectId>/<entityId>` с percent-encoding сегментов
по UTF-8. Разбор обязан проверить схему, число сегментов и канонические ID.
Ссылка другого проекта сохраняет явный `projectId`; она не становится локальной
предметной зависимостью автоматически.

**KEY-06.** Обычное текстовое упоминание `DOC-13` MUST оставаться обычным текстом.
Вставка устойчивой ссылки по ключу MUST использовать Markdown AST и проверенную
адресную карту. Regexp-replace произвольного текста, кода, экранированных фрагментов
и исторических снимков запрещён. Метка ссылки может остаться историческим текстом;
актуальное отображение ключа не меняет сохранённую цель.

## 11. Connect, restore и восстановление после crash

**RECOVERY-01.** `connect` MUST проверить идентичность проекта, выбранную ветку,
совместимость формата и историю до установки подключения. Первое подключение выполняет
fetch/validation без push и без применения remote-снимка к SQLite. Публикация локального
baseline либо согласование существующей ветки с pending выполняются последующим `now`.
Другой `projectId` MUST дать отказ без изменения данных. Отсутствие ветки данных
не разрешает менять default branch Git-хостинга или создавать коммит кода.

**RECOVERY-02.** Первый snapshot существующей локальной БД MUST включать все сохранённые
данные, адреса, comments и receipts. Миграция из schema v2 MUST создать проверяемый
baseline и переносимые версии, сохранив исходные IDs, предметные значения,
исторические ревизии и локальную CAS-семантику. Нельзя выдать отсутствие исторического
outbox за отсутствие данных для первого экспорта.

**RECOVERY-03.** Обычный `restore` из Git MUST принимать определённый источник/коммит, проверять
проект и строить подготовительную БД. До проверки Core, индексов, адресов, версий
и квитанций она не подключается как рабочая. Публикация готовой БД/привязки должна
быть восстановима после аварии. Отсутствующая БД MUST NOT автоматически заменяться
пустой при обычной команде.
Явный `--remote` не требует предыдущего `connect`: имя remote разрешается относительно
кодового cwd, URL/путь используется без кодового checkout. Новая реплика получает
проверенные БД, конфиг и подключение; существующая рабочая БД не перезаписывается.

**RECOVERY-04.** Restore поверх существующей БД с pending MUST NOT молча удалять
локальный остаток. Требуется сохранённая восстанавливаемая копия и явный контракт
переноса pending в подготовительную БД с проверкой Core. Исходная рабочая БД
остаётся доступной при отказе подготовки.

**RECOVERY-05.** Checkpoint MUST фиксировать проверенный канонический HEAD,
принятые changeset/dedup, переносимые версии и точную границу локального остатка.
Replay MUST применять сохранённые эффекты и проверенные переходы, а не запускать
пользовательские команды повторно. Ack импортированных изменений не превращается
в новую исходящую пользовательскую операцию.

**RECOVERY-06.** Восстановление из Git гарантирует только данные, содержащиеся
в доступном Git-снимке/истории. Для SQLite-only изменений необходима согласованная
резервная копия вместе с outbox. Статус MUST различать unexported и unpublished.

### Явное продолжение локальной публикации

**RECOVERY-07.** После сохранения намерения публикации ошибка либо неопределённый
исход MUST сохранять рабочую БД, staging и intent, включая поздние commits/outbox.
Обычный повтор при pending intent MUST возвращать `RESTORE_RECOVERY_REQUIRED`
до materializer. Совпадение inode, отсутствие WAL/SHM или прежнее содержимое файла
MUST NOT разрешать удаление опубликованной БД и повторный bootstrap.

**RECOVERY-08.** `resumeProjectRestoration(options, projectId, validateDatabase)` MUST
явно завершать привязку сохранённого локального состояния без нового snapshot.
Постоянный ID берётся из выбранного существующего конфига либо отдельного аргумента
`projectId`; без обоих — `RESTORE_PROJECT_ID_REQUIRED`, exit 2. `options.project`
остаётся именем регистрации workspace. Сканирование home для угадывания проекта запрещено.
Новая реплика не создаётся: предметные данные, `replicaId`, outbox и поздние commits
MUST сохраняться. Этот режим не заменяет правила переноса pending из RECOVERY-04.

**RECOVERY-09.** До validator Runtime MUST проверить локальное намерение, физическое
владение, schema/applicationId/projectId и соответствие выбранному config/path.
Validator MUST быть строго синхронным read-only вызовом Core, возвращать `undefined`
и закрывать все свои соединения. Bootstrap, материализация, мутации и отложенные
writers внутри validator запрещены; async/Promise и иной результат отклоняются.

Существующая принадлежащая публикации БД MUST проверяться по публичному пути,
включая её живой WAL; открытие staging под вторым именем не заменяет эту проверку.
Если публичный target отсутствует, новый exclusive link допускается только при
единственном staging-hardlink, отсутствии журналов под обоими именами и закрытых
соединениях validator. Неизвестные алиасы, чужой target/config, скопированный либо
повреждённый marker и сомнительная идентичность MUST приводить к сохраняющему отказу.
Подмена target после публикации конфига также является ошибкой, а не cleanup warning.

**RECOVERY-10.** Ветка resume в приложении MUST выполняться до `savedConnection`,
fetch, импорта Git-объектов, `accepted`/ack и записи progress обычного restore.
Она MUST NOT требовать supervisor, заменять сохранённую БД новым remote snapshot
или объявлять текущий fetched HEAD её источником. Последующие `connect`/`now`
выполняются отдельно по явному запросу пользователя.

Результат Runtime имеет форму:

```text
{
  location,
  resumed: true,
  preservedExisting: true,
  sourceCheckpoint: null,
  recovery: null | { publicationPath, stagingPath, failure: { code, message } }
}
```

`sourceCheckpoint` MUST оставаться `null`: Runtime не знает Git HEAD. Успех означает
привязку фактически сохранённого локального проекта, а не новую материализацию,
Git-checkpoint из RECOVERY-05 или подтверждение remote. Ошибки private cleanup
сохраняются в `recovery.failure` вместе с путями; неизвестные companion-файлы
не удаляются. Утрата владения публичной БД MUST оставаться ошибкой, не превращаясь
в успешную привязку с предупреждением.

**RECOVERY-11.** После полной cleanup отсутствие intent MUST давать
`RESTORE_NOT_PENDING`, exit 3, без validator и записи. При целых сохранённых
recovery-материалах повторная проверка и привязка допустимы. Совпадающий config
сохраняется дословно, отсутствующий публикуется эксклюзивно; публичный datafile
не удаляется cleanup-сценарием.

**RECOVERY-12.** Новые локальные намерения публикации MUST иметь версию 2 с полной
физической идентичностью БД и проверяемой связью маркеров. Версия MUST исключать
применение прежнего rollback reader v1 к новой публикации. Новый resume MUST
отвергать ранний intent v1 с сохранением материалов, без автоматической миграции
или догадок о владении. Номер intent независим от SQL-схемы и переносимого Git-формата.

### Обязательные границы отказа

| Момент аварии                             | Требуемое восстановление                                             |
| ----------------------------------------- | -------------------------------------------------------------------- |
| До SQLite commit пользовательской команды | Нет ни предметных эффектов, ни receipt/outbox                        |
| После SQLite commit до уведомления worker | Outbox обнаруживается после запуска без повторной команды            |
| После подготовки до Git commit            | Guard/HEAD перепроверяются, исходные IDs сохраняются                 |
| После Git commit до push                  | Локальный checkpoint не объявляется origin ack                       |
| Во время push, ответ неизвестен           | Проверка реальной ветки и ack перед повтором                         |
| После принятия push до локального ack     | Дедупликация по принятому ID/digest                                  |
| После push при новой локальной записи     | Подтверждается только опубликованный набор, новые данные сохраняются |
| Во время импорта SQLite                   | Весь локальный commit либо rollback, затем безопасный replay         |
| Во время restore до переключения          | Исходная БД/состояние восстановления остаётся определённым           |
| После смерти worker/supervisor            | Освобождение владения и уборка по IPC-04/05 до нового экземпляра     |

## 12. Workers, supervisor и process protocol

### Владение и планирование

**PROC-01.** Должен существовать не более чем один активный worker на физическую
локальную БД. Дедупликация MUST учитывать физический путь/идентичность файла
и `replicaId`, а не имя регистрации workspace. Две независимые БД одного проекта
не объединяются в один worker.

**PROC-02.** Постоянный worker MUST оставаться способен получать remote-изменения
при пустом outbox и продолжать независимые цепочки при конфликте. Обычное завершение
одноразового CLI-request не останавливает отдельно запущенные supervisor/workers.
`stop` MUST менять desired state, чтобы supervisor
не запускал процесс немедленно вопреки команде.

**PROC-03.** Host supervisor MUST восстанавливать процессы с desired `running`
и соблюдать общий ограниченный бюджет CPU/network/Git-процессов. У каждого проекта
свои backoff и ошибка; медленный проект не должен занимать весь бюджет бесконечно.
Планирование MUST иметь конечные deadlines, fairness и jitter повторов.

**PROC-04.** Polling MUST иметь нижнюю границу интервала и ограничение конкурентности;
ошибка не создаёт tight loop. Debounce экспорта MUST иметь верхнюю границу ожидания
и не зависеть от сетевого backoff. Значения настраиваются в одном владельце;
2s/15s из легаси не считаются автоматически подходящими новыми defaults или SLA.

**PROC-05.** Однотипные wake-up/`now` запросы допускается объединять, сохраняя
идентичность и исход каждого принятого запроса. Непереданное уведомление не теряет
durable работу. `nextAttempt` публикуется только после реального назначения
попытки живым планировщиком и сбрасывается при прекращении владения.

**PROC-06.** Только долгоживущий supervisor MUST владеть постоянными workers.
Supervisor запускается native manager через явный `service enable` для выбранного
`RELAY_HOME` либо живым foreground-вызовом `relay git-sync supervise`.
Короткий CLI-request, включая `--request`, MUST NOT создавать постоянные демоны,
передавать им владение своим lifetime-контейнером или обходить Job/process-group
cleanup ради их выживания после ответа. Запросы старта передаются уже готовому
совместимому supervisor; он создаёт worker в своей границе владения.

Native supervisor MUST следовать login-семантике пользовательского manager;
foreground supervisor MUST оставаться связанным с жизнью запустившей CLI и parent lease.
Обычный request не является родителем lifetime постоянного supervisor/worker.
Сохранённый desired `stopped` MUST учитываться при восстановлении supervisor.

### Одноразовый протокол CLI → binary

**IPC-REQUEST.** CLI MUST передавать бинарнику через `--request` одноразовый запрос
с точной оболочкой `GitSyncRequest`; ответ MUST иметь одну из двух указанных форм.
В записи ниже `?` обозначает необязательное поле:

```text
GitSyncRequest:
{ version: 1, action, options: { cwd, config?, home?, project? }, input? }

GitSyncResponse:
{ version: 1, ok: true, data }
| { version: 1, ok: false, error: { code, message, exitCode, details? } }
```

`cwd` обязателен; `cwd`, `config`, `home` и `project` — строки.
Каталог `action` и формы `input`/`data` принадлежат Contracts. `error` содержит
строковые `code`/`message`, числовой `exitCode` и необязательные структурированные
`details`. Этот launcher-запрос MUST NOT требовать `requestId`, идентичность
выбранной БД или worker, `expectedInstanceId` и readiness до выбора/создания worker.
Сведения о процессе, предусмотренные результатом конкретного действия, передаются
в `data` без изменения общей оболочки.

**IPC-VERSION.** `relay-git-sync --version` MUST автономно выводить package version
бинарника для проверки совместимости. Эта команда MUST работать без проекта,
базы, `--request` и запуска worker. Package version не заменяет версию оболочки
одноразового запроса или версию worker-control протокола.

### Управление постоянным worker

Долгоживущий worker-control протокол MUST передавать `protocolVersion`, `requestId`,
действие, идентичность выбранной БД и `expectedInstanceId` при обращении к конкретному
экземпляру. Ответ MUST содержать тот же `requestId`, `actualInstanceId`, readiness,
`binaryVersion`, `protocolVersion`, совместимость форматов и структурированный
результат/ошибку. `actualInstanceId` обозначает текущий `instanceId` worker;
неизвестный до discovery экземпляр нельзя подменять предполагаемым PID.

**IPC-01.** Contracts MUST владеть схемами обоих протоколов. Runtime MUST владеть
launcher, разрешением путей, проверкой совместимого бинарника и native registration
служб systemd/launchd/Task Scheduler как частью local launcher/lifecycle,
без Git-транспорта. Git Sync MUST владеть обработкой своих действий, самим процессом
`supervise`, workers и Git. Код CLI и Git Sync не связывается прямым импортом приложения.

**IPC-02.** Успешный start MUST ждать readiness: контекст БД проверен, формат
поддерживается, исключительное владение получено и канал управления отвечает.
Событие spawn и существование PID-файла недостаточны. Deadline старта сохраняет
диагностируемую причину раннего отказа.

**IPC-03.** Проверка отзывчивости MUST относиться к живому `instanceId`. Повторное
использование PID другим процессом не даёт права отправить ему stop/kill.
Несовместимая версия процесса не объявляется готовой; restart заменяет владельца
с проверкой освобождения ресурсов и подтверждением нового readiness.

**IPC-04.** Управление созданными Git/SSH/helpers MUST обеспечивать ограниченную
по времени остановку в явно определённой native-границе:

- Linux — subreaper (`PR_SET_CHILD_SUBREAPER`), собственная process group и уборка
  принадлежащих запуску осиротевших потомков;
- Windows — Job Object с kill-on-close и без разрешённого breakaway для принадлежащей
  запуску работы;
- macOS — managed foreground-профиль из IPC-TRANSPORT, собственная process group
  и живой якорь её идентичности. Уборка охватывает обычные Git/SSH/helpers, сохраняющие
  PGID, в том числе после выхода непосредственного Git и закрытия stdio потомками.

На macOS произвольно демонизирующиеся custom helpers, выходящие из группы через
`setsid`/`setpgid`, double-fork со сменой сессии или внешний сервис, не входят
в поддерживаемую гарантию. Double-fork без смены группы сам по себе не является escape.
Реализация MUST NOT объявлять process group непокидаемым job-контейнером или атомарным
fork-barrier: групповой сигнал не доказывает отсутствия любых конкурентных новых fork.
Имя `git`/`ssh` и запуск через LaunchAgent MUST NOT считаться доказательством
foreground-совместимости произвольного helper.

Уже существующие внешний ssh-agent, общий SSH master и Keychain MUST NOT считаться
owned descendants. Принудительное завершение чужих процессов по имени `git`,
одному PID или факту использования их сервиса запрещено.

**IPC-TRANSPORT.** Git-транспорт приложения MUST применять managed foreground-профиль:

- локальные вызовы Git MUST получать `-c gc.autoDetach=false` и
  `-c maintenance.autoDetach=false`, не запуская отдельный auto-maintenance daemon;
- стандартный OpenSSH MUST запускаться без `-f`, с `ForkAfterAuthentication=no`
  и `ControlPersist=no`; пользовательская конфигурация аутентификации сохраняется;
- custom SSH-обёртки, `GIT_SSH_COMMAND`, `core.sshCommand`, `ProxyCommand`,
  credential/askpass и другие helpers MUST иметь определённый foreground-контракт,
  чтобы считаться частью управляемого профиля. Их произвольное поведение не объявляется
  автоматически покрытым настройками стандартного OpenSSH;
- настройки профиля применяются к конкретному запуску. Общий launcher/guardian
  MUST NOT самовольно переписывать argv/env или пользовательские Git/SSH-конфиги.

Новый helper, сохранивший PGID, MUST оставаться в области уборки даже при имени
`daemon`, закрытых потоках или завершившемся родителе. Использование уже существующего
внешнего агента/master не даёт права завершать его и не превращает его в потомка Relay.

**IPC-05.** После аварии worker или потери foreground-parent lease оставшаяся
принадлежащая запуску работа MUST убираться до передачи владения в границе IPC-04.
Обрыв lease, в том числе после `SIGKILL` родителя на POSIX или принудительного
завершения на Windows, MUST обнаруживаться живым локальным процессом, ответственным за уборку,
а не таймером внутри уже погибшего родителя. Lease MUST NOT продолжать удерживаться
рабочей нагрузкой после смерти foreground-родителя.

Для Linux проверяется subreaper cleanup, для Windows — Job Object cleanup,
для macOS — уборка собственной группы конечного managed foreground-сценария.
Это MUST NOT описываться как универсальное macOS containment произвольных
демонизирующихся потомков. Терминальные сигналы и shutdown системы проверяются
отдельно от обычного завершения клиентского CLI; штатный выход CLI не завершает
worker отдельно запущенного supervisor. Выход foreground CLI `supervise` прекращает
его lease и инициирует остановку принадлежащего этому вызову supervisor/workers.

## 13. Платформенные службы Linux, macOS и Windows

**SVC-01.** В Project Runtime MUST быть реализованы реальные адаптеры пользовательского
автозапуска для всех трёх ОС. Общий интерфейс: `service enable`, `service disable`, `service status`.
Успешная генерация файла без регистрации/опроса менеджера служб не является реализацией
адаптера. Режим `supervise` остаётся доступным foreground для контейнера и внешнего
supervisor без платформенной регистрации.

**SVC-02.** Платформенные артефакты устанавливаются только по явной команде
`relay git-sync service enable`. Обычный запуск, установка бинарника, `connect`,
`worker start` и `auto enable` MUST NOT молча устанавливать службу. Все действия
выполняются от текущего пользователя; скрытые sudo, linger и административный
режим Windows запрещены.
Отсутствующий supervisor MUST NOT запускаться скрытым `systemd-run`, динамической
задачей Task Scheduler или иной неявной native registration. Короткий request
не получает исключение из правил process ownership ради фонового запуска.

### Linux: systemd --user

**SVC-LINUX.** Адаптер MUST создавать user-unit в пользовательском каталоге systemd
с корректным `ExecStart` для абсолютного пути `relay-git-sync supervise`, затем
выполнять `systemctl --user daemon-reload` и явное включение/запуск. Unit MUST задавать
`Restart=on-failure`, остановку собственного cgroup через `KillMode=control-group`
и привязку включения к `default.target`. Status
читает машинные свойства systemd, а не разбирает локализованный текст.

`disable` MUST остановить регистрацию, удалить только собственный unit и обновить
состояние менеджера. Работа user service обычно начинается при login. Запуск до
login/после logout требует отдельно настроенного linger; Relay MUST показать эту
границу и MUST NOT включать linger самостоятельно.

### macOS: launchd LaunchAgent

**SVC-MAC.** Адаптер MUST создавать plist в `~/Library/LaunchAgents` с устойчивым
принадлежащим Relay label и `ProgramArguments` как массивом точных аргументов.
Используются launchd bootstrap/bootout и запрос фактического состояния в домене
текущего пользователя; `RunAtLoad` включает запуск, `KeepAlive` с условием
`SuccessfulExit=false` задаёт восстановление после отказа. Намеренное отключение
выполняется через bootout, чтобы менеджер не перезапустил остановленную регистрацию.

LaunchAgent MUST описываться как механизм пользовательского login-сеанса.
Он MUST NOT объявляться системным LaunchDaemon или обещать запуск при boot
до входа пользователя. Недоступность нужного user/GUI domain даёт понятную ошибку,
а не скрытый запуск с повышенными правами.

`AbandonProcessGroup=false` сохраняет уборку того же PGID средствами launchd,
но MUST NOT объявляться удержанием произвольного дерева потомков. LaunchAgent
не расширяет границу IPC-04/05. У macOS public unprivileged API нет используемого
здесь непокидаемого Job Object-аналога; неподдерживаемый `NOTE_TRACK` и
`coalition_terminate`, не завершающий участников, не заменяют такой механизм.

### Windows: Task Scheduler текущего пользователя

**SVC-WINDOWS.** Адаптер MUST регистрировать задачу Task Scheduler с logon trigger
и principal текущего пользователя, минимальными правами и без скрытого сохранения
пароля. XML MUST задавать отдельные `Command` и `Arguments`, отсутствие случайного
стандартного лимита длительности, политику единственного экземпляра и ограниченные
перезапуски после отказа. Регистрация/удаление и запрос состояния выполняются через
штатный API/утилиту с контролем ошибок.
Для обычного logon-режима используются `InteractiveToken`, `LeastPrivilege`,
`ExecutionTimeLimit=PT0S` и `MultipleInstancesPolicy=IgnoreNew`. Исчерпание лимита
перезапусков показывается как фактическая остановка/ошибка, а не работающий supervisor.

Logon task MUST NOT изображаться службой, работающей до входа пользователя.
Вариант запуска без login требует отдельной явной настройки учётных данных/политики
и не включается этим действием автоматически. Идентичность задачи включает текущего
пользователя; удаление задачи другого пользователя запрещено.

### Общие платформенные требования

**SVC-03.** Пути бинарника, home и файлов конфигурации с пробелами, кавычками и Unicode
MUST корректно проходить через unit/plist/XML и argv. Запуск системной утилиты MUST
использовать массив аргументов без shell-конкатенации. Windows-кодирование Arguments
MUST проверяться обратным разбором в ожидаемый argv, включая завершающие backslash.

**SVC-04.** Enable/disable MUST быть идемпотентны для собственной регистрации.
Частичная ошибка после записи файла/регистрации MUST давать честный статус и
восстанавливаемый повтор, не удаляя чужие артефакты. Service status MUST отдельно
показывать desired registration, фактическую регистрацию/состояние manager и
отзывчивость supervisor с `instanceId`/версиями.

**SVC-05.** Разработка и штатные автоматические проверки MUST использовать fixtures,
не устанавливая службу на пользовательском хосте. Проверяются генерация unit/plist/XML,
argv системных команд, ошибки/rollback и отсутствие скрытых прав. Нативные проверки
на Linux, macOS и Windows MUST учитывать границы IPC-04/05 и выполняться отдельно.
macOS и Windows MUST иметь нативные прогоны в CI. Генератор, fake-адаптер или
POSIX-групповой тест, выполненный на Linux, MUST NOT считаться нативной приёмкой
macOS/Windows или доказательством универсального tree containment.

## 14. CLI и наблюдаемое состояние

Синтаксис ниже задаёт целевую группу команд. Для проектных действий используется
существующий выбор проекта/конфига CLI; `--all` статуса относится к локально известным
репликам, а не к сканированию всей файловой системы.

| Команда                                          | Требуемый результат                                                                               |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `relay git-sync status [--all] --format json`    | Локальный снимок статуса выбранной БД либо всех зарегистрированных БД без fetch и запуска worker  |
| `relay git-sync worker start`                    | Запрос готовому supervisor; desired `running` и подтверждённый readiness worker                   |
| `relay git-sync worker stop`                     | Desired `stopped`, отмена дальнейших попыток и ограниченное завершение собственного процесса      |
| `relay git-sync worker restart`                  | Готовый supervisor завершает старого worker и подтверждает readiness нового instance              |
| `relay git-sync now`                             | Явная попытка обмена с идентифицируемым результатом и deadline, без повторного исполнения мутаций |
| `relay git-sync request get <id>`                | Чтение состояния/результата прежней операции без нового submit                                    |
| `relay git-sync auto enable`                     | Готовый supervisor включает auto/desired `running` и подтверждает readiness worker                |
| `relay git-sync auto disable`                    | Отключение новых автоматических fetch/retry; ручной `now` остаётся доступен                       |
| `relay git-sync connect`                         | Проверенная настройка remote/общей ветки и идентичности                                           |
| `relay git-sync conflicts list`                  | Список открытых конфликтов и заблокированных цепочек                                              |
| `relay git-sync conflicts get <id>`              | Полный материал и fingerprint реального конфликта либо причина ожидания blocked без fingerprint   |
| `relay git-sync conflicts resolve <id>`          | Проверенное решение с обязательным fingerprint и автором                                          |
| `relay git-sync restore`                         | Новая реплика из Git либо явная привязка сохранённой БД в режиме resume                           |
| `relay git-sync service enable\|disable\|status` | Управление пользовательским автозапуском на текущей ОС                                            |
| `relay git-sync supervise`                       | Foreground supervisor; Runtime запускает `relay-git-sync supervise` с тем же контекстом           |

**CLI-01.** `now` при работающем worker MUST обратиться к единственному владельцу.
Если worker остановлен, MUST выполняться одноразовая попытка под lease запроса,
без постоянного демона и без изменения сохранённых desired state и auto-настройки.
Ручной `now` MUST работать без supervisor. Timeout клиентского ожидания MUST
сохранять `requestId` для проверки исхода; неизвестный исход не считается отменой.
Этот `requestId` идентифицирует явную сетевую операцию, а не readiness экземпляра.
Для нового submit ID назначается до запуска компонента; сам факт его назначения
не доказывает acceptance. Он передаётся в `input`/результате действия, не меняя
оболочку одноразового launcher-протокола.

Если после явного `relay git-sync now` остаются реальные неразрешённые конфликты,
команда MUST завершиться с exit 4 и ошибкой `SYNC_CONFLICT` со структурированными
деталями конфликтов и исхода независимых изменений. Материалы конфликтов и уже
согласованные независимые изменения MUST сохраняться; ошибка доставки не откатывает
их и не повторяет пользовательские мутации. Состояние «попытка завершена» MUST NOT
представляться как полная успешная доставка при оставшихся конфликтах.

**CLI-02.** `auto disable` MUST отменять будущие автоматические назначения;
состояние уже начатой попытки показывается отдельно до её завершения/отмены.
`worker stop` MUST иметь приоритет над auto-настройкой до следующего явного start
или auto enable. Наличие системной службы не отменяет desired `stopped` проекта.
Успех `auto enable`, `worker start` и `worker restart` MUST подтверждать readiness совместимого worker;
он не означает отсутствие конфликтов или завершение доставки.

**CLI-03.** Перед `worker start`, `worker restart` и `auto enable` MUST быть проверен
готовый совместимый supervisor выбранного home. Команда передаёт lifecycle-действие
этому supervisor, а не запускает постоянный процесс из одноразового request.
При отсутствии supervisor MUST возвращаться `SUPERVISOR_REQUIRED` с объяснением:
пользователь явно выполняет `service enable` либо держит `supervise` в живом сеансе.
Отказ `SUPERVISOR_REQUIRED` MUST сохранять прежние `mode` и `desired`; проверка
совместимости/readiness supervisor выполняется до изменения этих настроек.

`connect`, `restore`, `status` и ручной `now` MUST NOT требовать supervisor или
неявно запускать его. Установка службы не является побочным эффектом этих команд.
Первичная настройка постоянного обмена: один явный способ запуска supervisor
для `RELAY_HOME`, затем `connect` и `auto enable` выбранного проекта.

**CLI-04.** Режим `restore --resume` MUST принимать необязательный `--project-id`
как постоянный ID проекта, отдельно от workspace-параметра `--project`.
Режим resume несовместим с `--remote`/`--branch`; `--project-id` без resume запрещён.
CLI проверяет сочетание аргументов до запроса компонента, приложение — до выбора
ветки обычного restore. Отсутствующий ID в wire-input опускается, а не сериализуется
как `undefined`. Приложение передаёт результат RECOVERY-10 без выдуманного commit,
а ошибки recovery сохраняют исходные code/exitCode/details.

**CLI-05.** `now` и `status --refresh` MUST принимать `--wait-ms` в диапазоне
1…90000 мс (по умолчанию 60000) и необязательный `--request-id` прежней операции.
Без `--request-id` Runtime выделяет `input.operationId` до version probe/spawn;
с ним передаётся только `input.requestId` для ожидания, без нового submit.
Одновременные operationId/requestId в wire запрещены. `request get <id>` соответствует
`request.get {requestId}` и MUST читать live/сохранённый исход без запуска Git-обмена.

`GIT_SYNC_WAIT_TIMEOUT` (exit 4) MUST сохранять ID и наблюдавшееся queued/running,
не подменяясь неготовностью worker. Process timeout (`GIT_SYNC_TIMEOUT`, exit 124),
отмена или повреждение envelope сохраняют correlation и исходную диагностику;
при недоказанном исходе указывается `state: unknown`. `GIT_SYNC_OUTCOME_UNKNOWN`
(exit 4) и истечение retention MUST NOT трактоваться как успех, отмена или разрешение
повторного submit по read/wait ID. Persistent operation не отменяется самим budget
ожидания; одноразовый обмен сохраняет собственную границу request lease.

У cached `status` параметры ожидания запрещены без `--refresh`. Для workspace
`--refresh --all --wait-ms` применяется отдельно к каждой регистрации с отдельным ID;
один `--request-id` допустим только при выборе одного проекта, не с `--all` или
неявным workspace. Ошибка одной регистрации сохраняет её correlation рядом
с результатами остальных.

### JSON статуса v1

CLI JSON MUST иметь стабильную форму `data: {version: 1, scope, items}`, включая
один проект (`scope: "project"`) и частично недоступный workspace (`scope: "workspace"`).
Элемент `items` содержит `name`, `path`, `ok` и статус в `data` либо причину в `error`.
Ошибка одной регистрации не скрывает статусы доступных БД. В успешном статусе проекта
смысловые поля отображаются на следующие фактические пути:

| Поле                                                                                                       | Контракт                                                                                                               |
| ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `projectId`, `replicaId`, `databaseIdentity`                                                               | Идентичность проекта, реплики и физической БД; `projectId` может быть `null` до подключения                            |
| `mode`                                                                                                     | Сохранённый режим `auto` / `manual`                                                                                    |
| `worker.desired`                                                                                           | `running` / `stopped`                                                                                                  |
| `worker.actual`, `worker.responsive`                                                                       | Наблюдаемое `running` / `stopped` / `unknown` и результат health-проверки                                              |
| `worker.instance`, `worker.pid`, `worker.binaryVersion`, `worker.protocolVersion`                          | Сведения об экземпляре, по отдельности `null` при неизвестности                                                        |
| `phase`, `attemptId`                                                                                       | Фактическая фаза/попытка живого владельца; без него `idle` / `null`                                                    |

**STATUS-01.** Неизвестное MUST быть `null`, а не ноль, успех или вычисленное
предположение. Ahead/behind MUST считать реальные коммиты между известными refs;
число outbox MUST NOT выдаваться за Git ahead. Состояние «синхронизировано» всегда
ограничено известным HEAD и моментом наблюдения.

**STATUS-02.** Фазы MUST различать ожидание, fetch, подготовку, validation,
commit, push, проверку исхода, локальное применение, backoff и остановку.
Протухшая сохранённая фаза не означает выполняющийся сейчас процесс.

**STATUS-03.** Last error MUST сохранять причину и операцию: локальный Git-конфликт,
недоступный origin, несовместимость, занятость, отказ Core и stale resolve различимы.
Диагностика Git сохраняет полезный stderr с удалением credentials; машинный stdout
CLI остаётся одним корректным ответом, прогресс выводится через предусмотренный канал.

**STATUS-04.** Наличие конфликтов само по себе MUST NOT превращать `status`
или `conflicts list` в ошибку: это успешные чтения с exit 0, возвращающие состояние
и материалы списка. Неразрешённый конфликт после явного `now` имеет иной контракт
exit 4 / `SYNC_CONFLICT` из CLI-01. Готовность worker, завершение попытки и полная
доставка MUST оставаться различимыми исходами.

**STATUS-05.** `request get` MUST различать `queued`, `running`, `completed`, `failed`
и `unknown`. Успех чтения (exit 0) не означает completed; failed сохраняет ошибку,
unknown после потери владельца/expiry не утверждает отсутствие эффектов.
Журнал явных операций ограничен: до 64 активных и 128 недавних исходов, retention
15 минут; auto polling не журналируется. Эти границы MUST NOT сокращать срок
хранения durable outbox, доказательств дедупликации или неизменяемых batch receipts.

**STATUS-06.** Status/now MUST возвращать актуальный полный `pending.changesets`
после accept отдельно от `publication: {afterSequence, window}`. Window либо null,
либо `{afterSequence, nextSequence, hasMore, examined, included, deferred, sourceBytes,
oversized, completed}` последнего ограниченного окна. Deferred/hasMore относятся
к подготовке этого окна; completed не означает пустой outbox.
Неполный prepare MUST показывать `conflicts.freshness: "partial"`, не current по одному
совпадению generation. Конец suffix/cursor 0 не подтверждает просмотр пропущенного prefix.
Только полное покрытие контекста либо full-overlay accept позволяет отмечать полноту.
`nextAttempt.reason` различает publication-window, polling, contention и network-retry
и показывается лишь для действительно назначенной попытки живого владельца.

## 15. Совместимость и будущий PostgreSQL

**PG-01.** Порты MUST сохранять одинаковый смысл команд, ID, структурированных ссылок,
переносимых версий, адресов/резервов, exact data, атомарности и receipts независимо
от СУБД. Git служит локальным репликам; будущий серверный PostgreSQL обслуживается
своим адаптером через API.

**PG-02.** Будущий PostgreSQL-адаптер обязан реализовать асинхронное I/O и собственную
атомарную проверку версий/предикатов. Наличие такого порта сейчас MUST NOT описываться
как готовые PostgreSQL или HTTP API.

**PG-03.** Модель миграции MUST предусматривать consistent snapshot, перенос pending,
Core validation и явный writer cutover. После переключения не допускаются два
несогласованных авторитетных писателя Git/API. Offline-реплики получают определённый
режим повторного подключения и сохранения своих изменений; их outbox не отбрасывается.
Реальный запуск этой миграции относится к будущему серверному этапу.

**COMPAT-01.** Версии бинарника, SQL-схемы, предметной модели, Git-формата и process
protocol MUST проверяться независимо. Несовместимая новая версия не открывается
на запись старым worker. Техническая миграция schema v2 MUST быть атомарной,
сохраняющей исходные данные; новая schema version определяется реализованной миграцией.

AC-23, AC-24 и AC-26 MUST проверять, что постоянный worker создан долгоживущим
supervisor, предварительно запущенным явным service/foreground-сценарием. Завершение
короткого request с собственной Job/group не завершает эти процессы и не требует
выхода его потомков из контейнера. Потеря foreground-parent lease, напротив,
останавливает принадлежащие этому foreground-вызову supervisor/workers.

Отдельные случаи `worker start`, `worker restart` и `auto enable` без supervisor
MUST давать `SUPERVISOR_REQUIRED` при неизменных `mode`/`desired`, без скрытого native
install или запуска демона. При готовом совместимом supervisor проверяются readiness
worker и сохранение `stopped` после повторного запуска supervisor. `connect`, `restore`,
`status` и одноразовый `now` под lease MUST проверяться также без supervisor.

AC-25 и нативные AC-30–AC-32 MUST включать потерю foreground-parent lease и аварийное
завершение worker: `SIGKILL` на POSIX, эквивалентное принудительное завершение на Windows.
Утверждения проверяются после production cleanup и до cleanup fixture. На Linux
проверяется владение subreaper, на Windows — принадлежность Job Object и kill-on-close,
на macOS — конечный managed foreground-сценарий с обычными helpers в том же PGID,
в том числе с закрытыми stdio и после выхода непосредственного Git.

Приёмка профиля MUST проверять `gc.autoDetach=false`/`maintenance.autoDetach=false`,
foreground-настройки стандартного SSH и сохранность пользовательской auth-конфигурации.
Внешние agent/master/Keychain не завершаются. Сценарий custom helper с выходом через
`setsid`/`setpgid` MUST явно отличаться от поддерживаемого группового сценария macOS;
его нельзя засчитать как закрытую гарантию уборки. Нативный тест process group
не доказывает atomic fork-barrier или остановку любых произвольных fork-гонок.

Успешный AC-29 не заменяет AC-30–AC-32. Отсутствующий нативный прогон MUST явно
оставаться непроверенным критерием; он не получает статус успеха по анализу кода.

AC-21 MUST включать явный resume после сбоев до public link, между link/config
и после config. Второй процесс должен принять поздний commit/outbox до отказа
первой публикации; ordinary retry сохраняет их и не вызывает materializer, resume
сохраняет точные данные и `replicaId`, возвращая `sourceCheckpoint: null` без fetch/ack/progress.
Проверяются выбор ID без home scan, strict-sync read-only validator, чужой target
того же projectId, подмена после config, живой public WAL, сомнительные staging-алиасы,
legacy intent v1, частичная cleanup и `RESTORE_NOT_PENDING` после полной уборки.
CLI/приложение отдельно проверяют несовместимые источники resume, прозрачность
`recovery.failure` и работу без supervisor; успешная привязка не считается доставкой.

### Командный сценарий 2–3 независимых реплик

**AC-TEAM.** Обязательная функциональная приёмка MUST проверять обмен на 2–3 независимых
репликах. Штатный связанный сценарий использует три реплики одного проекта: двух активных
писателей и третьего участника, возвращающегося после offline. Fixture MUST создать
один origin, три отдельные файловые SQLite, Git-копии, окружения HOME/RELAY_HOME и разные
`replicaId`. Участники начинают с общего проверенного baseline. Независимость данных
не подменяется несколькими соединениями к одной БД.

Командный сценарий MUST включать конечные управляемые волны:

1. Активные писатели независимо создают разные документы с одинаковым предварительным
   ключом. Контролируемый первый push определяет winner; после обмена сохраняются все
   исходные ID, уникальные ключи, адреса и ссылки на ожидаемые ID.
2. Участники меняют независимые поля/сущности, дописывают комментарии к общей задаче
   и выполняют связанные atomic batch. Проверяются точные значения, неизменяемые
   первоначальные receipts и отсутствие частично принятых пакетов.
3. Несовместимые изменения одного поля дают полный материал конфликта. Весь changeset
   удерживается, причинные потомки ждут, независимая работа продолжает публикацию.
4. Третья реплика пропускает обмен, сохраняет собственные offline-изменения и возвращается
   с прежними source IDs/digests. Её локальный outbox согласуется без потери принятых данных
   других участников и без повторного исполнения пользовательских команд.
5. После явного разрешения разрешимых конфликтов все три реплики получают одинаковое
   каноническое состояние, переносимые версии, адреса, комментарии и receipts.
   Повторный обмен не создаёт echo; незавершённые случаи остаются явными, без ложного ack.

Уменьшенный состав участников MUST сохранять все гарантии AC-09–AC-22 и crash-границы
AC-25. Подробные non-FF, потеря успешного ответа push, поздняя запись между prepare/push,
crash/recovery, неделимость batch, дедупликация и отсутствие echo проверяются адресными
сценариями владельцев; для них достаточно двух реальных реплик. Их не требуется целиком
дублировать внутри AC-TEAM. Restore и несовместимые receipts сохраняют отдельные AC-21/AC-22.

Расширенные функциональные сценарии Core и Git Sync на 50 репликах запускаются только
вручную отдельным extended-набором вне обязательного CI, `check` и `test:all`.
В нём сохраняются точные предметные assertions, проверки отказов и конечные deadlines.
Этот размер — дополнительный масштаб функционального сценария, не обязательный порог
приёмки и не обещание поддержки 50 одновременно активных пользователей. Размещение
и явные команды запуска описаны в
[правилах extended-набора](tests/README.md#расширенная-проверка-репликации).

Штатный и extended-наборы MUST NOT выдавать функциональную сходимость за throughput,
p95/p99 или SLA. Нагрузка и сравнительные измерения разрешены только по отдельному
явному запросу, вне штатных проверок и CI.

## 17. Порядок реализации и критерий завершения

| Этап                   | Поставляемый результат                                                           | Проверяемый выход                            |
| ---------------------- | -------------------------------------------------------------------------------- | -------------------------------------------- |
| 1. Executor и ports    | Общий путь одиночных команд/batch, пригодная I/O-граница и SQLite-адаптер        | AC-01–AC-05, локальные регрессии             |
| 2. Durable changesets  | Атомарный outbox, переносимые версии, миграция исходной БД                       | AC-02, AC-04, AC-06, crash локального commit |
| 3. Snapshots и merge   | Exact export/import, записи по ID, ключи, переходы и предметное согласование     | AC-07–AC-17                                  |
| 4. Ручной обмен        | `connect`, `now`, `restore`, conflicts, подтверждения и recovery                 | AC-18–AC-22, соответствующие crash-границы   |
| 5. Постоянные процессы | Workers, supervisor, versioned control, CLI и три платформенных service-адаптера | AC-23–AC-33                                  |
| 6. Командная приёмка   | Три реплики и адресные регрессии затронутых сценариев                            | AC-TEAM и матрица применимых критериев       |

Существенная декомпозиция допустима в пределах нужных ответственностей.
Предметные и тестовые ревью выполняются по действующим правилам проекта.
Каждый этап MUST иметь работающий код и смысловые проверки до объявления готовности.
Наличие порта без реального SQLite-пути, непроверенного нативного адаптера или
интерфейса конфликтов без проверки переходов не считается завершением этапа.
