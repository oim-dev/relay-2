# Relay: единое ядро команд и Git-синхронизация локальных реплик

Этот документ сохраняет одобренное архитектурное предложение: участники работают
с независимыми локальными базами, а постоянные фоновые процессы согласуют изменения
через одну общую Git-ветку данных. Локальная команда завершается после надёжной
записи в SQLite; доступность сети не определяет возможность работать с проектом.

Документ предназначен разработчикам Core, Storage, Runtime, CLI и Git Sync.
Он объясняет решения, их причины и границы. Обязательные требования, форматы
и критерии приёмки находятся в [ТЗ реализации](GIT-SYNC-IMPLEMENTATION-SPEC.md).
Описанное ниже — целевое устройство, а не утверждение о готовности кода.
Примеры будущих API и команд обозначают проектируемый контракт.

## 2. Три ответственности и границы компонентов

Разделяем то, что хранится, то, что пользователь делает, и то, как изменения доставляются.

1. **Предметные данные:** сущности, связи, критерии, комментарии, планы, история,
   участия, назначения ключей и сохранённые адреса. Они имеют собственный смысл
   независимо от способа хранения и наличия Git.
2. **Прикладные операции:** автор, проверка исходных версий, разрешение адресов,
   атомарность нескольких действий, идемпотентность и результат команды.
3. **Репликация:** outbox, зависимости changeset, подтверждения доставки, согласование,
   конфликты, повторные попытки и жизненный цикл worker.

```text
Локальная CLI ──────┐
Будущий Server/API ─┼──→ Core ──→ контракт хранения ──┬──→ SQLite
Git Sync ──────────┘   команды/переходы               └──→ PostgreSQL позднее
   ↕
одна общая Git-ветка

Contracts: команды, результаты, переносимые данные и process protocol
Project Runtime: локальный контекст, пути, launcher/lifecycle и регистрация служб
Git Sync: Git, согласование, workers, supervisor и планирование доставки
```

Core остаётся единственным владельцем предметных правил. Storage реализует механизмы
чтения, CAS, транзакций и технических миграций. Contracts содержит переносимые формы
без Bun, SQL и файловой системы. Runtime выбирает контекст и запускает совместимый
компонент. CLI представляет результаты. Приложения не импортируют исходники друг друга.

Сетевой Git-код принадлежит `apps/git-sync`, а не Runtime или Core. Контракты
одноразового запуска и управления постоянным worker принадлежат Contracts;
локальный launcher, обнаружение контекста и платформенные service adapters — Runtime.
Runtime выполняет native registration в systemd, launchd и Task Scheduler как часть
local launcher/lifecycle, без Git-транспорта. Сам процесс `supervise`, workers
и Git принадлежат `apps/git-sync`. API Git, Core и снимков не зависит от ОС.

## 3. Один транзакционный исполнитель

Точечная команда — вызов `executeCommands([command])`. Batch передаёт тому же
исполнителю несколько команд. Используются общие схемы, обработчики, предметные правила
и результаты. Отдельного «упрощённого пути записи» для одиночной CLI-команды нет.

Предметные команды вроде создания документа, изменения критерия или переноса задачи
сохраняются как удобные адаптеры. Пользователю не требуется писать batch JSON ради
одной правки. Чтения остаются самостоятельными оптимизированными сценариями:
адресное чтение, ограниченная SQL-страница, краткая проекция и составной снимок.

Концептуальный пример будущего внутреннего API:

```text
relay application create …
  → executeCommands([application.create(…)])
  → приложение + его доска + адреса + changeset
  → один SQLite commit

relay batch …
  → executeCommands([document.create(…), task.create(…), task.link(…)])
  → все предметные эффекты + batch receipt + changeset
  → один SQLite commit
```

Неявные эффекты — часть той же операции. Создание приложения вместе с доской,
обновление участия реализации или перенос включения между планами не распадаются
на независимо отправляемые записи. Одна успешная изменяющая транзакция создаёт один
changeset независимо от числа SQL-записей и внутренних savepoint.

Проверка `--check` откатывает тот же расчёт и ничего не публикует. Повтор известного
batch возвращает прежнюю квитанцию без нового changeset. Чистый no-op не создаёт
фиктивную правку; первая запись квитанции нового batch сама является переносимым
эффектом, даже если его предметные действия оказались no-op.

Такое ядро исключает расхождение правил одиночной записи, batch и будущего API.
Импорт согласованных эффектов использует проверку переходов Core, но не повторное
исполнение исходного пользовательского запроса с повторной выдачей ID.

## 4. Независимые записи и агрегатные инварианты

Постоянный ID нужен не только карточке задачи или документа. Независимо изменяемые
элементы получают собственные записи и версии:

- критерий задачи;
- этап плана;
- включение задачи в этап;
- связь документа с предметной целью;
- участие приложения или исполнителя;
- назначение ключа и резерв адреса;
- комментарий и неизменяемый материал предметной истории.

Отдельная идентичность позволяет двум участникам добавить разные критерии или
комментарии, не заменяя целиком массив в карточке. Снятие связи адресует конкретное
включение, а не «все связи с таким текстом». Повторное включение имеет определённую
новую идентичность и не стирает факт снятия старого.

Граница записи не отменяет границу инварианта:

- `done` проверяет обязательные критерии, детей и зависимости задачи в актуальном
  согласованном контексте;
- `transfer` проверяет исходный и целевой план, их версии, принадлежность и ограничения
  включения; обе стороны меняются целиком либо не меняются;
- запись истории проверяет `session`, активный `runId`, автора и допустимый переход;
  два конкурентных захвата участия не становятся двумя допустимыми владельцами;
- неизменяемые комментарии, checkpoints и квитанции нельзя переписать импортом.

Упорядоченные коллекции используют устойчивые позиции. Вставка между A и B выделяет
позицию новому элементу, не перенумеровывая все последующие. Детерминированный tie-break
по ID допускается для одновременных независимых вставок; противоречивое перемещение
одного элемента или цикл ограничений порядка требует конфликта. Служебная компактация
позиций не должна выглядеть как массовая пользовательская правка.

## 5. Changeset: сохранённые эффекты, версии и причинность

Changeset — неделимая единица доставки одной локальной транзакции. Он содержит:

- уникальный постоянный ID и `replicaId` локальной БД;
- причинные зависимости от ранее полученных или созданных изменений;
- автора и версию формата;
- исходные переносимые версии затронутых записей и значимого контекста;
- конкретные эффекты с уже выделенными ID;
- данные `base` и `local`, необходимые для трёхстороннего согласования;
- сведения о проверяемом переходе, включая прочитанные обязательства и предикаты;
- ссылку на неизменяемую квитанцию, если запрос был явным batch.

Changeset и предметные записи сохраняются атомарно в SQLite. Уведомление worker —
ускорение обнаружения; потеря уведомления не теряет изменения, поскольку outbox
и поколение доступны после перезапуска.

Числовой `revision` локальной реализации не является распределёнными часами.
Переносимые версии различают независимые ветви изменения и позволяют проверить
исходное состояние. Время создания, `updatedAt`, максимум локальной ревизии и порядок
получения сообщений не выбирают победителя. Временные метки нужны для истории
и диагностики; причинность выражается явно.

Например, пакет B, добавляющий комментарий к задаче, созданной пакетом A, зависит
от A. Правка другого существующего документа не обязана ждать A только потому,
что возникла позже в той же реплике. Зависимости учитывают как запись, так и чтение
состояния, необходимого для допустимости перехода. Ошибочно объявленная независимость
опасна не меньше, чем избыточная глобальная очередь.

Подготовка публикации выбирает ограниченное SQL-окно sources до декодирования их JSON.
Один слишком большой changeset переносится целиком и отдельно; ограничение не дробит
атомарный пакет и не обещает ограничить размер всего canonical snapshot. Курсор окна
отделён от ack, а ожидание непринятых dependencies остаётся pending. Core `blocked()`
показывает эти причины отдельной полной диагностикой графа, не подменяя ими реальные
конфликты или дешёвые счётчики status. Транспорт сохраняет прогресс обхода и не зацикливается
на конфликтном префиксе; полный актуальный остаток сохраняется при accept.

Повтор доставки переносит сохранённые эффекты. Он не вызывает повторно `task.create`,
не генерирует новые ID и не пересчитывает пользовательский запрос на новом состоянии.
Повтор подготовки после non-fast-forward может менять транспортный коммит и
предварительное назначение ключа, сохраняя идентичность исходного changeset.

## 6. Одна общая ветка и каноническое состояние

Все участники публикуют в **одну общую ветку базы**. Веток участников и отдельного
интегратора нет. Локальные Git-клоны и служебные каталоги принадлежат репликам;
публикация выполняется обычным fast-forward push поверх полученного HEAD.

Ветка содержит текущее каноническое состояние:

- записи по постоянным ID;
- отдельные длинные Markdown-тексты;
- адреса, подтверждённые назначения и резервы;
- компактные подтверждения принятых changeset;
- явные batch receipts согласно действующему контракту идемпотентности;
- версию формата, идентичность проекта и контекст последней публикации,
  необходимый для проверки переходов.

Git не хранит рабочий SQLite, WAL, SQL-индексы, пути машины или PID worker.
Экспорт читает согласованный снимок **сохранённых данных**, а не пользовательские DTO.
Например, UI может показывать документ вне снятого раздела, но экспорт не должен
заменить сохранённую историческую ссылку значением `null`. Аналогично исторический
ключ в checkpoint или квитанции не заменяется текущим ключом сущности.

Физические пути нормализованных owners, parts, comments, receipts и подтверждений
закреплены в разделе snapshot ТЗ. `manifest.json` разделяет layoutVersion,
formatVersion и modelVersion: writer использует layout 2, reader — явные ветки 1 и 2
при прежних format 1/model 2. JSON-файлы layout 2 имеют два пробела и конечный LF;
предметные fingerprints остаются компактным canonical UTF-8 JSON без LF.
Markdown-sidecars связываются закрытыми `{field, digest}` с SHA-256 точных байтов.
Смена оформления не меняет source digests/версии и не переписывает старые коммиты
на idle; mixed history проходит обычную проверку Core.

Проверка publication history принадлежит Core, а непосредственный Git parent
и факт принятия общей веткой — транспорту. `validateReplicationHistory(base, target, {chain})`
выдаёт непрозрачный `ValidatedReplicationHistory` с неизменяемым `proof.snapshot`.
Его можно передать в `prepare`/`accept` вместе с этой же целью. Объект, созданный
самостоятельно или восстановленный из JSON, не переносит authority проверки;
локальные guards и pending проверяются заново. Это свидетельство внутри процесса,
не замена Git ack или переносимому материалу публикации.

Обычный Markdown хранится в отдельном UTF-8 файле. Строка JavaScript/JSON может
содержать непарный surrogate, который нельзя без потерь записать как UTF-8 Markdown.
Для такого не-well-formed UTF-16 допускается явно обозначенное lossless
JSON-представление с экранированием непарных code units. Импорт восстанавливает
исходную строку точно; нормализация, удаление или замена символов запрещены.

### Квитанция и подтверждение — разные объекты

Квитанция batch отвечает: «какой запрос с каким автором был выполнен и какой результат
получил вызывающий». Она сохраняет первоначальные ID, ревизии и полное содержание,
предусмотренное текущим контрактом. Повтор с тем же ключом возвращает её, даже если
сущность переименована или изменилась. Ключи квитанций автоматически не истекают.

Транспортное подтверждение отвечает: «этот changeset принят канонической веткой».
Оно содержит идентичность и контрольные сведения, достаточные для дедупликации
и восстановления после потерянного ответа. Оно не заменяет batch receipt и не должно
содержать новый пересчитанный пользовательский результат.

Полный вечный подробный журнал каждой команды для обмена не нужен. Обязательны
текущее состояние, доказательства дедупликации, явные квитанции и достаточный контекст
переходов. Подробные локальные пакеты можно освобождать после подтверждения и достижения
безопасной точки восстановления. Схема хранения не обещает постоянный размер дерева:
сами данные, неизменяемые квитанции и подтверждения могут расти.

Размер актуального дерева и размер всей Git-истории различаются. Удаление старого
служебного файла из нового снимка не удаляет его из прежних коммитов. Pruning рабочего
дерева не является очисткой Git-истории. Переписывание опубликованной истории и
force push не входят в обычную синхронизацию.

## 7. Цикл согласования и конкурентная публикация

Одна попытка выполняется следующим образом:

1. Получить remote HEAD через fetch и проверить идентичность проекта и формат.
2. Сопоставить подтверждения с локальным outbox. Выбрать готовые пакеты, чьи зависимости
   приняты remote либо включены ранее в тот же кандидат.
3. Подготовить предметное трёхстороннее согласование относительно соответствующих base.
4. Согласовать предварительные ключи с уже принятыми назначениями HEAD.
5. Проверить через Core данные, неизменяемость, переходы, связи и агрегатные ограничения.
6. Зафиксировать подготовку с guard локального поколения и точным набором changeset.
7. Создать канонический коммит поверх полученного HEAD и выполнить обычный fast-forward push.
8. Подтвердить принятие remote; сохранить ack и применить входящие изменения коротким
   локальным commit с повторной проверкой поколения и версий.

Сеть, Git-команды и тяжёлое согласование выполняются вне транзакции записи SQLite.
SQLite и Git не имеют общей транзакции, поэтому границы фиксируются восстановимыми
checkpoint подготовки и публикации.

Если remote продвинулся, push отклоняется как non-fast-forward. Worker делает fetch
и повторяет подготовку тех же пакетов с прежними ID. Если одновременно появились новые
коллизии ключей, их назначения пересчитываются относительно нового HEAD. Нельзя
заменить это принудительным push или слепым текстовым rebase файлов.

Если ответ push потерян, неизвестно, был ли коммит принят. Worker проверяет реальную
ветку и подтверждения. Принятый changeset не исполняется второй раз; неподтверждённый
остаётся ожидающим. Локальное создание коммита не означает принятие origin.

### Локальная запись во время сети

Пусть подготовка прочитала поколение 40 и changeset A. Пока выполняется push,
пользователь сохранил B и получил поколение 41. Успех push A не даёт права:

- заменить всю БД снимком поколения 40;
- объявить B отправленным;
- подтвердить новый локальный текст только по совпадению ключа сущности.

Можно подтвердить ровно A по его ID. Для установки объединённого состояния требуется
пересчитать актуальный локальный остаток с B и пройти новый guard. Неотправленные
пакеты остаются явным слоем над каноническим состоянием. Один конфликтный пакет не
превращает весь локальный снимок в блокирующую единицу.

## 8. Предметное трёхстороннее объединение

Согласование сравнивает `base`, `local` и `remote`, а не выбирает более поздний файл.

| Ситуация                                          | Ожидаемое решение                                                                      |
| ------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Разные сущности                                   | Совместить, затем проверить общие ссылки и предикаты                                   |
| Разные поля одной сущности                        | Совместить, если итог и переход допустимы                                              |
| Одинаковая правка одного поля                     | Один итог без дублирования эффекта                                                     |
| Разные новые комментарии                          | Сохранить оба по ID, не менять старые                                                  |
| Разные значения одного поля                       | Явный конфликт                                                                         |
| Непересекающиеся правки Markdown                  | Совместить по общему текстовому base с сохранением остальных байтов                    |
| Пересечение Markdown либо неоднозначная вставка   | Конфликт с тремя полными версиями                                                      |
| Добавления и снятия ID-связей                     | Рассчитать дельты относительно base; снятая связь не воскресает из устаревшего массива |
| Независимые вставки в порядок                     | Сохранить устойчивые позиции и детерминированный порядок                               |
| Несовместимые перемещения                         | Конфликт порядка                                                                       |
| Удаление против изменения                         | Конфликт, если предметное правило явно не разрешает сочетание                          |
| `done` против нового невыполненного обязательства | Конфликт допустимости перехода, даже если JSON корректен                               |
| Два конкурентных `session takeover`               | Конфликт владения, а не объединение двух активных run                                  |

Проверки JSON и `doctor` необходимы для обнаружения повреждения, но недостаточны.
Валидная конечная форма может быть получена запрещённым переходом: например,
переписыванием неизменяемого checkpoint или изменением автора существующего комментария.
Core проверяет исходное и итоговое состояния и контекст эффектов.

Changeset неделим. Если конфликтует один его эффект, ни один эффект пакета не
публикуется отдельно. Его зависимые пакеты ждут. Независимые пакеты этой и других
реплик продолжают согласование.

### Разрешение конфликтов

Конфликт сохраняет полные base/local/remote, затронутые ID, причины и fingerprint
просмотренных версий. Пользователь может изучить материалы и подготовить решение.
Перед применением проверяются fingerprint, актуальные версии и все правила Core.
Устаревшее решение отклоняется; оно не применяется «примерно к тому же полю».

Исходный пакет и исходная квитанция не переписываются. Решение — отдельная запись,
связанная с исходным changeset и просмотренными версиями. Выбор удалённого результата
не означает, что зависимые локальные пакеты автоматически допустимы: они повторно
проверяются на выбранных ID и состояниях. Правило неизменяемости нельзя обойти
параметром «принять моё».

Custom v1 задаёт `patch: [{transition, entityId, field, value}]` и изменяет только
`document.name`, `summary` или `body`, действительно затронутое выбранной исходной
command boundary. Остальные эффекты всего changeset проходят обычное согласование.
Неизменяемые source/receipt и исходные digests сохраняются; ручная поправка имеет
автора и время решения. Уже опубликованное более раннее решение не скрывает позднее
предложение: оно остаётся явным stale-конфликтом до выбора `remote` либо новой
предметной команды для дальнейшего изменения принятого результата.

Особый случай — независимое offline-исполнение разных запросов под одним batch
operation key. До обмена локальные базы не знают друг о друге. Несовместимые квитанции
дают конфликт всего пакета, а не молчаливую замену результата. Глобальное исполнение
ровно один раз до связи с origin не обещается; исходные локальные квитанции сохраняются.

## 9. Ключи, адреса и Markdown-ссылки

ID определяет идентичность. Человекочитаемый ключ — отдельное назначение в области
проекта. До подключения origin он локальный, после подключения и до принятия —
предварительный, после подтверждённого принятия — окончательный.

Пример коллизии:

```text
Реплика A: предварительный DOC-13 → id-A
Реплика B: предварительный DOC-13 → id-B

Origin первым принимает A:
  DOC-13 → id-A остаётся окончательным.

B получает новый HEAD:
  id-B получает свободный DOC-14.
  Если DOC-14 уже занят к следующей попытке, выбирается следующий свободный ключ.
  ID id-B и все структурированные ссылки на него остаются прежними.
```

Предварительная заявка отделена от окончательного назначения. Проигранный `DOC-13`
не становится алиасом `id-B`: этот адрес уже принадлежит `id-A`. Обычный rename,
сохраняющий исторический алиас, и collision renumber — разные операции. Подтверждённые
адреса и резервы удалённых назначений не выдаются другой сущности при обычном обмене.

Изменение по читаемому адресу защищается `expectedAddresses: [{ref, expectedId}]` —
привязкой, которую прочитал вызывающий. Если старый редактор помнит `DOC-13 → id-B`, команда
после перенумерации не должна изменить `id-A`. Совпадение числовой ревизии содержания
не заменяет проверку адреса.

После локально известного переназначения предварительного ключа запись по нему
без привязки к просмотренному ID отклоняется; можно адресовать
постоянный ID. Автоматическое разрешение ключа в текущий ID при новом вызове
не доказывает, какую привязку видел автор ввода. Без проверяемого guard нельзя
отличить «свежую интерактивную команду» от ввода старого редактора.

Структурированные ссылки всегда хранят ID. Для устойчивых Markdown-ссылок выбирается
явный адрес вида `relay://<projectId>/<entityId>`, например:

```markdown
[Требования к заказу](relay://<project-id>/<document-id>)
```

Угловые скобки обозначают подстановочные ID, а не буквальный адрес. Метка ссылки —
сохранённый текст автора; изменение ключа не меняет цель. Обычное упоминание `DOC-13`
без ссылки остаётся текстом и не обещает устойчивой адресации. Если интерфейс предлагает
вставку ссылки по ключу, он разрешает адрес по проверенной карте и сохраняет ID-адрес.
Markdown разбирается структурно; regexp-replace всех вхождений ключа запрещён.
Кодовые блоки, inline code и экранированный текст не преобразуются в ссылки.

## 10. Постоянные workers, supervisor и наблюдаемость

Единица worker — физическая локальная БД с собственной идентичностью реплики.
Одна БД, зарегистрированная в нескольких workspace или доступная через symlink,
имеет одного владельца синхронизации. Две независимые локальные реплики одного
`projectId` имеют разные `replicaId` и разных workers.

Постоянным worker владеет только долгоживущий supervisor. Его запускает native manager
после явного `relay git-sync service enable` либо пользователь держит foreground-вызов
`relay git-sync supervise` в живом сеансе. Перед первым включением фонового обмена
нужно настроить один из этих способов для выбранного `RELAY_HOME`, затем подключить
проект и вызвать `auto enable`.

Короткий CLI-request остаётся внутри собственного Job Object/process group.
Он не создаёт постоянных демонов и не выводит потомков из контейнера ради их сохранения
после ответа. Команды `worker start`, `worker restart` и `auto enable` обращаются
к готовому совместимому supervisor, который запускает worker и подтверждает readiness.
Если supervisor отсутствует, возвращается `SUPERVISOR_REQUIRED`, а `mode` и `desired`
не меняются. Совместимость и readiness supervisor проверяются до изменения настроек.

`connect`, `restore`, `status` и ручной `now` не требуют supervisor. При остановленном
worker ручной обмен выполняется одноразово под lease запроса, без запуска постоянного
демона и смены сохранённого режима. `worker stop` сохраняет desired `stopped`,
который учитывается и после следующего запуска supervisor.

Host supervisor восстанавливает умершие процессы и распределяет общий бюджет CPU
и сети. У проектов собственные состояния, ошибки и backoff. Медленный origin A
не удерживает слот всех проектов, а конфликт A не останавливает B. Повторные сигналы
об изменениях объединяются; durable outbox остаётся источником истины.

Один ручной `now` завершает одно ограниченное окно публикации. Успешное окно и
сохранённый cursor не означают пустую очередь; status показывает фактический полный
pending и отдельно сведения последнего окна. Полные conflicts/blocked получаются
явной диагностикой. Ожидающий dependency changeset не получает выдуманных сторон
или fingerprint и не требует resolve, пока не возник реальный конфликт.

Постоянный worker обнаруживает чужие изменения даже при пустом локальном outbox.
Polling ограничен по частоте и числу конкурентных Git-процессов; backoff включает
jitter, а очередь обеспечивает fairness. Debounce локального экспорта не зависит
от сетевого backoff и имеет верхнюю границу ожидания. Это функциональные свойства
планировщика, не обещание конкретной пропускной способности.

Целевой пользовательский интерфейс:

```text
relay git-sync status [--all] --format json
relay git-sync worker start|stop|restart
relay git-sync now [--request-id ID] [--wait-ms N]
relay git-sync request get ID
relay git-sync auto enable|disable
relay git-sync connect
relay git-sync conflicts list|get|resolve
relay git-sync restore
relay git-sync service enable|disable|status
relay git-sync supervise
```

Статус читает локальное наблюдение без запуска fetch. Он отдельно показывает:

- desired и actual состояние worker, отзывчивость, `instanceId` и версии;
- текущую фазу и идентичность выполняемой попытки;
- реальные Git ahead/behind относительно известного remote HEAD;
- число pending changeset и возраст самого старого;
- наличие неэкспортированных изменений;
- момент последнего успешного fetch и свежесть знаний о remote;
- конфликты, последнюю ошибку и действительно назначенную следующую попытку.

Неизвестное значение — `null`. Ноль ahead не равен пустому outbox: изменения могут
ещё не иметь Git-коммита. Старый heartbeat не доказывает отзывчивость, PID не доказывает
идентичность процесса, а `spawn` не доказывает готовность. Успех `worker start` требует
проверяемого readiness совместимого экземпляра.

Завершение попытки не равно полной доставке. Явный `relay git-sync now`, после
которого остаются реальные неразрешённые конфликты, возвращает exit 4 и `SYNC_CONFLICT`
с деталями. Материалы конфликта и уже согласованные независимые изменения сохраняются.
`status` и `conflicts list` остаются успешными чтениями с exit 0 при наличии конфликтов.
Успех `auto enable` и `worker start` подтверждает readiness, а не бесконфликтность данных.

Явные `now` и `status --refresh` имеют отдельный correlation ID. Новый submit
получает `operationId` до запуска компонента; `--request-id` только ждёт прежний
исход, а `request get` читает его без нового обмена. Истёкший budget ожидания
не равен неготовности worker. При process timeout или потере результата acceptance
может быть неизвестен; bounded retention возвращает `unknown`, не успех или отмену.
Этот краткоживущий журнал не заменяет durable changeset, транспортное подтверждение
или первоначальную batch receipt. One-shot по-прежнему ограничен своим request lease.

### Одноразовый запуск и управление worker

CLI передаёт бинарнику через `--request` одноразовый `GitSyncRequest`: `version: 1`,
`action`, `options: { cwd, config?, home?, project? }` и необязательный `input`.
Ответ содержит `version: 1`, `ok` и `data` либо структурированную `error`.
Точная оболочка определена в [ТЗ](GIT-SYNC-IMPLEMENTATION-SPEC.md#одноразовый-протокол-cli--binary).
Этот launcher-запрос не требует идентичности worker до его выбора или создания.
Автономный `relay-git-sync --version` выводит package version для проверки совместимости
бинарника без открытия проекта и запуска worker.

Долгоживущий worker-control протокол отдельно несёт `requestId`,
`expectedInstanceId`/`actualInstanceId`, readiness и версии binary/protocol.
Именно он проверяет отзывчивость и владение конкретного экземпляра процесса.

### Пользовательский автозапуск на трёх ОС

Foreground-вход `relay git-sync supervise` запускает тот же supervisor, что бинарник
`relay-git-sync supervise`. Он пригоден для внешнего supervisor и контейнера.
Native supervisor живёт под пользовательским manager в пределах его login-семантики;
foreground supervisor связан с жизнью запустившей его CLI и её parent lease.
Выход обычного одноразового request не завершает отдельно запущенные supervisor/workers.
Платформенные адаптеры Runtime предоставляют реальные `service enable`, `disable`
и `status`, регистрируя процесс `supervise` приложения Git Sync:

| ОС      | Пользовательский механизм                                                | Граница гарантии запуска                                                                                                 |
| ------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| Linux   | `systemd --user`, user-unit с `ExecStart` для `relay-git-sync supervise` | Обычно пользовательская login-сессия; запуск до login и продолжение после logout требуют отдельно настроенного linger    |
| macOS   | `launchd`, LaunchAgent текущего пользователя                             | Пользовательский login-сеанс; LaunchAgent не объявляется системным boot daemon                                           |
| Windows | Task Scheduler текущего пользователя, задача с logon trigger             | Вход выбранного пользователя; запуск до входа требует отдельного режима учётных данных и не обещается обычным logon task |

Артефакт платформы устанавливается только явной командой пользователя. Установка
бинарника, обычная предметная команда и `auto enable` не должны скрыто включать
пользовательскую службу. Скрытых `sudo`, изменения linger или запроса административного
режима нет. Отключение службы убирает только принадлежащие Relay регистрацию и процессы.
Отсутствие supervisor не устраняется скрытым `systemd-run`, динамической задачей
Task Scheduler или иной автоматической регистрацией за спиной пользователя.

Пути с пробелами и Unicode проходят через корректное кодирование unit/plist/XML
и точный массив аргументов, а не конкатенацию shell-строки. Readiness и идентичность
экземпляра одинаковы для всех ОС. Механизм владения процессами зависит от ОС:
Linux использует subreaper и собственную process group, Windows — Job Object
с kill-on-close, macOS — managed foreground-профиль транспорта и собственную
process group с живым якорем. Нормальное завершение короткого CLI-request не останавливает
worker отдельно запущенного supervisor; потеря lease foreground-родителя или авария worker запускает
уборку принадлежащей ему работы в поддерживаемой native-границе.

На macOS обычные Git/SSH и helpers, сохраняющие PGID, входят в эту гарантию,
включая потомков с закрытыми stdio и после выхода непосредственного Git.
Сам по себе fork, повторный fork или закрытие потоков не меняет группу.
Произвольные custom helpers, которые выполняют `setsid`/`setpgid`, double-fork
со сменой сессии или запускают внешнюю службу, не входят в доказанную гарантию
такой уборки. Public unprivileged API macOS не предоставляет непокидаемый аналог
Job Object: launchd очищает тот же PGID, устаревший `NOTE_TRACK` не даёт поддерживаемого
отслеживания дерева, а `coalition_terminate` не завершает участников. Process group
не является атомарным fork-barrier и не обещает остановить любые конкурентно
порождаемые процессы. Контракт macOS ограничен поддерживаемым foreground-профилем.

Профиль принадлежит Git-транспорту приложения. Каждый локальный вызов Git получает
`gc.autoDetach=false` и `maintenance.autoDetach=false`, чтобы автоматическое
обслуживание не уходило в отдельный daemon. Стандартный OpenSSH запускается без
`-f`, с `ForkAfterAuthentication=no` и `ControlPersist=no`, сохраняя пользовательскую
конфигурацию аутентификации. Произвольная SSH-обёртка или credential helper
не считается foreground-совместимой только по имени исполняемого файла.
Уже работающие внешний ssh-agent, SSH master и Keychain не являются принадлежащими
Relay потомками и не завершаются при уборке.

При разработке службы на хосте не устанавливаются. Генерация unit/plist/XML,
аргументы системных утилит и логика адаптеров проверяются в fixtures. Нативная
приёмка Linux, macOS и Windows проверяет потерю foreground-parent lease и принудительное
завершение worker в достижимой границе каждой ОС. Нативные macOS/Windows-проверки
обязательны в CI; Linux-прогон генератора, fake или POSIX-группового примитива
не считается нативным Windows/macOS-прогоном.

## 11. Подключение, восстановление и границы отказов

`connect` связывает существующую локальную реплику с общей веткой. Проверяются
`projectId`, формат и совместимость истории. Совпадение URL или имени каталога
не заменяет идентичность проекта. Существующее локальное состояние не затирается
удалённым снимком: непереданные эффекты участвуют в согласовании.
Первое `connect` выполняет fetch/validation без push и применения remote-снимка
к рабочей SQLite; первую публикацию либо обмен выполняет `now`. Имя remote вроде
`origin` разрешается в URL относительно кодового cwd при настройке подключения.
Транспорт использует отдельный bare-репозиторий рядом с физической БД; общая ветка
данных имеет самостоятельную историю, а файл SQLite в Git не попадает.

Восстановление после утраты БД строит новую подготовительную SQLite из конкретного
канонического Git-снимка, сохраняет ID, версии, адреса, резервы, точные тексты,
комментарии и квитанции. Затем Core проверяет данные, строятся индексы и атомарно
подключается готовая база. Отсутствующая БД обозначается как требующая восстановления,
а не как готовый пустой проект.
`restore --remote origin` не требует предварительного `connect`, если origin доступен
в кодовом checkout. Для действительно пустого каталога используется URL или путь
remote. Подробный пользовательский маршрут имеет один источник —
[руководство CLI](docs/CLI.md#git-синхронизация).

### Возобновление сохранённой публикации

Если публикация локальной БД прервалась, рабочая БД, staging и намерение публикации
сохраняются вместе с поздними commits и outbox. Обычный повтор restore не удаляет
эти файлы и не запускает materializer заново: он возвращает `RESTORE_RECOVERY_REQUIRED`.
Совпадающий inode и отсутствие WAL не доказывают, что после публикации не было записей.

Явное resume подключает **фактически сохранённый локальный проект**. Это завершение
привязки БД и конфига, а не создание реплики из нового remote snapshot. Runtime API
`resumeProjectRestoration(options, projectId, validateDatabase)` выбирает постоянный
ID из существующего выбранного конфига либо отдельного явного аргумента; home
не сканируется. Имя проекта в workspace не заменяет постоянный ID.

Runtime проверяет исходное владение публикацией, schema/applicationId/projectId
и вызывает строго синхронный read-only validator Core. Validator возвращает
`undefined`, закрывает соединения и не выполняет bootstrap, мутации или отложенные
записи. При существующем рабочем пути читается именно он, включая живой WAL.
Отсутствующий рабочий путь можно связать со staging только при доказанной идентичности,
отсутствии журналов и открытых соединений под дополнительными именами. Чужие файлы,
неизвестные hardlink-алиасы и сомнительное владение означают отказ с сохранением данных.

Ветка resume приложения выполняется до `savedConnection`, fetch, импорта Git-объектов,
ack и записи progress. Supervisor для неё не нужен. Результат содержит `resumed: true`,
`preservedExisting: true` и `sourceCheckpoint: null`: неизвестный Git HEAD не заменяется
свежим fetched HEAD. Последующие `connect`/`now` остаются явными отдельными действиями.

`recovery: null` означает завершённую уборку доказанных private-материалов. Если привязка
успешна, но cleanup не завершён, `recovery` сохраняет пути и исходную причину отказа;
это отличается от отказа владения чужой БД, который нельзя представить как warning.
После полной cleanup повтор возвращает `RESTORE_NOT_PENDING` (exit 3) без validator
и записи. Пока целые recovery-материалы остались, повторная проверка допустима.

Локальный intent имеет версию 2 с проверяемой физической идентичностью БД и связью
маркеров. Старый reader v1 должен отклонить его до прежнего разрушительного rollback.
Ранний intent v1 также сохраняется с отказом нового resume; догадки о его владении
и автоматическая миграция маркера не допускаются.

### Checkpoints и границы потери данных

Checkpoint восстановления фиксирует проверенный remote HEAD, принятые подтверждения
и границу воспроизведения. Replay означает применение сохранённых эффектов или
проверенных переходов Git-снимков, а не повтор пользовательских команд. Dedup
защищает комментарии, создание сущностей, квитанции и назначения ключей.

После crash между push и локальным ack worker сначала проверяет origin. После crash
до push он продолжает сохранённую подготовку либо пересчитывает её на новом HEAD.
После crash локального commit SQLite сохраняет либо всю операцию с changeset,
либо ничего. Потеря только локальных, ещё не экспортированных данных не исправляется
чтением origin; для них нужна согласованная резервная копия SQLite с outbox.

Независимая копия, восстановленная из Git, получает новую идентичность реплики для новых
записей. Сохранённые changeset старой реплики остаются с прежними ID. Это предотвращает
выдачу одинаковых новых событий двумя одновременно работающими копиями backup.
Resume незавершённой публикации сохраняет прежний `replicaId` и уже записанный outbox;
его результат не является новым Git-checkpoint или подтверждением доставки.

## 12. Пригодность к будущему PostgreSQL и API

Git применяется к локальным репликам. Будущий сервер с PostgreSQL получает те же
предметные команды через API; SQL-база сервера не обязана участвовать в Git-публикации.
Общими остаются IDs, связи, переносимые версии, резервы ключей, точные сохранённые
данные, атомарность и квитанции идемпотентности.

Граница I/O проектируется асинхронной, а чистые предметные правила остаются синхронными:

```text
load context → calculate effects → atomic commit(expected versions + predicates)
```

`load context` читает необходимые записи и предикаты одного согласованного контекста.
`calculate` не обращается к сети или БД. `atomic commit` проверяет исходные версии
и значимые предикаты: например, что за время расчёта не появилось запрещённое второе
включение задачи. Одних CAS изменяемых строк недостаточно против write skew.

SQLite-адаптер использует короткие строго синхронные транзакции `bun:sqlite`.
Нельзя передать Promise в существующий callback и считать это поддержкой PostgreSQL.
Будущий PostgreSQL-адаптер реализует собственные асинхронные чтения и транзакции
с эквивалентной проверкой конфликтов. В этот этап входят создание пригодных портов
и проверка их работы на SQLite; реальный PostgreSQL, Server и API пока отложены.
Заглушка не называется готовым адаптером.

Переход на серверное хранение предусматривает consistent snapshot, учёт pending
changeset, проверку Core, согласованный writer cutover и отдельную судьбу offline-реплик.
Смена источника записи не может одновременно оставить независимых Git- и API-писателей
без правила арбитража. Оставшиеся offline-изменения сохраняются и проходят контролируемое
согласование, а не молча теряются при переключении.

## 13. Качество и одобренная последовательность реализации

Обязательная функциональная приёмка охватывает **2–3 независимые реплики одного проекта**.
Командный сценарий на трёх репликах включает двух активных писателей и offline-return
третьего участника. Нужны одинаковые предварительные ключи, независимые и конфликтные
поля, append-only комментарии, атомарный batch, сохранение ID, причинность и отсутствие echo.
Детальные non-FF, потерянный ответ push, поздняя запись и crash/recovery проверяются
у владельцев на двух репликах; их не требуется повторять целиком в каждой командной волне.
Отдельно проверяются несколько проектов/workspace, дедупликация одного worker,
bounded polling, retry+jitter и fairness.

Расширенные сценарии на 50 репликах сохраняют функциональные утверждения и deadlines,
но запускаются только вручную отдельным extended-набором, вне обязательного CI,
`check` и `test:all`. Большое число реплик не является условием изменения архитектуры
или подтверждением производительности 50 одновременно активных пользователей.

Проверки распределяются по [правилам наборов](tests/README.md): чистые алгоритмы —
модульно, SQLite и Git — интеграционно, сигналы и готовность — процессно, законченные
маршруты — через бинарники. Fixtures изолированы от пользовательских проектов и
служб. Нагрузочные замеры выполняются только по явному запросу; без них не заявляются
p95/p99, пропускная способность или превосходство над легаси.

Одобрен порядок:

1. Единый executor и контракты хранения; сохранить локальные сценарии и batch.
2. Durable changeset/outbox и атомарная запись с предметными данными.
3. Переносимые snapshots, версии, адреса и предметное согласование.
4. Ручная синхронизация, restore и полноценные материалы/разрешение конфликтов.
5. Постоянные workers, host supervisor, платформенный автозапуск и CLI управления.
6. Командный сценарий AC-TEAM на трёх репликах и регрессии на всех затронутых границах.

Проверки появляются вместе с соответствующим механизмом; последний этап завершает
сквозную приёмку. Существенный рефакторинг разрешён, если он необходим этим границам.
Готовность каждого этапа определяется работающим кодом и проверяемым поведением,
а не созданием каталога, наличием интерфейса или зелёным пустым test script.
