# Архитектура Relay

Relay — общая рабочая память проекта для людей и AI-агентов: описание продукта,
знания, задачи, планы, предметная история работы и связи между ними.
Изменение кода, выполнение тестов и выпуск программ остаются внешним инструментам.

Документ описывает границы локальной CLI, Core, Storage, Project Runtime и развиваемого
Git Sync. Пользовательские команды приведены в [руководстве CLI](CLI.md).
Подробные нормативные правила обмена находятся в
[ТЗ Git Sync](../GIT-SYNC-IMPLEMENTATION-SPEC.md), обоснование — в
[дизайне](../GIT-SYNC-DESIGN.md). Серверные интерфейсы ниже обозначены как будущие.

## Текущий этап: рабочая CLI

Переносим основной функционал первой версии в локальную CLI. Исходники первой версии
находятся в `/home/gromov/projects/my/relay` (`../../../my/relay` относительно `docs/`).
Её сценарии, предметные правила и известные проблемы служат основой переноса;
старые Node.js/pnpm, JSON-хранилище и границы реализации не требуется воспроизводить.

Технологическая основа — **Bun + TypeScript + Turborepo**. Bun используется как runtime,
менеджер зависимостей, тестовый runner и инструмент сборки самостоятельных бинарников.
Turborepo организует задачи монорепозитория и их зависимости.

Единственный пользовательский интерфейс текущего этапа — команда `relay` для людей
и агентов. Локальные операции не требуют HTTP-сервера, браузера, MCP или доступного
Git origin. Workspace обслуживается CLI локально: реестр выбирает независимую базу
проекта. `relay git-sync` управляет отдельным компонентом обмена локальных реплик,
workers и supervisor. Компоненты и их переносимые контракты продолжают развиваться
по ТЗ синхронизации. Server, Web, MCP, `rest-sdk`, PostgreSQL, установщик и перенос
старых данных относятся к следующим этапам.

## Компоненты и ответственность

### Основа CLI

- **[`apps/cli` → `relay`](../apps/cli/README.md)** — разбор аргументов, выбор проекта, вызов предметных
  сценариев, представление результатов и ошибок, диагностика.
- **[`packages/contracts`](../packages/contracts/README.md)** — переносимые схемы команд, результатов,
  ошибок, command port, snapshots и процессных протоколов.
  Не зависит от Core, Bun, БД или React.
- **[`packages/core`](../packages/core/README.md)** — предметные сценарии и инварианты, разрешение ссылок,
  единый async-исполнитель изменений, локальные чтения и предметная репликация. Это библиотека,
  включаемая в бинарник, а не отдельный сервер.
- **[`packages/storage`](../packages/storage/README.md)** — локальная БД, запросы, репозитории, транзакции,
  нормализованные записи, версии, durable outbox, индексы и технические миграции схемы.
- **[`packages/project-runtime`](../packages/project-runtime/README.md)** — локальные пути, настройки, реестр проектов
  и привязки рабочих каталогов, launcher/lifecycle процессов и native registration
  пользовательских служб. Формы обмена процессами принадлежат Contracts, Git — приложению.
- **[`packages/typescript-config`](../packages/typescript-config/README.md)** — общие профили TypeScript для библиотек,
  Bun и будущего браузерного приложения.

### Устройство CLI

CLI использует Gunshi для описания и разбора команд, справки и локализации. Приложение
управляет потоками вывода и завершением процесса; каждый вызов получает собственную
конфигурацию и плагины. Предметные обработчики вызывают Core, а открытие БД выполняется
при запуске сценария. Справка и версия работают без проекта.

`Invocation` лениво принимает от Project Runtime `openProject` расположение и одно
проверенное рабочее соединение. Свойства `location` и `db` разделяют этот результат;
реестр ожидает Promise предметного writer и закрывает соединение в `finally`
после его успеха или отказа. Внешняя SQLite-транзакция вокруг async writer не создаётся;
обычные составные чтения сохраняют синхронные snapshots. Чтение и разбор источника `batch`,
а также проверка размера адресного набора `get` завершаются до выбора и открытия
проекта. Локальный `config get` использует `resolveProject`,
который самостоятельно закрывает проверочное соединение.

Процессные действия Git Sync используют `LocalInvocation` без открытия проектной БД
в CLI. Контекст, JSON решения и параметры выбора передаются через Runtime. Адресные
guards `--expected-addresses` декодируются без подстановки свежих ID; их предметная
проверка и разрешение scope планирования выполняются внутри command loader Core.
Версионные флаги `--expected-version`/`--target-version` передаются вместе с заданными
числовыми CAS, без создания фиктивной ревизии. `get --with-versions` ожидает
`QueryService.getManyVersioned` через отдельную async read-границу; его metadata
помещается в `meta.versions`, сохраняя прежнюю проекцию `data`. Этот Promise
не оборачивается SQLite callback-транзакцией. Без флага используется прежний `getMany`.

В `apps/cli/src` код сгруппирован по ответственности:

- `main.ts` — единственный файл в корне исходников: подключает процессные потоки
  и вызывает `runProcessCli` из `app/process-run.ts`;
- `app/` собирает программу и управляет одним запуском; `execution/` содержит реестр,
  контекст вызова, окружение, ленивое соединение и границы транзакции либо снимка;
- `input/`, `output/`, `pagination/` и `errors/` отвечают за общие источники ввода,
  представление, курсоры и ошибки CLI;
- `commands/{project,knowledge,tasks,planning,history,queries,batch,git-sync}/register.ts` регистрируют
  предметные группы; их локальные преобразования и типы располагаются рядом;
- `locales/commands/<область>.ts` хранит тексты групп, остальные словари находятся
  непосредственно в `locales/`, а `locales/ru.ts` содержит ресурсы Gunshi.

`app/program.ts` связывает группы с реестром. Общая инфраструктура не импортирует
конкретные команды; ввод, вывод, пагинация и ошибки не открывают проектную БД.
Модули импортируют владельцев функций и `*.types.ts` напрямую. Модульные тесты
располагаются рядом с проверяемой ответственностью; пустые модули и промежуточные
`index.ts` для симметрии каталогов не требуются.

Группы и действия регистрируют краткое описание, предметные пояснения и копируемые
примеры из `locales/commands/`. Общий renderer в `output/help.ts` дополняет справку
Gunshi; синтаксис и значения параметров берутся из схем парсера. Многострочные значения
в примерах сохраняются без добавления отступов внутри shell-кавычек.

Дерево `batch help` отражает доступный каталог предметных операций. Общая справка
и промежуточные группы дают навигацию; полный JSON-контракт выбранного действия
формируется лениво. Описания и перечисления полей переиспользуются из схем предметных
команд, а различия пакетного JSON, обязательность, пропуск и `null` описываются явно.
Эти метаданные служат справке; проверка и исполнение изменений принадлежат Core.

Регистрация действия может явно выбрать текстовый макет через `presentation`.
Чистые функции `output/` оформляют конфигурацию, страницы комментариев, дерево сессий,
workspace и обзор из уже полученного результата. Метка макета не входит в `data`/`meta`
и не сериализуется в JSON. Общая обработка терминального текста и продолжений страниц
остаётся единой; оформление не открывает БД и не делает дополнительных запросов.
`app/validation-errors.ts` адаптирует представление ошибок Gunshi, сохраняя исходную
валидацию, argv и приоритеты help/version.

Процессный вход подключает официальный плагин Gunshi для shell completion, который
пишет кандидатов через `console.log`. В `main.ts` этот вывод однократно привязывается
к контролируемому `process.stdout`, чтобы ошибки записи сохраняли диагностику и код выхода.
Изолированный `runCli` обслуживает обычные команды
с переданными потоками; оба входа используют общий запуск и обработку ошибок в `app/run.ts`.
`app/completion*` содержит адаптацию служебной команды, значения enum из схем и Bash-транспорт
с точной передачей слов без `eval`. Схемы обходятся только по запросу подсказок;
предметные обработчики, stdin и проектная БД при этом не используются.

### Устройство Core

В `packages/core/src` публичный API собирается только в корневом `index.ts`.
Каталоги `knowledge/`, `tasks/`, `planning/` и `history/` владеют предметными
сценариями, декодерами, правилами и локальными типами; сообщения и unit-тесты
располагаются рядом. Разделы документов относятся к знаниям.

`entities/` — нижний общий слой адресации, JSON-проверки, CAS, записи и пагинации.
`projections/entity-reader.ts` собирает декодеры разных видов и индекс разделов
в рамках снимка вызывающей операции. `queries/` связывает эти чтения с общим
адресным набором, поиском, обзором, техническим status и диагностикой doctor.
Краткое адресное чтение декодирует узкую SQL-проекцию без полных тел и журналов.

`CommandExecutor` в `batch/` — общий исполнитель одиночных команд и batch.
Точечные writers `KnowledgeService`, `TasksService`, `PlanningService` и `HistoryService`
возвращают Promise и делегируют ему. Каталог действий вызывает явные async loaders
и чистые предметные calculators; обратного вызова старого write-сервиса из batch нет.
`commands/` собирает согласованный контекст, промежуточные эффекты шагов и один план
guarded commit. Локальные ссылки адресуют предыдущие результаты; квитанция и outbox
сохраняются атомарно с изменениями. `check` проходит тот же commit-путь с откатом.

Граница I/O записи — `CommandStore.load/commit`, доступная у SQLite как `db.commands`.
Подготовка проверяет прочитанные версии и положительные/отрицательные предикаты;
commit защищает эти наблюдения от конкурентной записи. Предметные расчёты не делают
скрытых SQL-запросов. Обычные `get/list`, проекции, `QueryService.getMany` и чтение receipt
остаются явно локальными и синхронными через `ProjectStore`. Отдельный async
`QueryService.getManyVersioned` возвращает пользовательскую full/summary-проекцию,
поколение и metadata версий одного anchor; смена контекста отклоняет весь вызов.
Отдельное async-чтение `readVersionedEntity`/`CommandExecutor.readVersioned` возвращает
сохранённый агрегат с `recordVersion` и `aggregateVersion`; последнее значение служит
`NamedCommand.expectedVersion` и не подменяет локальный `ifRevision`.

`replication/` проверяет переносимые snapshots, подготовленные переходы, подтверждения
и решения конфликтов. `ReplicationService` использует отдельный синхронный локальный
`ReplicationStore`; сеть и процессы остаются за границей Core. Наличие async command port
не означает, что все локальные чтения или репликационный API стали сетевыми.

Зависимости выражены прямыми импортами: планирование использует чтения и общий
прогресс задач, задачи декодируют свои продуктовые цели у владельца знаний,
история и общие запросы используют проекции. Цепочка `history/history-reader.ts`
→ `projections/entity-reader.ts` → `history/history-data.ts` не образует файлового
цикла: нижний декодер истории не зависит от её читателя и сценариев. Аналогично
декодеры остальных областей и чистые правила разделов не импортируют оркестраторы.
Внутренние модули обращаются к конкретным владельцам, сохраняя единственный
публичный вход без дополнительных фасадов и промежуточных barrels.

### Устройство общих библиотек

В Contracts типы, перечисления и чистые проверки сгруппированы по предметным
семействам. Базовые `entities/` не зависят от агрегирующего `project-entity.types.ts`,
который объединяет проверенные записи всех видов. Общие правила автора, канонического
имени проекта и slug используются вызывающими компонентами; выбор контекста и
диагностики остаётся на их границах.

В Storage `database/` владеет соединением, файлом проекта и транзакционными границами,
`entities/` — SQL-операциями над записями, `sqlite/` — схемой и общими механизмами
драйвера. `commands/` реализует `CommandStore`: асинхронная внешняя форма не меняет
синхронность короткого callback `bun:sqlite`. Нормализованные части сохраняют собственные
ID, версии, снятия и позиции; чтение собирает привычные карточки агрегатов.
Репликационное хранение сохраняет outbox, проверяемые переходы и локальные checkpoints.
Самостоятельный `local-lock/` использует SQLite для межпроцессного mutex.
Нижние механизмы не импортируют фасад проектной базы.

В Project Runtime `project/` отвечает за создание и выбор проекта, `workspace/` —
за операции реестра. Общая `configuration/` владеет форматом конфигов, регистрациями,
путями и атомарной публикацией JSON; она не зависит от сценариев изменения workspace.
Единый внутренний выбор конфигурации обслуживает `openProject` и `resolveProject`.
Первый открывает и проверяет базу один раз, передавая `{ location, database }` вызывающему
с обязанностью закрытия; второй возвращает расположение и закрывает проверочное соединение.
Проверка проекта при регистрации workspace также закрывает своё проверочное соединение.
При несовместимости или несовпадении ID новое соединение освобождается до отказа.
Runtime также обнаруживает совместимый бинарник Git Sync, передаёт одноразовый
`GitSyncRequest`, проверяет health постоянного процесса и управляет native service
registration. Общие механизмы запуска и владения процессами не выполняют Git-команды.
Restore публикует подготовленную БД и привязку эксклюзивно. После сохранения намерения
публикации отказ сохраняет рабочую БД, staging и intent, включая поздние записи;
опубликованная БД не откатывается удалением даже при совпадающем inode.
У каждого пакета один публичный `src/index.ts`; внутренние импорты обращаются к
модулям-владельцам напрямую. Типы и словари располагаются рядом со своей областью.

### Синхронизация и последующие интерфейсы

- **[`apps/git-sync` → `relay-git-sync`](../apps/git-sync/README.md)** — отдельный компонент Git-обмена, подготовки
  объединения, конфликтов и доставки изменений; владеет worker, supervisor и Git-транспортом.
  Пользователь управляет им через `relay git-sync`, без отдельного Server.
- **`apps/server` → `relay-server`** — будущие REST API, SSE, обслуживание нескольких
  проектов и раздача Web. HTTP-реализация принадлежит приложению; отдельный
  `server-runtime` в согласованную структуру не входит.
- **`apps/web`** — будущий интерфейс человека, поставляемый как статические ресурсы
  вместе с Server.
- **[`packages/rest-sdk`](../packages/rest-sdk/README.md)** — заготовка общего HTTP-клиента для Web и будущего удалённого
  режима CLI. Планируется генерация из API; локальный путь CLI проходит прямо в Core.
- **MCP** — отложенный интерфейс; его размещение, транспорт и состав команд не определены.

Приложения не импортируют исходники друг друга. Все предметные изменения CLI,
будущих Server и Git Sync проходят через Core. Git-транспорт принадлежит Git Sync,
а не `project-runtime`. Дополнительные воркеры выделяются только при появлении
конкретной ответственности и необходимости отдельного процесса.

## Путь локальной команды

```text
Пользователь / агент
        │
        ▼
   CLI (relay) ───→ Project Runtime: выбор и локальный контекст проекта
        │
        ▼
       Core: сценарии, ссылки и инварианты
        │
        ▼
     Storage: запросы и транзакции
        │
        ▼
   SQLite выбранного проекта

Contracts: общие схемы команд, результатов, ошибок и событий
```

Поток предметной записи:

1. CLI разбирает ввод и через Project Runtime получает выбранный проект с единственным
   открытым соединением, совместимость и постоянный ID которого уже проверены.
2. Async executor через command port загружает согласованный контекст, разрешает
   пользовательские ссылки и проверяет исходные guards. Чистые правила рассчитывают
   последовательность эффектов, включая неявные изменения.
3. SQLite-адаптер одной короткой транзакцией проверяет версии/предикаты и сохраняет
   эффекты, первоначальную receipt и changeset. Отказ откатывает весь пакет.
4. CLI ожидает результат, представляет его и закрывает соединение. Успех локальной
   записи не зависит от публикации в origin.

`execute(command)` использует `executeCommands([command])`; batch передаёт несколько
команд тому же каталогу. Неявное создание доски приложения и составные изменения
входят в одну транзакцию. Явный batch сохраняет ключ, запрос с автором и первоначальный
результат: replay возвращает квитанцию до новых адресных/CAS проверок.
Обычный readonly-путь использует локальный синхронный snapshot вместо command executor.
Пользовательский контракт описан в [руководстве CLI](CLI.md#применить-связанный-пакет).

## Локальное хранение и конкурентность

Принято: **каждый проект имеет отдельную локальную SQLite-базу в режиме WAL через
`bun:sqlite`**. Предметные данные, индексы и поколения изменений принадлежат этой БД.
При работе с 10+ проектами на одном ПК у каждого свои WAL и блокировка записи.
Схема версионируется, производительность требует измерений.

Project Runtime разрешает выбранный проект в путь к его БД. `relay.config.json` в корне проекта
содержит постоянный ID проекта. Стандартный путь SQLite при создании и выборе —
`RELAY_HOME/projects/<id>/project.sqlite` (корень по умолчанию — `~/.relay`);
необязательный `databasePath` в конфиге переопределяет его. Инициализация сохраняет
только `version` и `projectId`; разрешение базы едино для прямого выбора и workspace.
`relay.workspace.json` хранит имена регистраций и пути каталогов локальных проектов;
в каждом каталоге обязателен собственный `relay.config.json`. Без явного конфига
проверяется только текущий каталог запуска. Чтение workspace и выбор его проекта
выполняются в процессе CLI. Совместное использование базы
разными Git-клонами/worktree автоматически пока не определяется.

У участников команды независимые локальные данные. На одном хосте несколько
бинарников могут открывать свои соединения к БД одного проекта. WAL позволяет
параллельное чтение и запись, но активный писатель для файла только один. Разные
проекты не конкурируют за одну SQLite-блокировку, хотя используют общие CPU, память
и диск. Транзакции и атомарные пакеты ограничены БД выбранного проекта.

Границы конкурентности:

- короткие транзакции и адресные изменения с проверкой исходных ревизий и предикатов;
- Git, сеть и тяжёлая подготовка объединения вне транзакции записи;
- атомарное сохранение конкретных эффектов, квитанции и changeset для последующего обмена;
- проверка поколения и transport-state перед применением подготовленного объединения,
  включая receipt-only изменения, не меняющие поколение предметных карточек.

Рабочие файлы SQLite, WAL, SQL-индексы и локальные привязки каталогов не входят
в Git-обмен. Локальная числовая CAS-ревизия и переносимая версия различаются;
исторические ревизии в неизменяемой квитанции остаются частью её результата.
Будущий PostgreSQL-адаптер должен реализовать ту же семантику command port
с собственным асинхронным I/O. Его реализации и серверного API пока нет.

## Git-обмен и идентичность сущностей

Командный сценарий использует независимые SQLite-реплики, offline-работу и публикацию
в одну общую Git-ветку. Git Sync — отдельный бинарник согласованного выпуска:

```text
CLI ───→ Core ───→ Storage ───→ SQLite выбранного проекта
          ▲
          │ предметное применение изменений
       Git Sync
          ↕ переносимые текстовые данные
       Git origin
```

Согласованный протокол использует текущее каноническое состояние по постоянным ID,
отдельные тексты, адреса/резервы, неизменяемые batch receipts и компактные подтверждения.
Экспорт сохраняет данные, а не пользовательские effective-проекции. Changeset содержит
уже выделенные ID и эффекты одной транзакции. Транспорт получает HEAD, выбирает готовые
пакеты, согласует их через Core и публикует коммит поверх HEAD обычным fast-forward push.
Ветки участников и отдельный интегратор не нужны.

Core проверяет не только форму конечного snapshot, но и предметные переходы,
неизменяемость и причинное основание. Конфликтный changeset неделим; зависимые ждут,
независимые продолжают обмен. Новые локальные записи защищены guard поколения/состояния.
При non-fast-forward повторяется подготовка тех же пакетов; при потерянном ответе
проверяются реальная история и ack. Пользовательская мутация не исполняется заново,
force push не используется. Полный контракт формата и восстановления — в ТЗ Git Sync.

Один `now` завершает одно bounded окно. Durable cursor привязан к replicaId и физической
БД, а актуальный pending не выводится из позиции курсора или размера окна. Частичный
prepare сохраняет freshness конфликтов `partial`; конец suffix не означает просмотр
всего оставшегося графа. Полная диагностика различает реальные conflicts и blocked
dependencies с состоянием pending, без фиктивного fingerprint для ожидания.

`validateReplicationHistory(base, target, {chain})` возвращает Core-owned capability
`ValidatedReplicationHistory` и её точный immutable `proof.snapshot`. `prepare`/`accept`
переиспользуют только выданное Core свидетельство для фактической принятой основы;
конструктор, JSON-копия и непроверенный prefix его не заменяют. Применение повторно
проверяет local guard, source proofs и pending. Git parent/acceptance по-прежнему
доказывает приложение, а не этот объект Core.

Решения сохраняются неизменяемо отдельно от original source/receipt и связываются
с publication proofs. Custom v1 адресует изменённые `document.name/summary/body`
конкретной исходной boundary; весь остальной atomic changeset сохраняет обычные
merge/transition правила. Это не универсальный JSON patch по проекту.

Согласованное направление идентичности:

- постоянный ID выдаётся сразу, структурированные связи опираются на него;
- читаемый ключ имеет область действия проекта и предварителен до подтверждения
  назначения в общей ветке данных origin;
- при коллизии ключей первая принятая origin публикация закрепляет номер, другая
  сущность получает следующий свободный предварительный ключ;
- подтверждённые назначения не перенумеровываются при обычной синхронизации,
  удалённые назначения резервируются;
- подтверждение ключа отделено от публикации новых изменений его содержимого;
  потеря ответа push требует проверки origin;
- Core разрешает структурированные адреса в ID; `expectedAddresses: [{ref, expectedId}]`
  сохраняет контекст прочитанной привязки. После известного переназначения ключа
  запись без такого guard отклоняется; постоянный ID остаётся однозначным.

Часы компьютеров и максимум числовой ревизии не определяют победителя.
Произвольные упоминания ключей в Markdown не переписываются при renumber;
контракт устойчивых ID-ссылок задан в ТЗ. Транспортное подтверждение не заменяет
первоначальную пользовательскую квитанцию. Удаление файла из актуального дерева
не удаляет старые версии из Git-истории.

### Процессное управление и автозапуск

CLI передаёт одноразовый JSON через `relay-git-sync --request`; совместимость бинарника
проверяется автономным `--version`. Эта оболочка не требует заранее выбранного worker.
Долгоживущий control-протокол отдельно проверяет экземпляр, физическую идентичность,
выпуск и readiness. Контракты принадлежат Contracts, launcher и native registration —
Runtime, процессы worker/supervisor и Git — приложению Git Sync.

Единица worker — физическая БД, а не регистрация workspace. Supervisor ограничивает
общий бюджет работы и восстанавливает процессы с desired `running`; `stop` сохраняет
desired `stopped`. Только этот долгоживущий supervisor владеет постоянными workers.
`worker start/restart` и `auto enable` обращаются к готовому совместимому supervisor;
при его отсутствии возвращается `SUPERVISOR_REQUIRED` без изменения `mode`/`desired`.
Короткий `--request` остаётся в своём Job/process group, не создаёт постоянных демонов
и не выводит потомков из lifetime-контейнера. `connect`, `restore`, `status` и ручной
`now` не требуют supervisor; при остановленном worker `now` выполняется одноразово под lease.
Статус разделяет живость worker, фазу обмена, Git ahead/behind,
outbox, конфликты, freshness и действительно назначенную следующую попытку.
Неизвестное остаётся `null`; без явного refresh статус не выполняет Git-запросы.

Новый `now`/refresh получает `operationId` в Runtime до spawn. Переданный `requestId`
обозначает только read/wait прежнего исхода; оболочка `GitSyncRequest` v1 не меняется.
`request.get` читает bounded outcome с состоянием queued/running/completed/failed/unknown.
Wait deadline, readiness и потеря достоверного исхода различаются; expiry не означает
отсутствие эффектов. Запросы ожидания не создают новую операцию и не продлевают
lifetime one-shot вопреки его lease.

Пользовательский автозапуск устанавливается только `relay git-sync service enable`:
Linux — `systemd --user`, macOS — LaunchAgent, Windows — Task Scheduler текущего
пользователя. Это login-механизмы; Linux linger и отдельные режимы запуска без login
не включаются скрыто. Первичная настройка фонового обмена начинается с явного
`service enable` для выбранного home либо живого foreground `relay git-sync supervise`,
после чего выполняются `connect` и `auto enable`. Native manager владеет своим supervisor;
foreground supervisor связан с жизнью запустившей CLI. Выход обычного request
не останавливает отдельно запущенные supervisor/workers. Скрытых `systemd-run`
или динамических Task Scheduler задач для обхода этого порядка нет.
Граница уборки — Linux subreaper, Windows Job Object, macOS managed foreground
в собственной process group. Произвольно демонизирующиеся custom helpers на macOS
не объявляются удерживаемыми; process group не даёт atomic fork-barrier. Внешние
agent/master/Keychain не принадлежат запуску. Детали настроек транспорта и нативной
приёмки остаются в [процессном контракте](../GIT-SYNC-IMPLEMENTATION-SPEC.md#12-workers-supervisor-и-process-protocol).

## Восстановление и совместимость

`connect` связывает существующий локальный проект с проверенной общей веткой:
первое подключение выполняет fetch/validation без push/import, а обмен выполняет `now`.
Имя `origin` разрешается относительно cwd при настройке; сохранённый URL используется
в private bare рядом с SQLite. Кодовая ветка не становится веткой данных.
Начало работы с существующей базой и получение независимой реплики описаны в
[едином руководстве подключения](CLI.md#git-синхронизация).

Синхронизация изменяет строки существующей БД выбранного проекта, а не пересоздаёт её
при каждом обмене. После удаления БД восстановление возможно до состояния, сохранённого в Git.
Для изменений, существующих только в SQLite, нужна отдельная согласованная резервная копия.

`restore --remote … --branch …` подготавливает независимую БД, сохраняет предметные
ID, переносимые версии, адреса и квитанции, проверяет результат через Core и публикует
локальную привязку. `restore` не заменяет существующую рабочую БД.
Отсутствующая БД означает необходимость восстановления, а не готовый пустой проект.
После сбоя публикации Runtime возвращает `RESTORE_RECOVERY_REQUIRED`. Обычный повтор
с прежним intent отклоняется до materializer, без удаления данных, повторного bootstrap
или выдачи старой БД за новый fetched snapshot.

Явный `restore --resume [--project-id ID]` вызывает
`resumeProjectRestoration(options, projectId, validateDatabase)` до `savedConnection`,
fetch, импорта Git-объектов и записи accepted/progress. ID выбирается из существующего
конфига либо отдельного аргумента без home scan; `--project` остаётся именем workspace-регистрации.
Runtime проверяет владение, schema/applicationId/projectId и выполняет строго синхронный
read-only validator Core, который закрывает соединения и не делает bootstrap или запись.
Resume сохраняет БД, `replicaId` и поздний outbox; `sourceCheckpoint: null` означает,
что Git HEAD не установлен этой операцией. Это завершение локальной привязки без supervisor,
а не новый Git-checkpoint или подтверждение доставки.

Intent v2 защищает новую публикацию от прежнего rollback reader v1; legacy intent,
чужой target и сомнительная идентичность отклоняются с сохранением материалов.
Неполная private cleanup отражается отдельным `recovery` после успешной привязки,
а повтор после полной уборки даёт `RESTORE_NOT_PENDING`, exit 3. Ошибка владения БД
не подменяется cleanup warning. Детали публичного маршрута — в
[руководстве resume](CLI.md#завершить-прерванную-локальную-публикацию).

Версия приложения, SQL-схемы, переносимого формата и process protocol — разные уровни.
Техническая миграция SQLite сохраняет данные существующей новой версии; перенос
JSON-хранилища первой реализации и переход на PostgreSQL/API — отдельные будущие сценарии.

## Расширение после CLI

При добавлении Server и Web предметные сценарии остаются в Core:

```text
Локальный CLI ──────────────────────────────→ Core → Storage
                                               ▲
Web / удалённый CLI → REST SDK → Server / REST ──┤
                                               │
Git Sync ──────────────────────────────────────┘

Server ── SSE ──→ Web
```

Relay устанавливается в среду пользователя; основной вход — `relay` в PATH.
CLI, Server и фоновые сервисы поставляются отдельными бинарниками согласованного
выпуска. Установка и обновление — отдельные операции, механизм которых ещё не выбран.

Локальный process protocol Git Sync не является REST API продукта. Серверный стек,
точные REST/SSE-контракты и архитектура MCP определяются на следующих этапах.
Для будущего PostgreSQL сохраняются команды, переносимые ID/версии, атомарность
и receipts; переход требует consistent snapshot, учёта pending и явного writer cutover.

## Проверка архитектуры

Организация наборов описана в [tests/README.md](../tests/README.md): модульные проверки
правил, интеграционные проверки реальных изолированных БД и Git, процессные проверки
бинарников и сквозные сценарии CLI. API/Web-сценарии появятся вместе с этими интерфейсами.
Правила качества и карта проверяемых сценариев находятся в
[материалах для разработки](development/README.md).

Обязательная приёмка обмена строится на 2–3 независимых репликах. Штатный командный
сценарий соединяет два активных писателя и третью реплику, возвращающуюся после offline,
с собственными SQLite/Git и общим origin. Проверяются конкретные значения, ID, ссылки,
квитанции, коллизии ключей, конфликты и причинность. Подробные варианты non-FF,
потерянного ответа, поздней записи, crash/recovery, атомарности и отсутствия echo
остаются у владельцев правил и могут проверяться на двух репликах.
Расширенные 50-репличные сценарии запускаются отдельно вручную по
[правилам extended-набора](../tests/README.md#расширенная-проверка-репликации), без SLA.
Ссылки на смысловые проверки содержит
[карта сценариев](development/TEST-COVERAGE.md); наличие набора не заменяет его выполнение
на согласованном состоянии кода.

Нативная матрица [CI](../.github/workflows/ci.yml) включает Linux, macOS и Windows.
Проверки генерации unit/plist/XML и Linux-fakes не подтверждают native lifecycle другой ОС.

Отдельно проверяется работа с 10+ проектами на одном ПК: изоляция данных и конкурентная
запись в разные SQLite-базы, суммарное потребление ресурсов и задержки команд.

Производительность измеряется только вручную по запросу, вне CI и штатных проверок:
запуск бинарника, p95/p99 операций, ожидание записи, память, рост WAL и восстановление
разных объёмов данных.
При добавлении Server проверяется его отзывчивость во время синхронизации.
Целевые SLA и превосходство над первой версией пока не установлены.
Организация измерений описана в [benchmarks/README.md](../benchmarks/README.md).
