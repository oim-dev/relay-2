# Архитектура Relay

Relay — общая рабочая память проекта для людей и AI-агентов: описание продукта,
знания, задачи, планы, предметная история работы и связи между ними.
Изменение кода, выполнение тестов и выпуск программ остаются внешним инструментам.

Документ описывает примерную архитектуру рефакторинга. Источник принятых решений
и открытых вопросов — [PROJECT.md](../PROJECT.md). Ниже целевое устройство не означает
наличия реализации: сейчас приложения и библиотеки являются заглушками.

## Текущий этап: рабочая CLI

Переносим основной функционал первой версии в локальную CLI. Исходники первой версии
находятся в `/home/gromov/projects/my/relay` (`../../relay` относительно `docs/`).
Её сценарии, предметные правила и известные проблемы служат основой переноса;
старые Node.js/pnpm, JSON-хранилище и границы реализации не требуется воспроизводить.
Навигация по исходному проекту приведена в [PROJECT.md](../PROJECT.md#12-откуда-черпаем-знания).

Технологическая основа — **Bun + TypeScript + Turborepo**. Bun используется как runtime,
менеджер зависимостей, тестовый runner и инструмент сборки самостоятельных бинарников.
Turborepo организует задачи монорепозитория и их зависимости.

Единственный пользовательский интерфейс текущего этапа — команда `relay` для людей
и агентов. Локальные операции не требуют HTTP-сервера, браузера, MCP или доступного
Git origin. Server, Web и MCP начинаем добавлять после переноса основного функционала
и появления рабочей CLI. IPC, установщик и миграция старых данных также отложены.

## Компоненты и ответственность

### Основа CLI

- **`apps/cli` → `relay`** — разбор аргументов, выбор проекта, вызов предметных
  сценариев, представление результатов и ошибок, диагностика.
- **`packages/contracts`** — переносимые схемы команд, результатов, ошибок и событий.
  Не зависит от Core, Bun, БД или React.
- **`packages/core`** — предметные сценарии и инварианты, разрешение ссылок,
  согласованное применение изменений и атомарные пакеты операций. Это библиотека,
  включаемая в бинарник, а не отдельный сервер.
- **`packages/storage`** — локальная БД, запросы, репозитории, транзакции,
  индексы и технические миграции схемы.
- **`packages/project-runtime`** — локальные пути, настройки, реестр проектов
  и привязки рабочих каталогов. Будущий общий локальный протокол относится сюда,
  но его транспорт и интерфейсы ещё не выбраны.
- **`packages/typescript-config`** — общие профили TypeScript для библиотек,
  Bun и будущего браузерного приложения.

### Синхронизация и последующие интерфейсы

- **`apps/sync` → `relay-sync`** — отдельный компонент Git-обмена, подготовки
  объединения, обработки конфликтов и доставки изменений. Заготовка уже есть;
  реализация определяется задачами переноса.
- **`apps/server` → `relay-server`** — будущие REST API, SSE, обслуживание нескольких
  проектов и раздача Web. HTTP-реализация принадлежит приложению; отдельный
  `server-runtime` в согласованную структуру не входит.
- **`apps/web`** — будущий интерфейс человека, поставляемый как статические ресурсы
  вместе с Server.
- **`packages/rest-sdk`** — заготовка общего HTTP-клиента для Web и будущего удалённого
  режима CLI. Планируется генерация из API; локальный путь CLI проходит прямо в Core.
- **MCP** — отложенный интерфейс; его размещение, транспорт и состав команд не определены.

Приложения не импортируют исходники друг друга. Все предметные изменения CLI,
будущих Server и Sync проходят через Core. Git-транспорт принадлежит Sync,
а не `project-runtime`. Дополнительные воркеры выделяются только при появлении
конкретной ответственности и необходимости отдельного процесса.

## Путь локальной команды

```text
Пользователь / агент
        │
        ▼
   CLI (relay) ───→ Project Runtime: выбор и локальный контекст проекта
        │
        ▼
       Core: сценарии, ссылки и инварианты
        │
        ▼
     Storage: запросы и транзакции
        │
        ▼
   локальная БД

Contracts: общие схемы команд, результатов, ошибок и событий
```

Примерный поток выполнения:

1. CLI разбирает ввод и получает локальный контекст проекта через Project Runtime.
2. Core разрешает пользовательские ссылки, проверяет предметные правила и формирует
   согласованное изменение.
3. Storage выполняет чтение или короткую транзакцию записи. Для изменения проверяется
   исходная ревизия; атомарный пакет должен применяться целиком.
4. CLI представляет результат либо ошибку. Успех локальной записи не зависит
   от публикации в origin.

Это распределение ответственности, а не утверждённые сигнатуры API. Конкретные
интерфейсы Core/Storage, контракт атомарных пакетов и гарантии повторной доставки
ещё предстоит определить.

## Локальное хранение и конкурентность

Обсуждаемое направление — **SQLite в режиме WAL через `bun:sqlite`**. Выбор общей
БД пользователя или отдельных БД локальных экземпляров проектов остаётся открытым.
Схема и индексы ещё не реализованы, производительность не подтверждена измерениями.

У участников команды независимые локальные данные. На одном хосте несколько
бинарников могут открывать свои соединения к одному файлу БД. WAL позволяет
параллельное чтение и запись, но активный писатель для файла только один.

Предлагаемый подход:

- короткие транзакции и адресные изменения с проверкой исходных ревизий;
- Git, сеть и тяжёлая подготовка объединения вне транзакции записи;
- атомарное сохранение локальной операции и поколения данных для последующего обмена;
- проверка поколения перед применением подготовленного объединения.

Рабочие файлы SQLite, WAL, SQL-индексы и локальные привязки каталогов не входят
в Git-обмен. Точные границы транзакций и модель ревизий требуют отдельного решения.
Синхронный API `bun:sqlite` нужно учитывать при добавлении серверного процесса.

## Git-обмен и идентичность сущностей

Базовый командный сценарий — 10+ участников с независимыми копиями, offline-работой
и конкурентной публикацией в общий origin. Sync планируется отдельным бинарником
согласованного выпуска:

```text
CLI ───→ Core ───→ Storage ───→ локальная БД
          ▲
          │ предметное применение изменений
         Sync
          ↕ переносимые текстовые данные
       Git origin
```

Предлагаемая модель обмена — детерминированный экспорт текущего состояния с отдельными
записями по постоянным ID и историей Git. Sync получает удалённое состояние и готовит
объединение общего предка, локальной и удалённой версий. Core проверяет итоговые
сущности, связи и инварианты. Если локальное поколение успело измениться, кандидат
пересчитывается, а не затирает новые данные. Повтор после конкурентного отказа push
касается транспорта уже сохранённых изменений, а не повторного выполнения мутации.

Согласованное направление идентичности:

- постоянный ID выдаётся сразу, структурированные связи опираются на него;
- читаемый ключ имеет область действия проекта и предварителен до подтверждения
  назначения в общей ветке данных origin;
- при коллизии ключей первая принятая origin публикация закрепляет номер, другая
  сущность получает следующий свободный предварительный ключ;
- подтверждённые назначения не перенумеровываются при обычной синхронизации,
  удалённые назначения резервируются;
- подтверждение ключа отделено от публикации новых изменений его содержимого;
  потеря ответа push требует проверки origin;
- Core разрешает текстовые ссылки в ID; устаревший ввод требует проверяемой карты
  ключей, чтобы перенумерация не направила запись на другую сущность.

Точный формат файлов, распределённые ревизии, политика конфликтов и синтаксис ссылок
открыты. Часы компьютеров и максимум числовой ревизии не определяют победителя.
Конфликт одного участника не должен блокировать всю команду.

## Восстановление и совместимость

Синхронизация изменяет строки существующей БД, а не пересоздаёт её при каждом обмене.
После удаления БД восстановление возможно до состояния, сохранённого в Git.
Для изменений, существующих только в SQLite, нужна отдельная согласованная резервная копия.

Предлагается импортировать Git-состояние в подготовительную БД, построить индексы,
сохранить ID, ревизии и ключи, проверить результат через Core и затем подключить его.
Отсутствующая БД означает необходимость восстановления, а не готовый пустой проект.

Версия приложения, версия SQL-схемы и версия переносимого формата — разные уровни.
Политики совместимости, резервирования и миграции данных первой версии ещё не выбраны.

## Расширение после CLI

При добавлении Server и Web предметные сценарии остаются в Core:

```text
Локальный CLI ──────────────────────────────→ Core → Storage
                                               ▲
Web / удалённый CLI → REST SDK → Server / REST ──┤
                                               │
Sync ──────────────────────────────────────────┘

Server ── SSE ──→ Web
```

Relay устанавливается в среду пользователя; основной вход — `relay` в PATH.
CLI, Server и фоновые сервисы поставляются отдельными бинарниками согласованного
выпуска. Установка и обновление — отдельные операции, механизм которых ещё не выбран.

Для управления локальными процессами обсуждался IPC через сокет или именованный
канал: готовность, версии, уведомление о работе и остановка. Транспорт, жизненный
цикл и доставка изменений Server не утверждены. Сохранённые поколения данных
предложены для обнаружения пропущенных уведомлений; Web получает события через SSE.
Серверный стек, точные REST/SSE-контракты и архитектура MCP определяются на следующих этапах.

## Проверка архитектуры

Организация наборов описана в [tests/README.md](../tests/README.md): модульные проверки
правил, интеграционные проверки реальных изолированных БД и Git, процессные проверки
бинарников и сквозные сценарии CLI. API/Web-сценарии появятся вместе с этими интерфейсами.

Ключевая будущая проверка обмена — 10+ изолированных экземпляров с общим origin,
конкурентными изменениями, коллизиями ключей, offline и перезапусками. После обмена
и разрешения конфликтов состояния должны сойтись без потери принятых изменений
и целостности ссылок.

Производительность измеряется отдельно: запуск бинарника, p95/p99 операций,
ожидание записи, память, рост WAL и восстановление разных объёмов данных.
При добавлении Server проверяется его отзывчивость во время синхронизации.
Целевые SLA и превосходство над первой версией пока не установлены.
