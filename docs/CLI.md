# Локальная работа через CLI

`relay` — самостоятельный бинарник на Bun. Вложенные команды, параметры и русскую
справку обрабатывает Gunshi. Точный состав параметров доступен через
`relay <команда> --help`; справка и версия работают без выбранного проекта.

## Запуск

Из корня исходников:

```bash
bun install --frozen-lockfile
bun run build:cli
export PATH="$PWD/apps/cli/dist:$PATH"
relay --help
```

Экспорт PATH действует в текущем терминале. Для работы выберите каталог своего проекта.

## Автодополнение

`relay complete <shell>` печатает скрипт подключения для `bash`, `zsh`, `fish` или
`powershell`. Подсказки команд, параметров и значений перечислений берутся из схем CLI:
например, `relay docu<Tab>`, `relay task create --<Tab>` и `relay --format j<Tab>`.
Генерация и запрос подсказок доступны без проекта и открытия его БД.

Для Bash нужен установленный и подключённый `bash-completion`. После установки
команды `relay` один раз выполните:

```bash
mkdir -p ~/.local/share/bash-completion/completions
relay complete bash > ~/.local/share/bash-completion/completions/relay
source ~/.local/share/bash-completion/completions/relay
```

В новых терминалах этот файл подхватывает `bash-completion`. Подключение выполняется
в интерактивной оболочке; `.envrc` отвечает за переменные окружения и `PATH`.
Bash-скрипт запрашивает кандидатов у текущей команды `relay` из `PATH`, поэтому после
обычной пересборки новые команды доступны без повторной генерации скрипта.

Для других оболочек используйте `relay complete zsh`, `relay complete fish` или
`relay complete powershell` и подключите выведенный скрипт средствами своей оболочки.
После переноса бинарника сгенерируйте эти скрипты заново: они содержат путь запуска.
Команда `complete` выводит shell-скрипт или служебный протокол без JSON-обёртки.

## Проект и размещение данных

```bash
relay init --name "Библиотека инструкций" --slug instructions
relay project get
relay config get
```

В рабочем каталоге создаётся `relay.config.json` с полями `version` и `projectId`.
По умолчанию SQLite-база определяется как `RELAY_HOME/projects/<projectId>/project.sqlite`;
если `RELAY_HOME` не задан, используется `~/.relay`. Это правило действует и при создании,
и при последующих запусках. SQLite работает в режиме WAL.

Необязательное поле `databasePath` в конфиге переопределяет стандартное расположение.
Абсолютный путь используется напрямую, относительный разрешается от физического каталога
конфига, включая открытие через символьную ссылку. Пустой или нестроковый путь считается
ошибкой. Без этого поля смена `RELAY_HOME` меняет место поиска базы; саму базу команда
не переносит. `relay config get --format json` возвращает исходный конфиг в `data`
и вычисленный абсолютный путь в `meta.databasePath`.

Обычная команда проверяет только текущий каталог: запускайте Relay из корня проекта
или workspace. Родительские каталоги и `.relay/config.json` автоматически не проверяются.
`--config <path>` выбирает файл явно; `RELAY_CONFIG` позволяет задать путь через окружение.
Чтение отсутствующей базы завершается ошибкой. Повторная инициализация не заменяет
существующий проект. Регистрация и расположение базы отделены от предметного имени
проекта и его постоянного ID.

## Локальный workspace

В каталоге, из которого удобно работать с несколькими проектами:

```bash
relay workspace project init
relay workspace project add backend ../backend
relay workspace project add frontend ../frontend
relay workspace project list
relay project get --project backend
relay document list --project frontend
```

Перед регистрацией проект должен быть инициализирован. Команда `add` принимает каталог
с обязательным `relay.config.json` в его корне. Workspace хранит только имя регистрации
и путь каталога; ID и необязательное переопределение пути базы читаются из конфигурации
выбранного проекта. Стандартное размещение использует `RELAY_HOME` текущего вызова.
Файл `relay.workspace.json` может выглядеть так:

```json
{
  "version": 1,
  "projects": [
    { "name": "backend", "path": "../backend" },
    { "name": "frontend", "path": "../frontend" }
  ]
}
```

Относительные пути каталогов разрешаются от физического каталога workspace-файла,
включая открытие через символьную ссылку. В результате `workspace project list`
возвращаются абсолютные пути `path`. Файл workspace также ищется только в текущем
каталоге, если не задан явный `--config` или `RELAY_CONFIG`.
Для предметной команды в workspace требуется явный `--project`.
Одинаковые ключи сущностей в разных проектах относятся к независимым записям.
`workspace project remove <name>` удаляет регистрацию и сохраняет данные проекта.
Рядом с реестром находится служебный `relay.workspace.json.lock.sqlite`: он
сериализует изменения регистраций между процессами, включая аварийное завершение
одного из них, и не содержит предметных данных проекта.

## Содержание и изменения

```bash
relay document create \
  --name "Правила проверки" \
  --body-file ./rules.md \
  --actor human
relay document get DOC-1
relay task create \
  --board product \
  --title "Проверить сохранение текста" \
  --description "Сохранить документ и сверить полное содержание после повторного запуска." \
  --actor human
```

Ключи в примерах иллюстративны: используйте адрес из результата создания.
Автор задаётся через `--actor` или `RELAY_ACTOR`. Перед изменением прочитайте запись:
`--if-revision` принимает её исходную ревизию. При конфликте перечитайте данные
и согласуйте изменение. CLI не подставляет свежую ревизию и не повторяет мутацию.

У вложенных изменений ревизия принадлежит владельцу: разделы документов — проекту,
участие приложения — приложению, этапы и состав плана — плану, контрольные точки
истории — сессии. Комментарии задачи дописываются независимо: они не требуют
`--if-revision` и не меняют ревизию содержания задачи.

Текстовые параметры поддерживают непосредственный ввод и соответствующий
`--<поле>-file`; путь `-` читает stdin. У одного поля должен быть один источник,
а stdin может использоваться только одним полем команды. Markdown сохраняется
с пустыми строками и значимыми отступами. Полное содержание читается через `get`.

Наборы ссылок задаются повторением параметра, например `--targets FEATURE-1
--targets FEATURE-2`. Для структурированного ввода доступны `--input` и
`--input-file`; пустой набор задаётся явно, например `--input '{"targets":[]}'`.
В командах релиза обозначение выпуска принимает параметр `--release-version`;
`--version` показывает версию самого CLI.

Читаемые ключи являются локальными адресами проекта. Ссылки между записями хранят
постоянные ID; переименование ключа сохраняет прежний адрес как алиас.

## Области команд

| Область              | Команды                                                                             |
| -------------------- | ----------------------------------------------------------------------------------- |
| Проекты              | `init`, `project`, `config`, `workspace project`                                    |
| Знания продукта      | `product`, `feature`, `scenario`, `application`, `implementation`                   |
| Библиотека           | `document`, `document section`                                                      |
| Работа               | `board`, `task`, `task parent`, `task dependency`, `task criterion`, `task comment` |
| Планирование         | `plan`, `plan stage`, `plan stage task`, `release`                                  |
| История работы       | `session`, `checkpoint`                                                             |
| Чтение и диагностика | `search`, `inspect`, `overview`, `storage status`, `doctor check`                   |

Доступные действия каждой группы перечисляет её справка. Доска продукта создаётся
при инициализации, а доска приложения — при создании приложения.
Готовность задач и планов вычисляется с учётом обязательств; сохранённый статус
и фактическая готовность различаются. Выпуск в Relay фиксирует сведения о результате,
а фактическую сборку, проверки и публикацию выполняют внешние инструменты.

## Вывод и продолжение списков

По умолчанию результат — читаемый текст. `--format json` предназначен для скриптов
и отладки. Успешные результаты идут в stdout, ошибки — в stderr. Код `0` означает
успех, `2` — ошибку ввода, `3` — отсутствие искомой записи, `4` — конфликт;
прочие ошибки имеют ненулевой код.

Списки поддерживают `--limit` и `--cursor`. Продолжение относится к конкретному
проекту, запросу и поколению данных. После изменения данных прежний курсор
отклоняется: начните список заново. Страница списка не является полным содержимым
проекта, а краткая карточка не заменяет адресное чтение записи.
