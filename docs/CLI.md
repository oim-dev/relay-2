# Работа через CLI

`relay` — самостоятельный бинарник на Bun. Вложенные команды, параметры и русскую
справку обрабатывает Gunshi. Точный состав параметров доступен через
`relay <команда> --help`; справка и версия работают без выбранного проекта.

## Запуск

Из корня исходников:

```bash
bun install --frozen-lockfile
bun run build:cli
export PATH="$PWD/apps/cli/dist:$PATH"
relay --help
```

Экспорт PATH действует в текущем терминале. Для работы выберите каталог своего проекта.
Корневая команда `build:cli` также собирает `apps/git-sync/dist/relay-git-sync`.
Git Sync использует отдельный компонент того же выпуска: CLI находит его рядом с собой,
в `PATH`, в сборке checkout либо по явному `RELAY_GIT_SYNC_BIN`. Для обмена нужен Git
в `PATH` и доступ к remote; обычные локальные команды работают без них.

## Справка и примеры

```bash
relay --help
relay task
relay task create --help
relay plan stage task transfer --help
```

Корневая справка знакомит с областями работы. Предметная группа без подкоманды показывает
свои действия, пояснения и примеры. `batch` выполняет пакет непосредственно, а
`batch result` читает его квитанцию. Справка действия описывает параметры, результат,
существенные условия и связанные команды. Она доступна через `--help` или `-h`
без настроенного проекта и чтения stdin.

Примеры рассчитаны на POSIX shell, включая Bash и Zsh. Заменяйте условные ключи, ID,
пути и ревизии данными своего проекта. Ревизию берите из прочитанной записи владельца:
он указан в справке изменяющей команды. Обязательные предметные поля могут передаваться
отдельными параметрами либо через `--input`; подробности приводит справка действия.
При ошибке ввода CLI показывает путь к справке распознанной команды;
в JSON он находится в отдельном поле `error.helpCommand`.

## Автодополнение

`relay complete <shell>` печатает скрипт подключения для `bash`, `zsh`, `fish` или
`powershell`. Подсказки команд, параметров и значений перечислений берутся из схем CLI:
например, `relay docu<Tab>`, `relay task create --<Tab>` и `relay --format j<Tab>`.
Генерация и запрос подсказок доступны без проекта и открытия его БД.

Для Bash нужен установленный и подключённый `bash-completion`. После установки
команды `relay` один раз выполните:

```bash
mkdir -p ~/.local/share/bash-completion/completions
relay complete bash > ~/.local/share/bash-completion/completions/relay
source ~/.local/share/bash-completion/completions/relay
```

В новых терминалах этот файл подхватывает `bash-completion`. Подключение выполняется
в интерактивной оболочке; `.envrc` отвечает за переменные окружения и `PATH`.
Bash-скрипт запрашивает кандидатов у текущей команды `relay` из `PATH`, поэтому после
обычной пересборки новые команды доступны без повторной генерации скрипта.

Для других оболочек используйте `relay complete zsh`, `relay complete fish` или
`relay complete powershell` и подключите выведенный скрипт средствами своей оболочки.
После переноса бинарника сгенерируйте эти скрипты заново: они содержат путь запуска.
Команда `complete` выводит shell-скрипт или служебный протокол без JSON-обёртки.

## Проект и размещение данных

```bash
relay init --name "Библиотека инструкций" --slug instructions
relay project get
relay config get
```

В рабочем каталоге создаётся `relay.config.json` с полями `version` и `projectId`.
По умолчанию SQLite-база определяется как `RELAY_HOME/projects/<projectId>/project.sqlite`;
если `RELAY_HOME` не задан, используется `~/.relay`. Это правило действует и при создании,
и при последующих запусках. SQLite работает в режиме WAL.

Начальные записи создаются от `system`; `--actor` для `init` не требуется и не меняет
авторство этих записей.

Явно пустой `RELAY_HOME`, включая строку из пробелов, отклоняется до файловых действий.
Относительный путь разрешается от каталога запуска; отсутствие переменной выбирает
`HOME/.relay`.

Необязательное поле `databasePath` в конфиге переопределяет стандартное расположение.
Абсолютный путь используется напрямую, относительный разрешается от физического каталога
конфига, включая открытие через символьную ссылку. Пустой или нестроковый путь считается
ошибкой. Без этого поля смена `RELAY_HOME` меняет место поиска базы; саму базу команда
не переносит. `relay config get --format json` возвращает исходный конфиг в `data`
и вычисленный абсолютный путь в `meta.databasePath`.

Обычная команда проверяет только текущий каталог: запускайте Relay из корня проекта
или workspace. Родительские каталоги и `.relay/config.json` автоматически не проверяются.
`--config <path>` выбирает файл явно; `RELAY_CONFIG` позволяет задать путь через окружение.
Чтение отсутствующей базы завершается ошибкой. Повторная инициализация не заменяет
существующий проект. Регистрация и расположение базы отделены от предметного имени
проекта и его постоянного ID.

## Локальный workspace

В каталоге, из которого удобно работать с несколькими проектами:

```bash
relay workspace project init
relay workspace project add backend ../backend
relay workspace project add frontend ../frontend
relay workspace project list
relay project get --project backend
relay document list --project frontend
```

Перед регистрацией проект должен быть инициализирован. Команда `add` принимает каталог
с обязательным `relay.config.json` в его корне. Workspace хранит только имя регистрации
и путь каталога; ID и необязательное переопределение пути базы читаются из конфигурации
выбранного проекта. Стандартное размещение использует `RELAY_HOME` текущего вызова.
Файл `relay.workspace.json` может выглядеть так:

```json
{
  "version": 1,
  "projects": [
    { "name": "backend", "path": "../backend" },
    { "name": "frontend", "path": "../frontend" }
  ]
}
```

Относительные пути каталогов разрешаются от физического каталога workspace-файла,
включая открытие через символьную ссылку. В результате `workspace project list`
возвращаются абсолютные пути `path`. Файл workspace также ищется только в текущем
каталоге, если не задан явный `--config` или `RELAY_CONFIG`.
Для предметной команды в workspace требуется явный `--project`.
Одинаковые ключи сущностей в разных проектах относятся к независимым записям.
`workspace project remove <name>` удаляет регистрацию и сохраняет данные проекта.
Рядом с реестром находится служебный `relay.workspace.json.lock.sqlite`: он
сериализует изменения регистраций между процессами, включая аварийное завершение
одного из них, и не содержит предметных данных проекта.

## Содержание и изменения

```bash
relay document create \
  --name "Правила проверки" \
  --body-file ./rules.md \
  --actor human
relay document get DOC-1
relay task create \
  --board product \
  --title "Проверить сохранение текста" \
  --description "Сохранить документ и сверить полное содержание после повторного запуска." \
  --actor human
```

Ключи в примерах иллюстративны: используйте адрес из результата создания.
Автор задаётся через `--actor` или `RELAY_ACTOR`. Перед изменением прочитайте запись:
`--if-revision` принимает исходную локальную ревизию, а `--expected-version` —
переносимый токен изменяемого владельца. Для изменения существующего владельца
требуется хотя бы одно предусловие; можно передать оба, тогда проверяются оба,
включая no-op. Токен получают через [get с версиями](#переносимые-версии).
При конфликте перечитайте данные и согласуйте изменение. CLI не подставляет свежую
ревизию или токен и не повторяет мутацию.

Если вы уже читали адрес по ключу, можно дополнительно передать ожидаемый ID:

```bash
relay document get DOC-1 --format json
relay document update DOC-1 --if-revision 3 --body 'Новая редакция' \
  --expected-addresses '[{"ref":"DOC-1","expectedId":"прочитанный-ID"}]' \
  --actor human
```

Замените `DOC-1`, `3` и `прочитанный-ID` значениями из первого ответа.
`--expected-addresses` принимает JSON-массив объектов с ровно двумя непустыми строками
`ref` и `expectedId`; пустой массив `[]` допустим. Это общий параметр предметных записей
и batch. CLI передаёт привязку дословно, а Core проверяет её внутри исполнения.
Несовпадение даёт `ADDRESS_CHANGED`. После локально известного переназначения
предварительного ключа запись или новая ссылка по нему без guard отклоняется
с `ADDRESS_GUARD_REQUIRED`; можно использовать постоянный ID. Разрешение ключа
в его текущий ID не доказывает, какую сущность имел в виду автор старого ввода.

У вложенных изменений предусловие версии принадлежит владельцу: разделы документов — проекту,
участие приложения — приложению, этапы и состав плана — плану, контрольные точки
истории — сессии. Комментарии задачи дописываются независимо: они не требуют
`--if-revision` и не меняют ревизию содержания задачи.

Текстовые параметры поддерживают непосредственный ввод и соответствующий
`--<поле>-file`; путь `-` читает stdin. У одного поля должен быть один источник,
а stdin может использоваться только одним полем команды. Markdown сохраняется
с пустыми строками и значимыми отступами. Полное содержание читается через `get`.

Текст с начальным дефисом передавайте в одном аргументе `--поле='исходный текст'`,
через `--поле-file` или JSON. Кавычки вокруг отдельного значения сохраняют его текст,
но не отменяют разбор начального дефиса как параметра CLI.

Наборы ссылок задаются повторением параметра, например `--targets FEATURE-1
--targets FEATURE-2`. Для структурированного ввода доступны `--input` и
`--input-file`; пустой набор задаётся явно, например `--input '{"targets":[]}'`.
В командах релиза обозначение выпуска принимает параметр `--release-version`;
`--version` показывает версию самого CLI.

Читаемые ключи являются локальными адресами проекта. Ссылки между записями хранят
постоянные ID; обычное переименование ключа сохраняет прежний адрес как алиас.
При первом обмене предварительный ключ может измениться из-за коллизии с другой
репликой. Первое принятое общей веткой назначение сохраняется; проигравшая сущность
получает свободный ключ с прежним ID. Чужой занятый ключ не становится её алиасом.

## Прочитать рабочий набор

В выбранном проекте передайте от одного до 200 адресов. Ключи в примерах условные:

```bash
relay get DOC-1 TASK-1 PLAN-1
relay get DOC-1 TASK-1 PLAN-1 --summary
relay get DOC-1 TASK-1 PLAN-1 --format json
```

По умолчанию `get` возвращает полное содержание выбранных записей из одного снимка.
Каждый текстовый блок начинается с заголовка, содержащего номер и адрес; блоки
разделены пустой строкой. Markdown не усекается. `--summary` оставляет краткие
карточки с названием, идентичностью, ревизией и сохранённым состоянием, без тел
документов и вложенных составов.
Краткое чтение проверяет выбранные поля; полное предметное содержание проверяется
при обычном `get`.

Порядок и повторения адресов сохраняются. JSON содержит `data.view` (`full` или
`summary`) и `data.items`: успешный элемент содержит исходный `ref`, `ok: true` и
`entity`, ошибочный — `ok: false` и `error`. Одна запись имеет ту же форму списка.
Если часть адресов не найдена или неверна, остальные результаты доступны; общий
код завершения ненулевой, а JSON частичного результата в stdout имеет `ok: false`.
Неожиданная ошибка хранилища завершает весь вызов обычной диагностикой в stderr.

Общее адресное чтение выполняется через `get`; прежняя группа `inspect` удалена.
Предметные команды вроде `document get` сохраняют удобство чтения известного вида.

### Переносимые версии

Флаг `--with-versions` общей команды `get` добавляет версии успешных ID отдельно
от содержания. Он работает для одного или нескольких адресов, включая `--summary`:

```bash
relay get DOC-1 --summary --with-versions --format json
relay document update DOC-1 --body 'Новая редакция' \
  --expected-version 'aggregate-version-from-get' --actor human
```

Подставьте ключ своего документа и значение `meta.versions[ID].aggregateVersion`
из первого ответа; его ID находится в `data.items[0].entity.id`. Токен непрозрачен
и передаётся дословно. `recordVersion` описывает первичную запись, а `aggregateVersion`
учитывает также её нормализованные части и используется для изменения владельца.
Версия и локальный CAS не заменяют адресный guard `--expected-addresses`.

`data.view`, `data.items`, порядок, повторы, ошибки отдельных адресов, `data.generation`
и пользовательская проекция сохраняются. Например, снятый раздел документа показывается
как `null`, а его историческая сохранённая ссылка не переписывается. `meta.versions`
относится к тому же согласованному anchor, содержит только успешные ID и не добавляется
в `entity`/`data` или content hash. `--summary` не загружает полные тела и журналы.
При смене anchor вызов завершается `COMMAND_CONTEXT_CHANGED`, не выдавая смешанный
результат. Без флага `get` сохраняет прежнюю форму ответа; текстовый вывод с флагом
показывает версии отдельными строками.

`product create` и `implementation create` также принимают `--expected-version`
существующего паспорта продукта и приложения соответственно. Для вложенных действий
читайте версию владельца: например, для этапа — плана, для checkpoint — сессии.

При переносе задачи между планами нужны предусловия обоих владельцев:

```bash
relay get PLN-1 PLN-2 --summary --with-versions --format json
relay plan stage task transfer PLN-1 TASK-1 target-stage-id --target-plan PLN-2 \
  --expected-version 'source-aggregate-version' --target-version 'target-aggregate-version' \
  --reason 'Перенос в следующий этап' --actor human
```

Замените адреса, ID этапа и оба токена прочитанными значениями. `--target-version`
принадлежит целевому плану и может заменять либо дополнять `--target-revision`.
Если переданы обе формы, проверяются обе; токен исходного плана не подходит целевому.

## Применить связанный пакет

`batch` объединяет предметные изменения выбранного проекта в одну транзакцию.
Например, создайте новую редакцию документа и архивируйте предыдущую. Здесь
`DOC-1` и ревизию `3` нужно заменить адресом и ревизией прочитанного документа:

```bash
relay batch --actor agent --operation-key publish-spec-v2 --input - <<'JSON'
{
  "version": 1,
  "operations": [
    {
      "op": "document.create",
      "as": "new-spec",
      "input": {
        "name": "Правила бронирования, редакция 2",
        "body": "Актуальные правила бронирования переговорных.",
        "documentStatus": "active"
      }
    },
    {
      "op": "document.update",
      "ref": "DOC-1",
      "ifRevision": 3,
      "input": {"documentStatus": "archived"}
    }
  ]
}
JSON
```

Единый `--input` принимает JSON непосредственно, `@путь` к UTF-8 файлу либо `-`
для stdin. Относительный путь считается от каталога запуска. Источник ограничен
8 MiB, пакет — 200 операциями. `batch -h` описывает общую форму пакета и его гарантии;
справка по конкретным действиям открывается через `batch help`.

Локальное имя `as` позволяет ссылаться на результат предыдущего шага через
`{"$ref":"имя"}` в адресном поле. Например, `scenario.create` принимает
`"feature":{"$ref":"booking"}` после создания фичи с `"as":"booking"`.
Ссылки вперёд запрещены. `{"$revision":"имя"}` в `ifRevision` использует возвращённую
ревизию того же владельца: этапа — плана, критерия — задачи. Для первой правки существующего
владельца передайте прочитанный `ifRevision` либо переносимый `expectedVersion`.
Текстовые поля передаются дословно.

В JSON-операции batch поле `expectedVersion` соответствует предметному флагу
`--expected-version`, а `input.targetVersion` — `--target-version` целевого плана.
Токен нужного владельца берётся из `get --with-versions` (`meta.versions[ID].aggregateVersion`)
либо versioned API Core. Обычный CLI `get` также возвращает локальную `revision`
для `--if-revision`.
Если в операции заданы и `ifRevision`, и `expectedVersion`, проверяются оба.
Старый токен не актуализируется внутри пакета; для следующего шага над тем же владельцем
можно использовать `$revision` предыдущего результата. Для переноса между планами
целевой план имеет собственное условие `input.targetRevision` либо `input.targetVersion`.
Подробности версии и её области — в [Core README](../packages/core/README.md#использование-в-приложении).

### Справка о пакетных операциях

```bash
relay batch -h
relay batch help
relay batch help plan
relay batch help plan stage
relay batch help plan stage create
relay batch help product create
```

Промежуточные уровни показывают действия и подгруппы выбранной области. У конкретной
операции перечислены её поля: JSON-тип, назначение, обязательность, поведение при
пропуске и `null`, Markdown, ссылки и значения перечислений. Здесь же находятся
владелец ревизии, предметные условия и готовый пример пакета. Адреса и ревизии примера
нужно заменить прочитанными значениями своего проекта.

Справка не требует проекта или автора. Вызовы `relay batch help plan stage create`
и `relay batch help plan stage create -h` равнозначны. Пакет применяется через
`relay batch --input …`.

### Вложенные действия пакета

`ref` располагается на верхнем уровне операции и адресует владельца. Дополнительные
адреса передаются в `input`. Справка выбранного действия, например
`relay batch help plan stage create`, перечисляет его поля и пути с поддержкой `$ref`.

| Действие                  | `ref`  | Адресные поля `input` | Владелец `ifRevision` |
| ------------------------- | ------ | --------------------- | --------------------- |
| `plan.stage.create`       | План   | `before`, если задан  | План                  |
| `plan.stage.update`       | План   | `stageId`             | План                  |
| `plan.stage.task.add`     | План   | `stageId`, `task`     | План                  |
| `task.criterion.add`      | Задача | —                     | Задача                |
| `task.criterion.complete` | Задача | `criterionId`         | Задача                |
| `task.comment.add`        | Задача | —                     | Не требуется          |

Создание реализации меняет состав приложения: `implementation.create` принимает
`ifRevision` либо `expectedVersion` этого приложения. Для нового приложения используйте `$revision` шага
его создания, для следующей реализации — шага предыдущего изменения состава.
`product.create` заполняет существующий паспорт и требует его предусловие версии. Владельцы
ревизий остальных действий указаны в соответствующих разделах `batch help`.

Например, следующий пакет создаёт план с этапом и включает существующую задачу
`TASK-1`. Замените ключ задачи своим; её ревизия для включения в план не требуется:

```json
{
  "version": 1,
  "operations": [
    { "op": "plan.create", "as": "plan", "input": { "title": "Первый выпуск" } },
    {
      "op": "plan.stage.create",
      "as": "stage",
      "ref": { "$ref": "plan" },
      "ifRevision": { "$revision": "plan" },
      "input": { "title": "Реализация" }
    },
    {
      "op": "plan.stage.task.add",
      "ref": { "$ref": "plan" },
      "ifRevision": { "$revision": "stage" },
      "input": { "stageId": { "$ref": "stage" }, "task": "TASK-1" }
    }
  ]
}
```

### Проверка и восстановление пакета

Для подготовленного файла сначала можно проверить применение:

```bash
relay batch --actor agent --input @changes.json --check
relay batch --actor agent --input @changes.json --operation-key changes-01 --return full
relay batch result changes-01 --return full
```

`--check` выполняет предметные проверки и откатывает все изменения. Ключ операции
для проверки не требуется; выданные предварительные адреса не резервируются.
При применении состояние и ревизии проверяются заново. Ошибка исполнения до commit
откатывает весь пакет; диагностика указывает неуспешную операцию и проблемное поле.

Применение требует `--operation-key`, уникальный в проекте. Данные и квитанция
сохраняются атомарно. Повтор того же запроса с тем же автором и ключом возвращает
первоначальный результат без повторной записи; другое содержание вызывает конфликт.
Пробелы оформления JSON и порядок свойств объектов не влияют на идентичность;
порядок операций, значения, исходные адреса, локальные имена и наличие полей влияют.
Ошибка вывода после commit не отменяет запись. При потере ответа повторяйте запрос
с тем же ключом либо читайте результат через `batch result`. Ключи автоматически
не истекают. `--return full` добавляет полные итоговые записи к компактным квитанциям;
сохранённый результат относится ко времени исходной операции.
Повтор известного пакета возвращает квитанцию до новых адресных guards и CAS:
`--expected-addresses` не превращает replay в повторное исполнение мутаций.

## Git-синхронизация

Git Sync обменивает данные независимых локальных реплик через одну общую ветку
Git-репозитория. Server для этого не нужен. Все участники выбирают одну ветку данных;
по умолчанию это `relay-data-v2`. SQLite остаётся местом локальной работы, а успешная
предметная команда не ждёт сети или фонового процесса. Новая версия и её обмен
продолжают развиваться; подробный целевой контракт задан в
[ТЗ Git Sync](../GIT-SYNC-IMPLEMENTATION-SPEC.md).
`connect`, `restore`, `status` и ручной `now` доступны без запущенного supervisor.

### Подключить проект и выполнить обмен

Для первой публикации уже существующего локального проекта запустите из его корня:

```bash
relay git-sync connect --remote origin --branch relay-data-v2
relay git-sync now
relay git-sync status --format json
```

`origin` — имя Git remote в текущем кодовом checkout. При подключении Relay один раз
разрешает его URL относительно каталога запуска и сохраняет полученный адрес.
Можно сразу передать URL или абсолютный путь к репозиторию, например
`--remote /путь/к/командному.git`: кодовый checkout тогда не нужен.
`--branch relay-data-v2` можно опустить — это имя ветки данных по умолчанию.
В workspace выберите проект через `--project`.
Выбор через `--project` или `--config` не меняет каталог разрешения `origin`:
для remote другого checkout передайте его URL либо запустите команду из этого checkout.

Данные расположены в трёх разных местах:

- рабочая SQLite выбранного проекта содержит локальные записи и очередь изменений;
- служебный bare-репозиторий рядом с физическим файлом БД,
  `<databasePath>.git-sync/repository/`, обслуживает Git-транспорт;
- общая ветка remote содержит переносимое текстовое состояние проекта.

SQLite и её WAL в Git не записываются. Ветка данных имеет самостоятельную историю,
отдельную от истории веток кода; переходить на неё в рабочем checkout не требуется.
Изменения кодовой ветки сами по себе не являются изменениями данных Relay.

Первое `connect` выполняет fetch и проверку совместимости ветки, но не делает push
и не импортирует remote-снимок в SQLite. Первую публикацию локальных данных выполняет
`now`. Если данные команды уже опубликованы, новую независимую копию получают через
[restore](#восстановить-независимую-реплику) без предварительного `init`/`connect`.

`now` обрабатывает одно ограниченное окно очереди, сохраняя прогресс обхода между
запусками. Успех окна не означает отправку всей очереди: проверьте фактический pending
и при необходимости продолжите `now` либо автоматический обмен.
Если остаются реальные неразрешённые конфликты,
он возвращает exit 4 / `SYNC_CONFLICT` с деталями. Материалы конфликтов и уже
согласованные независимые изменения сохраняются. Ошибка сети также не отменяет
предыдущие локальные записи. Повтор доставки работает с сохранёнными changeset,
а не повторяет пользовательские команды.

### Прочитать состояние проекта или workspace

```bash
relay git-sync status --format json
relay git-sync status --refresh --format json
relay git-sync status --all --format json
```

Обычный `status` читает локально известное состояние и проверяет отзывчивость процесса,
не выполняя Git-обмен. `--refresh` явно получает сведения remote, но не отправляет
pending и не применяет удалённое содержание. Состояние worker отделено от доставки:
desired/actual, responsive и instance не равны отсутствию конфликтов или пустой очереди.
Git ahead/behind считает коммиты между известными refs, а pending — changeset;
неэкспортированные пакеты учитываются отдельно. Неизвестные значения в JSON равны `null`.
Свежесть последнего fetch и реально назначенная следующая попытка показываются отдельно.

Успешный status/now содержит `publication: {afterSequence, window}`. В window показаны
курсор подготовки и следующего окна, hasMore, examined/included/deferred, sourceBytes,
oversized и completed. Это сведения последнего окна, а `pending.changesets` — полный
актуальный остаток. Deferred/hasMore описывают момент подготовки, completed не обещает
пустой outbox. Частичный просмотр конфликтов помечается `conflicts.freshness: "partial"`;
один конец cursor-обхода не делает непросмотренные материалы актуальными.

Из корня workspace без `--project` статус перечисляет все регистрации; `--all`
выбирает этот режим явно и несовместим с `--project`. В обычной CLI JSON-обёртке поле
`data` имеет одинаковую форму для одного проекта и workspace:
`{version: 1, scope: "project" | "workspace", items: [...]}`.
Элемент содержит `name`, `path`, `ok` и статус в `data` либо причину в `error`.
Для одиночного выбора неизвестный путь регистрации равен `null`.
Ошибка одной регистрации сохраняет остальные элементы и даёт ненулевой общий код;
частичный JSON доступен в stdout. Само наличие предметных конфликтов не делает
`status` или `conflicts list` ошибкой: успешное чтение возвращает exit 0.

### Дождаться исхода по request ID

Явные `now` и `status --refresh` создают операции с `requestId`. Время ожидания
задаётся `--wait-ms`: целое число от 1 до 90000 мс, по умолчанию 60000.
Это бюджет ожидания ответа, а не признак готовности worker и не гарантия отмены работы.

```bash
relay git-sync now --wait-ms 5000 --format json
relay git-sync request get request-id --format json
relay git-sync now --request-id request-id --wait-ms 60000 --format json
```

Подставьте ID из результата первого вызова либо `error.details.requestId`.
Без `--request-id` начинается новая операция: Runtime назначает ей внутренний
`operationId` до запуска компонента. С `--request-id` команда только ждёт прежний исход
и не отправляет новую работу. `request get` читает состояние без нового обмена.
Используйте тот же выбранный проект и `RELAY_HOME`.

`request get` возвращает `queued`, `running`, `completed`, `failed` или `unknown`.
Код 0 означает успешное чтение этого состояния; только `completed` обозначает успешный
исход операции. У `failed` сохранена ошибка. `unknown` после потери владельца или
истечения retention не означает ни успех, ни отмену, ни отсутствие эффектов.
Завершённая операция также не обещает пустую очередь: актуальные pending и конфликты
проверяются отдельно.

- `GIT_SYNC_WAIT_TIMEOUT` (exit 4) содержит ID и наблюдавшееся `queued/running`.
  Это истёкшее ожидание принятого запроса, а не `GIT_SYNC_NOT_READY`.
- `GIT_SYNC_TIMEOUT` (exit 124) на процессной границе сохраняет ID с `state: unknown`:
  принятие и завершение операции могли остаться неизвестными.
- `GIT_SYNC_OUTCOME_UNKNOWN` (exit 4) означает отсутствие достоверного исхода.
  Запрос по этому ID не становится новым submit; новую попытку пользователь выбирает отдельно.

При постоянном worker истечение ожидания не отменяет его принятую операцию.
Одноразовый обмен остаётся ограничен lifetime своего request lease; его окончательный
исход также проверяется по ID. Журнал ограничен активными и недавними результатами
и не заменяет durable changeset, Git ack или неизменяемую batch-квитанцию.

У `status` параметры ожидания допускаются только с `--refresh`. Продолжить ожидание
одного проекта можно через `status --refresh --request-id request-id --wait-ms 60000`.
В workspace `--refresh --all --wait-ms 5000` задаёт отдельный бюджет каждой регистрации;
их IDs находятся в собственных результатах/ошибках `items`. Один `--request-id`
несовместим с `--all` и неявным режимом всего workspace — сначала выберите `--project`.

### Автоматический обмен и процессы

Постоянными workers владеет долгоживущий supervisor. Сначала запустите его для
выбранного `RELAY_HOME`: один раз явно включите пользовательскую login-службу:

```bash
relay git-sync service enable
```

Либо держите supervisor на переднем плане в отдельном живом терминале:

```bash
relay git-sync supervise
```

Во втором случае команды проекта выполняются из другого терминала с тем же `RELAY_HOME`.
Затем из корня проекта подключите remote, если это ещё не сделано, и включите обмен:

```bash
relay git-sync connect --remote origin --branch relay-data-v2
relay git-sync auto enable
```

`auto enable`, `worker start` и `worker restart` обращаются к готовому совместимому
supervisor и ждут readiness worker. Если supervisor не запущен, команда возвращает
`SUPERVISOR_REQUIRED`, сохраняя прежние `mode` и `desired`. Короткий CLI-request
не запускает постоянных демонов и не устанавливает native-службу скрыто.

Дальнейшее управление выбранным проектом:

```bash
relay git-sync worker start
relay git-sync worker restart
relay git-sync auto disable
relay git-sync worker stop
```

`auto enable` после проверки supervisor сохраняет настройку автоматического обмена.
Одна БД в нескольких workspace не требует нескольких workers. Supervisor
наблюдает за проектами и ограничивает общий бюджет сетевых циклов.
Успех запуска означает readiness, а не завершение доставки.

`auto disable` прекращает новые фоновые сетевые попытки, сохраняя возможность
ручного `now`; уже начатый цикл может завершиться. `worker stop` останавливает
владельца и сохраняет желаемое состояние `stopped`. Обычный выход короткой CLI-команды
не останавливает отдельно запущенные supervisor/workers. Сохранённый `stopped`
учитывается и при следующем запуске supervisor. Без постоянного worker ручной
`now` выполняется одноразово под lease запроса, не меняя режим и desired state.

### Просмотреть и разрешить конфликт

`conflicts list` возвращает в `data` объект `{conflicts: [...], blocked: [...]}`.
Первый массив содержит реальные конфликты с fingerprint; второй — изменения,
ожидающие зависимостей: `{id, state:"pending", code:"REPLICATION_DEPENDENCY", message,
dependencies}`. Ожидание не требует разрешения как трёхстороннего конфликта.
Get по такому ID показывает причину без fingerprint/сторон, а попытка resolve
отклоняется с `REPLICATION_DEPENDENCY`, exit 4, и `details.blocked` без мутации.
Pending из-за бюджета или dependencies само по себе не вызывает `SYNC_CONFLICT`.

Для реального конфликта возьмите ID из `conflicts` и прочитайте актуальные материалы:

```bash
relay git-sync conflicts list --format json
relay git-sync conflicts get conflict-id --format json
relay git-sync conflicts resolve conflict-id \
  --input '{"fingerprint":"прочитанный-fingerprint","choice":"local"}' \
  --actor human
relay git-sync now
```

Замените `conflict-id` и `прочитанный-fingerprint` значениями из ответов.
Ввод решения принимает `choice: "local"`, `"remote"` либо `"custom"` и обязательный
`fingerprint`. Выбор относится ко всему changeset. `--input` также читает
`@resolution.json` или stdin при значении `-`; автор задаётся `--actor` либо `RELAY_ACTOR`.
Устаревший fingerprint отклоняется: перечитайте конфликт и согласуйте решение заново.
`resolve` сохраняет проверенное решение; для доставки выполните `now` и проверьте
оставшиеся pending и конфликты.
Результат resolve содержит `{id, generation, included, conflicts, blocked, pending,
deferred, hasMore}`. Списки conflicts/blocked полные, pending фактический; остальные
сведения о включении/ожидании относятся к ограниченному preview. Это не Git ACK.
Ни выбор локальной стороны, ни решение конфликта не обходят неизменяемость истории
и предметные правила Core.

Custom v1 разрешает согласовать только `name`, `summary` или `body` существующего
документа, если это поле действительно изменялось выбранным исходным шагом changeset.
Пример содержимого `resolution.json`:

```json
{
  "fingerprint": "прочитанный-fingerprint",
  "choice": "custom",
  "patch": [
    {
      "transition": 0,
      "entityId": "document-id",
      "field": "body",
      "value": "Согласованный текст"
    }
  ]
}
```

Подставьте fingerprint, ID документа и индекс исходного шага из `conflicts get`.
`transition` нумеруется с нуля в `changeset.transitions`; у legacy atomic boundary
используется 0. Передайте файл той же команде `conflicts resolve --input @resolution.json`.
Остальные эффекты пакета проходят обычное согласование и проверки Core. Произвольные
JSON paths, незатронутые поля, другие виды записей, компоненты и история не принимаются.
Исходный changeset, его digest и первоначальная квитанция не переписываются.

Если origin уже принял другое решение, позднее предложение остаётся явным конфликтом
`REPLICATION_RESOLUTION_STALE`. Выбор `remote` принимает опубликованный результат;
его последующее изменение выполняется новой предметной командой.

### Восстановить независимую реплику

Новый участник получает тот же проект из опубликованной ветки без предыдущего `connect`.
Если команда запускается из Git checkout с настроенным `origin`, достаточно:

```bash
relay git-sync restore --remote origin --branch relay-data-v2
```

В действительно пустом каталоге имени `origin` ещё нет. Передайте URL либо абсолютный
путь remote вместо его имени:

```bash
relay git-sync restore --remote https://example.org/team/project.git \
  --branch relay-data-v2
```

Замените URL своим адресом. В обоих вариантах `--branch` можно опустить для
`relay-data-v2`; предварительные `init` и `connect` не требуются. Команда выполняет
fetch и проверку опубликованных данных, создаёт БД, `relay.config.json` и сохранённое
Git-подключение, сохраняя предметные ID
и квитанции, но выделяя собственный ID локальной реплики. Существующая рабочая БД
не заменяется. Для конфига того же проекта с утраченной БД доступно явное восстановление;
без `--remote` используется сохранённое подключение. Только локальные, не попавшие
в доступную Git-историю изменения требуют отдельной резервной копии.

Если публикация локальной БД прервалась или обнаружено её незавершённое намерение,
возвращается `RESTORE_RECOVERY_REQUIRED` (exit 4). Рабочая БД, staging и intent
сохраняются: опубликованный файл уже мог принять поздние записи через другой worktree,
даже при прежнем inode и отсутствии WAL/SHM. Повтор обычного `restore` при таком
намерении отклоняется до повторного создания БД и не объявляет прежние данные
результатом нового fetched snapshot. Удаление staging/intent ради повторного запуска
не является безопасным продолжением восстановления.

### Завершить прерванную локальную публикацию

После `RESTORE_RECOVERY_REQUIRED` явно подключите сохранённый проект в контексте
исходной операции: используйте тот же `RELAY_HOME` и каталог либо явный `--config`.
Если конфиг ещё не опубликован, передайте известный постоянный ID проекта:

```bash
relay git-sync restore --resume --project-id project-id
```

Замените `project-id` постоянным ID исходного проекта. Если выбранный конфиг уже
существует, Runtime берёт ID из него:

```bash
relay git-sync restore --resume --config ./relay.config.json
```

`--project` по-прежнему означает имя регистрации workspace, а `--project-id` —
постоянный ID и допускается только в режиме resume. `--resume` несовместим
с `--remote` и `--branch`. Без выбранного конфига и явного ID возвращается
`RESTORE_PROJECT_ID_REQUIRED` (exit 2); home не сканируется для поиска кандидата.
Supervisor и установленная служба для resume не нужны.

Resume сохраняет фактическую локальную БД, её `replicaId`, поздние commits и outbox.
Core только проверяет сохранённые данные; новая материализация, fetch, импорт
Git-объектов, ack и обновление progress не выполняются. Успех возвращает
`data.resumed: true`, `data.preservedExisting: true` и `data.sourceCheckpoint: null`:
подтверждена локальная привязка, а не соответствие новому Git HEAD.
Дальнейшие `git-sync connect` и `git-sync now` — отдельные явные действия.

`data.recovery: null` означает завершённую уборку доказанных private-материалов.
Непустое `recovery` содержит пути и `failure: {code, message}`: привязка успешна,
но часть cleanup не завершена. Неизвестные companion-файлы сохраняются. Чужая БД,
неподтверждённое владение или повреждённый intent дают сохраняющий отказ, а не такой
успех с предупреждением. После полной cleanup повтор возвращает `RESTORE_NOT_PENDING`
(exit 3) без validator и записи; при целых оставшихся recovery-материалах повторная
проверка допустима. Прежние intent v1/v2 не преобразуются автоматически в intent v3:
их SQLite-alias могут принадлежать живым соединениям и требуют отдельного офлайн-восстановления.

### Пользовательский автозапуск

Из терминала пользователя с выбранным `RELAY_HOME`:

```bash
relay git-sync service enable
relay git-sync service status --format json
relay git-sync service disable
```

Только явное `service enable` устанавливает пользовательскую регистрацию и запускает
supervisor. `auto enable`, `connect` и обычные предметные команды службу не устанавливают.
Автоматических `systemd-run` или динамических Task Scheduler задач вместо неё нет.

- Linux использует `systemd --user`. Обычный запуск привязан к login; работа до входа
  и после logout зависит от отдельно настроенного linger. Relay не включает его сам.
- macOS использует LaunchAgent графической сессии текущего пользователя после login.
- Windows использует Task Scheduler с logon trigger текущего пользователя без
  административного режима и скрытого сохранения пароля. Одна задача поддерживает
  supervisor до `service disable`, в том числе после выхода с кодом 0. Регистрация/обновление
  и login активируют свои native-триггеры; каждый повторяется с интервалом в одну минуту.
  Это не общий лимит одного старта в минуту и не конечный счётчик неудачных запусков.
  Пока экземпляр работает, `IgnoreNew` не запускает второй; готовность всё равно проверяется health.

`service status` различает регистрацию у native manager и отзывчивость supervisor.
`service disable` удаляет только свою регистрацию данного home, сохраняя проекты.
На Windows сначала запрещаются новые активации task, затем ожидаются остановка и освобождение
mutex supervisor. Ошибка стадии не включает задачу обратно автоматически; `service status`
показывает фактическое состояние, после устранения причины можно явно повторить команду.
В регистрации сохраняется абсолютный путь бинарника: после его переноса повторите
`service enable`. Для контейнера или внешнего supervisor служба не нужна:

```bash
relay git-sync supervise --home /var/lib/relay
```

Замените путь своим корнем данных. Native supervisor запускается пользовательским manager
в пределах описанной login-семантики. Foreground supervisor живёт вместе с запустившей
CLI: команда передаёт потоки и сигналы, а завершение этого сеанса или потеря parent lease
инициирует остановку его supervisor/workers. Завершение другого, одноразового CLI-request
не прекращает их работу.
На macOS гарантия относится к managed foreground Git/SSH/helpers в собственной
process group. Произвольные custom helpers с `setsid`/сменой группы не считаются
полностью удерживаемыми; группа не является атомарным fork-barrier. Уже работающие
внешние ssh-agent, SSH master и Keychain не становятся потомками Relay.
Управляемый Git-профиль отключает auto-maintenance detach; foreground-настройки
поддерживаемого OpenSSH сохраняют пользовательскую auth-конфигурацию.
Точные платформенные границы и нативная приёмка описаны в
[разделах IPC и служб ТЗ](../GIT-SYNC-IMPLEMENTATION-SPEC.md#12-workers-supervisor-и-process-protocol).

## Области команд

| Область              | Команды                                                                                                              |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Проекты              | `init`, `project`, `config`, `workspace project`                                                                     |
| Знания продукта      | `product`, `feature`, `scenario`, `application`, `implementation`                                                    |
| Библиотека           | `document`, `document section`                                                                                       |
| Работа               | `board`, `task`, `task parent`, `task dependency`, `task criterion`, `task comment`                                  |
| Планирование         | `plan`, `plan stage`, `plan stage task`, `release`                                                                   |
| История работы       | `session`, `checkpoint`                                                                                              |
| Чтение и диагностика | `get`, `search`, `overview`, `storage status`, `doctor check`                                                        |
| Пакетные изменения   | `batch`, `batch result`, `batch help`                                                                                |
| Git-обмен            | `git-sync connect`, `now`, `status`, `request get`, `auto`, `worker`, `conflicts`, `restore`, `service`, `supervise` |

Доступные действия каждой группы перечисляет её справка. Доска продукта создаётся
при инициализации, а доска приложения — при создании приложения.
Готовность задач и планов вычисляется с учётом обязательств; сохранённый статус
и фактическая готовность различаются. Выпуск в Relay фиксирует сведения о результате,
а фактическую сборку, проверки и публикацию выполняют внешние инструменты.

## Фильтры списков знаний

```bash
relay application list --type backend
relay board list --application APP-1
relay implementation list --feature FEATURE-1 --active
relay document list --without-section
```

`implementation list --feature` выбирает реализацию фичи и реализации её сценариев;
`--target` ограничивает точную цель. Переданные условия пересекаются. Без `--active`
список реализаций включает также снятое участие.

`--without-section` выбирает документы вне активных разделов, включая документы
удалённого раздела. Он несовместим с одновременно переданным `--section-id`;
`--without-section=false` отключает этот фильтр. Значение `--section-id none`
остаётся буквальным ID раздела. Условия фильтрации сохраняются в команде продолжения;
изменение условий требует начать список заново.

## Вывод и продолжение списков

По умолчанию результат — читаемый текст. `--format json` предназначен для скриптов
и отладки. Успешные результаты идут в stdout, ошибки — в stderr. Код `0` означает
успех, `2` — ошибку ввода, `3` — отсутствие искомой записи, `4` — конфликт;
прочие ошибки имеют ненулевой код.

Текстовое представление выбирается по назначению команды: `config get` показывает
исходный конфиг и вычисленные пути, `task comment list` — полные тела комментариев
текущей страницы, `overview` — глобальную сводку отдельно от карты. В `session tree`
родитель за пределами окна обозначается его постоянным ID, а не ложным корнем.
Снятое участие реализации помечается в списке независимо от её сохранённого статуса.
JSON сохраняет предметные данные и метаданные без служебной метки макета.

Списки поддерживают `--limit` и `--cursor`. Продолжение относится к конкретному
проекту, запросу и поколению данных. После изменения данных прежний курсор
отклоняется: начните список заново. Страница списка не является полным содержимым
проекта, а краткая карточка не заменяет адресное чтение записи.

Страницы задач этапа и планов релиза сохраняют порядок включения и загружают полные
карточки только выбранного окна. Total и ревизия владельца относятся к тому же снимку;
существование ссылок всего состава проверяется отдельно по лёгким идентичностям.
