# Локальная работа через CLI

`relay` — самостоятельный бинарник на Bun. Вложенные команды, параметры и русскую
справку обрабатывает Gunshi. Точный состав параметров доступен через
`relay <команда> --help`; справка и версия работают без выбранного проекта.

## Запуск

Из корня исходников:

```bash
bun install --frozen-lockfile
bun run build:cli
export PATH="$PWD/apps/cli/dist:$PATH"
relay --help
```

Экспорт PATH действует в текущем терминале. Для работы выберите каталог своего проекта.

## Справка и примеры

```bash
relay --help
relay task
relay task create --help
relay plan stage task transfer --help
```

Корневая справка знакомит с областями работы. Предметная группа без подкоманды показывает
свои действия, пояснения и примеры. `batch` выполняет пакет непосредственно, а
`batch result` читает его квитанцию. Справка действия описывает параметры, результат,
существенные условия и связанные команды. Она доступна через `--help` или `-h`
без настроенного проекта и чтения stdin.

Примеры рассчитаны на POSIX shell, включая Bash и Zsh. Заменяйте условные ключи, ID,
пути и ревизии данными своего проекта. Ревизию берите из прочитанной записи владельца:
он указан в справке изменяющей команды. Обязательные предметные поля могут передаваться
отдельными параметрами либо через `--input`; подробности приводит справка действия.
При ошибке ввода CLI показывает путь к справке распознанной команды;
в JSON он находится в отдельном поле `error.helpCommand`.

## Автодополнение

`relay complete <shell>` печатает скрипт подключения для `bash`, `zsh`, `fish` или
`powershell`. Подсказки команд, параметров и значений перечислений берутся из схем CLI:
например, `relay docu<Tab>`, `relay task create --<Tab>` и `relay --format j<Tab>`.
Генерация и запрос подсказок доступны без проекта и открытия его БД.

Для Bash нужен установленный и подключённый `bash-completion`. После установки
команды `relay` один раз выполните:

```bash
mkdir -p ~/.local/share/bash-completion/completions
relay complete bash > ~/.local/share/bash-completion/completions/relay
source ~/.local/share/bash-completion/completions/relay
```

В новых терминалах этот файл подхватывает `bash-completion`. Подключение выполняется
в интерактивной оболочке; `.envrc` отвечает за переменные окружения и `PATH`.
Bash-скрипт запрашивает кандидатов у текущей команды `relay` из `PATH`, поэтому после
обычной пересборки новые команды доступны без повторной генерации скрипта.

Для других оболочек используйте `relay complete zsh`, `relay complete fish` или
`relay complete powershell` и подключите выведенный скрипт средствами своей оболочки.
После переноса бинарника сгенерируйте эти скрипты заново: они содержат путь запуска.
Команда `complete` выводит shell-скрипт или служебный протокол без JSON-обёртки.

## Проект и размещение данных

```bash
relay init --name "Библиотека инструкций" --slug instructions
relay project get
relay config get
```

В рабочем каталоге создаётся `relay.config.json` с полями `version` и `projectId`.
По умолчанию SQLite-база определяется как `RELAY_HOME/projects/<projectId>/project.sqlite`;
если `RELAY_HOME` не задан, используется `~/.relay`. Это правило действует и при создании,
и при последующих запусках. SQLite работает в режиме WAL.

Начальные записи создаются от `system`; `--actor` для `init` не требуется и не меняет
авторство этих записей.

Явно пустой `RELAY_HOME`, включая строку из пробелов, отклоняется до файловых действий.
Относительный путь разрешается от каталога запуска; отсутствие переменной выбирает
`HOME/.relay`.

Необязательное поле `databasePath` в конфиге переопределяет стандартное расположение.
Абсолютный путь используется напрямую, относительный разрешается от физического каталога
конфига, включая открытие через символьную ссылку. Пустой или нестроковый путь считается
ошибкой. Без этого поля смена `RELAY_HOME` меняет место поиска базы; саму базу команда
не переносит. `relay config get --format json` возвращает исходный конфиг в `data`
и вычисленный абсолютный путь в `meta.databasePath`.

Обычная команда проверяет только текущий каталог: запускайте Relay из корня проекта
или workspace. Родительские каталоги и `.relay/config.json` автоматически не проверяются.
`--config <path>` выбирает файл явно; `RELAY_CONFIG` позволяет задать путь через окружение.
Чтение отсутствующей базы завершается ошибкой. Повторная инициализация не заменяет
существующий проект. Регистрация и расположение базы отделены от предметного имени
проекта и его постоянного ID.

## Локальный workspace

В каталоге, из которого удобно работать с несколькими проектами:

```bash
relay workspace project init
relay workspace project add backend ../backend
relay workspace project add frontend ../frontend
relay workspace project list
relay project get --project backend
relay document list --project frontend
```

Перед регистрацией проект должен быть инициализирован. Команда `add` принимает каталог
с обязательным `relay.config.json` в его корне. Workspace хранит только имя регистрации
и путь каталога; ID и необязательное переопределение пути базы читаются из конфигурации
выбранного проекта. Стандартное размещение использует `RELAY_HOME` текущего вызова.
Файл `relay.workspace.json` может выглядеть так:

```json
{
  "version": 1,
  "projects": [
    { "name": "backend", "path": "../backend" },
    { "name": "frontend", "path": "../frontend" }
  ]
}
```

Относительные пути каталогов разрешаются от физического каталога workspace-файла,
включая открытие через символьную ссылку. В результате `workspace project list`
возвращаются абсолютные пути `path`. Файл workspace также ищется только в текущем
каталоге, если не задан явный `--config` или `RELAY_CONFIG`.
Для предметной команды в workspace требуется явный `--project`.
Одинаковые ключи сущностей в разных проектах относятся к независимым записям.
`workspace project remove <name>` удаляет регистрацию и сохраняет данные проекта.
Рядом с реестром находится служебный `relay.workspace.json.lock.sqlite`: он
сериализует изменения регистраций между процессами, включая аварийное завершение
одного из них, и не содержит предметных данных проекта.

## Содержание и изменения

```bash
relay document create \
  --name "Правила проверки" \
  --body-file ./rules.md \
  --actor human
relay document get DOC-1
relay task create \
  --board product \
  --title "Проверить сохранение текста" \
  --description "Сохранить документ и сверить полное содержание после повторного запуска." \
  --actor human
```

Ключи в примерах иллюстративны: используйте адрес из результата создания.
Автор задаётся через `--actor` или `RELAY_ACTOR`. Перед изменением прочитайте запись:
`--if-revision` принимает её исходную ревизию. При конфликте перечитайте данные
и согласуйте изменение. CLI не подставляет свежую ревизию и не повторяет мутацию.

У вложенных изменений ревизия принадлежит владельцу: разделы документов — проекту,
участие приложения — приложению, этапы и состав плана — плану, контрольные точки
истории — сессии. Комментарии задачи дописываются независимо: они не требуют
`--if-revision` и не меняют ревизию содержания задачи.

Текстовые параметры поддерживают непосредственный ввод и соответствующий
`--<поле>-file`; путь `-` читает stdin. У одного поля должен быть один источник,
а stdin может использоваться только одним полем команды. Markdown сохраняется
с пустыми строками и значимыми отступами. Полное содержание читается через `get`.

Текст с начальным дефисом передавайте в одном аргументе `--поле='исходный текст'`,
через `--поле-file` или JSON. Кавычки вокруг отдельного значения сохраняют его текст,
но не отменяют разбор начального дефиса как параметра CLI.

Наборы ссылок задаются повторением параметра, например `--targets FEATURE-1
--targets FEATURE-2`. Для структурированного ввода доступны `--input` и
`--input-file`; пустой набор задаётся явно, например `--input '{"targets":[]}'`.
В командах релиза обозначение выпуска принимает параметр `--release-version`;
`--version` показывает версию самого CLI.

Читаемые ключи являются локальными адресами проекта. Ссылки между записями хранят
постоянные ID; переименование ключа сохраняет прежний адрес как алиас.

## Прочитать рабочий набор

В выбранном проекте передайте от одного до 200 адресов. Ключи в примерах условные:

```bash
relay get DOC-1 TASK-1 PLAN-1
relay get DOC-1 TASK-1 PLAN-1 --summary
relay get DOC-1 TASK-1 PLAN-1 --format json
```

По умолчанию `get` возвращает полное содержание выбранных записей из одного снимка.
Каждый текстовый блок начинается с заголовка, содержащего номер и адрес; блоки
разделены пустой строкой. Markdown не усекается. `--summary` оставляет краткие
карточки с названием, идентичностью, ревизией и сохранённым состоянием, без тел
документов и вложенных составов.
Краткое чтение проверяет выбранные поля; полное предметное содержание проверяется
при обычном `get`.

Порядок и повторения адресов сохраняются. JSON содержит `data.view` (`full` или
`summary`) и `data.items`: успешный элемент содержит исходный `ref`, `ok: true` и
`entity`, ошибочный — `ok: false` и `error`. Одна запись имеет ту же форму списка.
Если часть адресов не найдена или неверна, остальные результаты доступны; общий
код завершения ненулевой, а JSON частичного результата в stdout имеет `ok: false`.
Неожиданная ошибка хранилища завершает весь вызов обычной диагностикой в stderr.

Общее адресное чтение выполняется через `get`; прежняя группа `inspect` удалена.
Предметные команды вроде `document get` сохраняют удобство чтения известного вида.

## Применить связанный пакет

`batch` объединяет предметные изменения выбранного проекта в одну транзакцию.
Например, создайте новую редакцию документа и архивируйте предыдущую. Здесь
`DOC-1` и ревизию `3` нужно заменить адресом и ревизией прочитанного документа:

```bash
relay batch --actor agent --operation-key publish-spec-v2 --input - <<'JSON'
{
  "version": 1,
  "operations": [
    {
      "op": "document.create",
      "as": "new-spec",
      "input": {
        "name": "Правила бронирования, редакция 2",
        "body": "Актуальные правила бронирования переговорных.",
        "documentStatus": "active"
      }
    },
    {
      "op": "document.update",
      "ref": "DOC-1",
      "ifRevision": 3,
      "input": {"documentStatus": "archived"}
    }
  ]
}
JSON
```

Единый `--input` принимает JSON непосредственно, `@путь` к UTF-8 файлу либо `-`
для stdin. Относительный путь считается от каталога запуска. Источник ограничен
8 MiB, пакет — 200 операциями. `batch -h` описывает общую форму пакета и его гарантии;
справка по конкретным действиям открывается через `batch help`.

Локальное имя `as` позволяет ссылаться на результат предыдущего шага через
`{"$ref":"имя"}` в адресном поле. Например, `scenario.create` принимает
`"feature":{"$ref":"booking"}` после создания фичи с `"as":"booking"`.
Ссылки вперёд запрещены. `{"$revision":"имя"}` в `ifRevision` использует возвращённую
ревизию того же владельца: этапа — плана, критерия — задачи. Первая правка существующей
записи требует числовую ревизию из чтения. Текстовые поля передаются дословно.

### Справка о пакетных операциях

```bash
relay batch -h
relay batch help
relay batch help plan
relay batch help plan stage
relay batch help plan stage create
relay batch help product create
```

Промежуточные уровни показывают действия и подгруппы выбранной области. У конкретной
операции перечислены её поля: JSON-тип, назначение, обязательность, поведение при
пропуске и `null`, Markdown, ссылки и значения перечислений. Здесь же находятся
владелец ревизии, предметные условия и готовый пример пакета. Адреса и ревизии примера
нужно заменить прочитанными значениями своего проекта.

Справка не требует проекта или автора. Вызовы `relay batch help plan stage create`
и `relay batch help plan stage create -h` равнозначны. Пакет применяется через
`relay batch --input …`.

### Вложенные действия пакета

`ref` располагается на верхнем уровне операции и адресует владельца. Дополнительные
адреса передаются в `input`. Справка выбранного действия, например
`relay batch help plan stage create`, перечисляет его поля и пути с поддержкой `$ref`.

| Действие                  | `ref`  | Адресные поля `input` | Владелец `ifRevision` |
| ------------------------- | ------ | --------------------- | --------------------- |
| `plan.stage.create`       | План   | `before`, если задан  | План                  |
| `plan.stage.update`       | План   | `stageId`             | План                  |
| `plan.stage.task.add`     | План   | `stageId`, `task`     | План                  |
| `task.criterion.add`      | Задача | —                     | Задача                |
| `task.criterion.complete` | Задача | `criterionId`         | Задача                |
| `task.comment.add`        | Задача | —                     | Не требуется          |

Создание реализации меняет состав приложения: `implementation.create` принимает
`ifRevision` этого приложения. Для нового приложения используйте `$revision` шага
его создания, для следующей реализации — шага предыдущего изменения состава.
`product.create` заполняет существующий паспорт и требует его ревизию. Владельцы
ревизий остальных действий указаны в соответствующих разделах `batch help`.

Например, следующий пакет создаёт план с этапом и включает существующую задачу
`TASK-1`. Замените ключ задачи своим; её ревизия для включения в план не требуется:

```json
{
  "version": 1,
  "operations": [
    { "op": "plan.create", "as": "plan", "input": { "title": "Первый выпуск" } },
    {
      "op": "plan.stage.create",
      "as": "stage",
      "ref": { "$ref": "plan" },
      "ifRevision": { "$revision": "plan" },
      "input": { "title": "Реализация" }
    },
    {
      "op": "plan.stage.task.add",
      "ref": { "$ref": "plan" },
      "ifRevision": { "$revision": "stage" },
      "input": { "stageId": { "$ref": "stage" }, "task": "TASK-1" }
    }
  ]
}
```

### Проверка и восстановление пакета

Для подготовленного файла сначала можно проверить применение:

```bash
relay batch --actor agent --input @changes.json --check
relay batch --actor agent --input @changes.json --operation-key changes-01 --return full
relay batch result changes-01 --return full
```

`--check` выполняет предметные проверки и откатывает все изменения. Ключ операции
для проверки не требуется; выданные предварительные адреса не резервируются.
При применении состояние и ревизии проверяются заново. Ошибка исполнения до commit
откатывает весь пакет; диагностика указывает неуспешную операцию и проблемное поле.

Применение требует `--operation-key`, уникальный в проекте. Данные и квитанция
сохраняются атомарно. Повтор того же запроса с тем же автором и ключом возвращает
первоначальный результат без повторной записи; другое содержание вызывает конфликт.
Пробелы оформления JSON и порядок свойств объектов не влияют на идентичность;
порядок операций, значения, исходные адреса, локальные имена и наличие полей влияют.
Ошибка вывода после commit не отменяет запись. При потере ответа повторяйте запрос
с тем же ключом либо читайте результат через `batch result`. Ключи автоматически
не истекают. `--return full` добавляет полные итоговые записи к компактным квитанциям;
сохранённый результат относится ко времени исходной операции.

## Области команд

| Область              | Команды                                                                             |
| -------------------- | ----------------------------------------------------------------------------------- |
| Проекты              | `init`, `project`, `config`, `workspace project`                                    |
| Знания продукта      | `product`, `feature`, `scenario`, `application`, `implementation`                   |
| Библиотека           | `document`, `document section`                                                      |
| Работа               | `board`, `task`, `task parent`, `task dependency`, `task criterion`, `task comment` |
| Планирование         | `plan`, `plan stage`, `plan stage task`, `release`                                  |
| История работы       | `session`, `checkpoint`                                                             |
| Чтение и диагностика | `get`, `search`, `overview`, `storage status`, `doctor check`                       |
| Пакетные изменения   | `batch`, `batch result`, `batch help`                                               |

Доступные действия каждой группы перечисляет её справка. Доска продукта создаётся
при инициализации, а доска приложения — при создании приложения.
Готовность задач и планов вычисляется с учётом обязательств; сохранённый статус
и фактическая готовность различаются. Выпуск в Relay фиксирует сведения о результате,
а фактическую сборку, проверки и публикацию выполняют внешние инструменты.

## Фильтры списков знаний

```bash
relay application list --type backend
relay board list --application APP-1
relay implementation list --feature FEATURE-1 --active
relay document list --without-section
```

`implementation list --feature` выбирает реализацию фичи и реализации её сценариев;
`--target` ограничивает точную цель. Переданные условия пересекаются. Без `--active`
список реализаций включает также снятое участие.

`--without-section` выбирает документы вне активных разделов, включая документы
удалённого раздела. Он несовместим с одновременно переданным `--section-id`;
`--without-section=false` отключает этот фильтр. Значение `--section-id none`
остаётся буквальным ID раздела. Условия фильтрации сохраняются в команде продолжения;
изменение условий требует начать список заново.

## Вывод и продолжение списков

По умолчанию результат — читаемый текст. `--format json` предназначен для скриптов
и отладки. Успешные результаты идут в stdout, ошибки — в stderr. Код `0` означает
успех, `2` — ошибку ввода, `3` — отсутствие искомой записи, `4` — конфликт;
прочие ошибки имеют ненулевой код.

Текстовое представление выбирается по назначению команды: `config get` показывает
исходный конфиг и вычисленные пути, `task comment list` — полные тела комментариев
текущей страницы, `overview` — глобальную сводку отдельно от карты. В `session tree`

Снятое участие реализации помечается в списке независимо от её сохранённого статуса.
JSON сохраняет предметные данные и метаданные без служебной метки макета.

Списки поддерживают `--limit` и `--cursor`. Продолжение относится к конкретному
проекту, запросу и поколению данных. После изменения данных прежний курсор
отклоняется: начните список заново. Страница списка не является полным содержимым
проекта, а краткая карточка не заменяет адресное чтение записи.

Страницы задач этапа и планов релиза сохраняют порядок включения и загружают полные
карточки только выбранного окна. Total и ревизия владельца относятся к тому же снимку;
существование ссылок всего состава проверяется отдельно по лёгким идентичностям.
