# Документация для читателя

Документ помогает человеку понять компонент, воспользоваться им или принять решение
при разработке. Содержание выбирается под эту задачу, а не по списку исходных файлов.
Текст пишется по-русски; имена пакетов, API, команд и параметров сохраняются.

## Ответственность документов

| Документ                     | Что получает читатель                                         |
| ---------------------------- | ------------------------------------------------------------- |
| Корневой README              | Назначение Relay, решаемые задачи и первый шаг                |
| README приложения или пакета | Назначение компонента, условия использования и рабочий пример |
| AGENTS.md                    | Правила изменения кода в своей области                        |
| Архитектура                  | Границы компонентов, их взаимодействие и принятые решения     |
| Руководство пользователя     | Подробные сценарии, команды и особенности поведения           |
| Стайлгайды                   | Общие требования к коду, тестам и документации                |
| TSDoc                        | Контракт конкретного API: входы, результат, ошибки и гарантии |

У подробного правила один основной источник. В другом документе допустимы короткое
пояснение и ссылка на него. Результаты поручений, журналы проверок, исследования и
черновики сохраняются в `.artifacts/` по правилам проекта.

## README — паспорт компонента

README пишется для человека, который впервые встретил компонент. У внутреннего
пакета этим человеком обычно будет разработчик другого компонента Relay. Ему нужны
понятное назначение и условия применения, а не восстановление устройства по коду.

Перед написанием определите читателя и его следующий шаг. Затем раскройте сведения,
которые действительно помогут ему:

- что представляет собой компонент и какую задачу решает;
- кому и в каких ситуациях он нужен;
- как начать использование на небольшом примере;
- какие требования и особенности запуска, подключения или сборки существенны;
- какие ограничения влияют на использование;
- где находится дальнейшее руководство.

Это вопросы автору, а не обязательный набор заголовков. Приложение, библиотека,
конфигурационный пакет и заготовка требуют разного объёма и последовательности текста.
Пустые разделы и одинаковые вводные абзацы во всех пакетах не добавляются.

### Начало и основной текст

Первый абзац объясняет назначение обычным языком. Технологии появляются там, где
определяют требования или помогают понять применение. Термины раскрываются через
задачу и наблюдаемый результат.

Например, для библиотеки предметных правил:

> Core отвечает за правила работы с данными Relay: знаниями проекта, задачами,
> планами и историей работы. Он проверяет допустимость изменений и обеспечивает
> согласованное выполнение связанных операций.

Перечень «содержит сервисы, декодеры, валидаторы и helpers» такого объяснения не даёт.
README не используется как каталог файлов, список внутренних классов, описание
каждой функции, журнал реализации или отчёт о завершённом рефакторинге.

Возможности описываются через задачи читателя. Короткий список уместен, когда облегчает
выбор; длинный перечень технических деталей выносится в документ с соответствующей
ответственностью. Внутренний рефакторинг без изменения использования обычно не требует
обновлять README.

### Примеры и команды

Пример показывает один понятный результат и использует действующий публичный API.
Для команды указываются рабочий каталог, предварительные условия и результат.
Подстановочные значения должны быть очевидны и объяснены рядом.

- У приложения показывается короткий пользовательский сценарий.
- У библиотеки — подключение и использование с необходимым контекстом и освобождением
  ресурсов, если пример их открывает.
- У пакета настроек — подключение подходящего профиля.
- У заготовки — назначение и текущая доступность; будущие API не изображаются рабочими.

Пакету без самостоятельной сборки или запуска не добавляются искусственные инструкции.
Общие требования установки описываются в корне; локальный README ссылается на них и
добавляет особенности своего компонента. Полный каталог команд проверки принадлежит
руководству разработки, а не каждому паспорту.

### Актуальность и навигация

Реализованное поведение отделяется от целевого. Статус описывается через доступность
для читателя, без датированных отчётов и обещаний готовности.

Ссылки подбираются по следующему действию: изучить сценарий, понять архитектуру,
подключить соседний компонент или внести изменение. Подпись объясняет назначение
ссылки. Содержимое всех соседних документов в README не копируется.

## AGENTS.md — локальные правила работы

Корневой AGENTS.md содержит общие правила репозитория и обязательные ссылки на
стайлгайды. Файл приложения или пакета добавляет правила только для своей области:
границы ответственности, существенные инварианты и выбор проверок.

Локальные инструкции дополняют корневые. Их согласованность поддерживается явно;
нельзя рассчитывать, что более близкий файл автоматически отменит противоречащее
правило. Перед работой в компоненте агент читает его README и применимые инструкции.

Каждый пункт должен помогать принять конкретное решение. Например: «проверяй ревизию
содержания задачи до no-op; добавление комментария не меняет эту ревизию» полезнее
общего пожелания «сохраняй корректность данных».

В локальный файл не копируются стайлгайды, общие требования к языку, полный порядок
ревью или отчёты о прошлых задачах. README объясняет назначение компонента, поэтому
его пересказ в AGENTS.md также не требуется. Инструкция появляется на уровне
самостоятельной области ответственности; дополнительных файлов в каждом каталоге
исходников ради симметрии не создаётся.

Правила меняются вместе с действующим порядком работы. Создание и изменение
агентских инструкций требует прямого поручения пользователя согласно корневому AGENTS.md.

## Проверка документации

При ревью прочитайте документ без контекста поручения:

- понятны ли назначение и предполагаемый читатель с первых абзацев;
- можно ли выполнить показанный пример с описанными условиями;
- верны ли команды, пути, API и заявления о доступности;
- помогает ли каждая подробность использованию или принятию решения;
- сохранились ли единые владельцы правил и непротиворечивые ссылки.

Обновление требуется при изменении назначения, публичного поведения, способа
использования или правил разработки. Сам факт завершения задачи и успешные проверки
не являются основанием дописывать README. Вносите минимальную правку в соответствующий
существующий раздел; отдельный документ для каждого исправления не создаётся.
