# Стайлгайд TypeScript

Назначение кода, контракт данных и последовательность сценария должны быть понятны
без восстановления контекста разработки. Документация, декомпозиция и точные типы
входят в реализацию задачи.

Правила обязательны для нового и содержательно изменяемого TypeScript-кода CLI
и библиотек. Изменение функции включает приведение её документации и затронутых
контрактов к этим правилам. Приведение остального кода выполняется отдельными,
обозримыми изменениями; правка одного метода не требует переписывать весь пакет.

Границы пакетов определяет [архитектура](../ARCHITECTURE.md), правила проверки
поведения — [руководство по тестированию](TESTING.md). Форматирование выполняет
Prettier с конфигурацией репозитория.

## 1. Документирование функций

Каждая именованная функция и метод имеют многострочный блок документации TSDoc
на русском языке: открывающий `/**`, текст и закрывающий `*/` располагаются
на отдельных строках. Правило распространяется на публичные и внутренние функции,
приватные методы, явно объявленные конструкторы и функции, присвоенные переменным
или свойствам.

Документация раскрывает применимые к функции сведения:

- назначение;
- существенные ограничения входных данных;
- результат и смысл отсутствующего результата;
- побочные эффекты, включая изменение переданных объектов и владение ресурсами;
- ожидаемые ошибки и условия их возникновения;
- для мутаций — атомарность, владельца ревизии и поведение при отсутствии изменений
  (no-op);
- для составного чтения — гарантии согласованности и существенные ограничения
  стоимости, например загрузку полного набора перед фильтрацией.

Короткой функции достаточно одного предложения, но блок остаётся многострочным.
`@param`, `@returns`, `@throws` добавляются, когда поясняют контракт. Не нужно повторять
имя функции, очевидные типы или заполнять неприменимые разделы шаблона.

```ts
/**
 * Определяет закрытие принимающей стороны потока.
 *
 * Позволяет CLI корректно обработать прекращение чтения stdout,
 * например при передаче вывода в `head`.
 */
export function isBrokenPipe(error: unknown): boolean {
  return error !== null && typeof error === "object" && "code" in error && error.code === "EPIPE";
}
```

Короткие встроенные callbacks в `map`, `filter`, `find` отдельной документации
не требуют. Сложный callback выделяется в именованную документированную функцию.
Описание тестовых случаев и callbacks `test`/`describe` подчиняется
[правилам тестирования](TESTING.md#стиль-оформления-тестов); именованные
тестовые helpers документируются как функции.

Комментарии внутри функции объясняют причину решения или защищаемый инвариант:

```ts
// Проверяем исходную ревизию до no-op: устаревший запрос должен быть отклонён.
```

Комментарий обновляется вместе с поведением функции. Документация модуля описывает
его ответственность и границы; документация класса не заменяет контрактов методов.

## 2. Документирование типов и полей

Каждый именованный интерфейс и тип имеют многострочный блок TSDoc: открывающий
`/**`, текст и закрывающий `*/` располагаются на отдельных строках. Это относится
и к внутренним контрактам, объединениям и производным типам.

Поля интерфейсов, объектных типов и классов документируются однострочным блочным
комментарием `/* ... */` непосредственно над объявлением поля. Для полей используется
именно `/*`, без второй звёздочки; весь комментарий занимает одну строку.
Унаследованные поля документируются в исходном контракте.

Описание поля раскрывает его предметный смысл и применимые ограничения:

- ID это, ключ или пользовательская ссылка;
- формат и единицы измерения;
- допустимые значения и границы;
- смысл `null`, отсутствующего свойства, `undefined` и пустой коллекции;
- порядок и уникальность элементов, если они существенны;
- значение по умолчанию и место его применения, если оно предусмотрено.

```ts
/**
 * Проверенные параметры изменения родителя задачи.
 */
export interface SetTaskParentInput {
  /* Постоянный ID изменяемой задачи; ключи и алиасы уже разрешены. */
  readonly taskId: string;

  /* Постоянный ID нового родителя; null снимает связь с родителем. */
  readonly parentId: string | null;

  /* Ожидаемая ревизия содержания задачи; проверяется даже при неизменном родителе. */
  readonly ifRevision: number;
}
```

Описание `id` как «Идентификатор» недостаточно: нужно указать, что идентифицируется
и в какой области. Ограничения описываются у владельца правила; комментарий поля
может ссылаться на общий контракт вместо копирования его подробностей. Если описание
поля не помещается в одну строку с учётом ширины форматирования, подробные инварианты
выносятся в документацию типа, а у поля остаётся краткий смысл и ссылка на контракт.

Соглашения о типах:

- `interface` используется для именованных структур объектов;
- `type` — для объединений, производных типов и преобразований типов;
- входные поля и коллекции объявляются `readonly`, если функция не должна их менять;
- отсутствие свойства и `null` различаются осознанно и документируются;
- связанные варианты данных описываются discriminated union: значение `kind`
  определяет допустимую форму данных.

## 3. Типы отдельно от реализации

Именованные `interface` и `type` объявляются в отдельных файлах контрактов.
Аннотации параметров, результатов и локальных переменных остаются в реализации.

| Что описывает тип               | Где находится                                        |
| ------------------------------- | ---------------------------------------------------- |
| Переносимый предметный контракт | `packages/contracts`                                 |
| Внутренние данные сценария Core | Рядом со сценарием в `*.types.ts`                    |
| Детали хранения                 | В `packages/storage`, отдельно от реализации         |
| Локальный контекст проекта      | В `packages/project-runtime`, отдельно от реализации |
| Аргументы и представление CLI   | В `apps/cli`, отдельно от реализации                 |

- Типы одной предметной области группируются вместе; один интерфейс не требует
  отдельного файла.
- Общий файл `types.ts` на весь пакет не создаётся.
- Локальные типы не переносятся в `contracts` только ради отделения от реализации.
- Типовые зависимости подключаются через `import type` либо типовые спецификаторы
  `type` в смешанном импорте.
- Файл типов не импортирует реализацию сервиса. Зависимость от общей схемы или набора
  констант допустима, если они не зависят от сервиса.
- Типы, выводимые из схем и констант, остаются производными: вручную дублировать их
  структуру или перечень значений нельзя.
- Сложные повторяющиеся объектные аннотации получают имя и размещаются в файле типов.

Возможное устройство предметного модуля:

```text
packages/core/src/
  tasks.ts           # Оркестрация предметных сценариев
  task-input.ts      # Проверка и преобразование внешнего ввода
  task-rules.ts      # Чистые предметные правила
  task-graph.ts      # Расчёт графа
  task.types.ts      # Внутренние контракты
  task.messages.ts   # Тексты диагностик
```

Это пример распределения ответственности, а не обязательный набор файлов.
Каждый файл появляется при наличии соответствующей ответственности.

## 4. Декомпозиция по ответственности

Одна функция выполняет один понятный шаг на одном уровне детализации. Оркестратор
сценария связывает предметные шаги, а их подробности находятся в соответствующих
модулях.

Типичная последовательность сценария:

1. Проверить форму входа.
2. Получить согласованное состояние.
3. Разрешить ссылки.
4. Проверить предметные ограничения.
5. Рассчитать изменение.
6. Сохранить результат.

Проверка состояния и запись сохраняют общую транзакцию там, где это требуется.
Декомпозиция также сохраняет согласованный снимок составного чтения, проверку
исходной ревизии до no-op и независимость журнала комментариев.

Различимые границы имеют:

- проверка внешнего ввода;
- декодирование сохранённых данных;
- чистые предметные правила и вычисления;
- запросы к хранилищу;
- оркестрация транзакции;
- форматирование результата.

Поводы пересмотреть декомпозицию:

- функция длиннее 60 строк или файл длиннее 400 строк;
- вложенность больше трёх уровней;
- несколько независимых причин изменения функции;
- крупные блоки разделены комментариями «теперь проверяем», «теперь сохраняем»;
- одинаковое предметное правило встречается в нескольких местах.

Численные пороги запускают ревью структуры, а не механическое дробление.
Декларативные схемы и таблицы оцениваются по смыслу. Выделенная функция имеет понятную
ответственность; однофункциональные обёртки без самостоятельного смысла не нужны.

Имена отражают действие и предмет: `resolveTaskReference`, `validateTaskTitle`,
`calculateTaskProgress`. Имена `process`, `handle`, `helper`, `utils` требуют уточнения
ответственности. Несколько позиционных boolean-параметров заменяются объектом
именованных настроек либо отдельными предметными операциями.

Общее правило имеет одного владельца. Чистые расчёты получают данные аргументами
и не обращаются к БД. Общий граф или индекс рассчитывается один раз на согласованный
снимок операции. Ограничение выдачи после полной загрузки не считается ограничением
стоимости чтения.

## 5. Тексты и предметные константы

Пользовательские сообщения, справка, подписи и тексты диагностик хранятся в словарях
отдельно от алгоритмов. Правило действует и для текста, используемого один раз.

```ts
// task.messages.ts

/**
 * Диагностики операций над задачами.
 */
export const taskMessages = {
  emptyUpdate: "Передайте хотя бы одно поле задачи",

  /**
   * Описывает несовпадение ожидаемой и сохранённой ревизий.
   */
  revisionConflict: (expected: number, actual: number): string =>
    `Ревизия задачи изменилась: ожидалась ${expected}, текущая — ${actual}`,
} as const;
```

Использование в реализации:

```ts
throw new RelayError("INVALID_ARGUMENT", taskMessages.emptyUpdate, 2);
```

Правила словарей:

- Ключи описывают смысл: `emptyUpdate`, `revisionConflict`.
- Сообщение хранится целиком; предложения не собираются из переводимых фрагментов.
- Динамические значения передаются через типизированные параметры либо механизм
  подстановок используемой библиотеки локализации.
- Словари группируются по предметным областям; общий словарь на весь проект
  не создаётся.
- CLI использует существующую структуру локализации в `apps/cli/src/locales`.
- Core хранит свои диагностики внутри своего пакета и не зависит от словарей CLI.
- Программная обработка ошибок опирается на стабильный код и структурированные
  данные, а не на текст сообщения.

Тексты для человека, предметные значения и технические литералы имеют разных
владельцев:

| Содержимое                                             | Размещение                              |
| ------------------------------------------------------ | --------------------------------------- |
| Сообщения, справка, подписи, диагностики               | Словари соответствующей области         |
| Статусы, наборы допустимых значений, предметные лимиты | Константы или схемы у владельца правила |
| SQL, имена свойств, технические идентификаторы         | Соответствующие технические модули      |

Лимиты вроде `1024` и `256 * 1024` получают предметные имена и одного владельца,
если выражают правила системы. Одинаковое числовое значение само по себе не делает
два ограничения одним правилом.

Названия тестов, данные fixtures и ожидаемые тексты в проверках не являются
пользовательским словарём. Их размещение определяется читаемостью и независимостью
проверки по [руководству тестирования](TESTING.md).

## 6. Типизация и читаемость

- У именованных функций явно указывается возвращаемый тип.
- `unknown` используется на внешних границах и при декодировании хранения; после
  проверки данные получают предметный тип.
- `Record<string, unknown>` не проходит через весь сценарий вместо проверенного
  входного контракта.
- `any`, утверждения типов через `as` и оператор `!` не заменяют проверку данных.
  Вынужденное применение обосновывается конкретным инвариантом или ограничением
  стороннего API. `as const` используется для сохранения литеральных типов.
- Ветвления оформляются с фигурными скобками.
- Вложенные тернарные выражения заменяются понятными условиями или именованным
  вычислением.
- Неожиданные ошибки и повреждённые данные не превращаются в пустую коллекцию,
  пустую строку или успешный результат.
- Ошибка преобразуется на границе с сохранением причины.

## 7. Проверка соблюдения

Механические правила проверяются существующими Prettier, Oxlint и TypeScript
в пределах их конфигурации. Добавление правила в этот документ не означает,
что соответствующая автоматическая проверка уже настроена. Недостающие проверки
добавляются отдельно; смысловые требования проверяются на ревью.

При ревью изменения проверяются:

- содержательность и актуальность документации функций и полей;
- разделение контрактов и реализации;
- размещение пользовательских текстов в словарях;
- связность модулей и понятность последовательности сценария;
- единый владелец предметного правила;
- сохранение транзакционных гарантий;
- стоимость обращений к хранилищу.

Проверки поведения выбираются по риску изменения согласно
[руководству тестирования](TESTING.md). Успешные автоматические проверки
не заменяют ревью контрактов и структуры.
