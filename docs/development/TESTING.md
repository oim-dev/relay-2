# Написание и сопровождение тестов

Тест защищает наблюдаемое поведение или предметный инвариант. Его ценность определяется
ошибкой, которую он обнаружит, и стоимостью выполнения и сопровождения.
Зелёный набор и высокий процент покрытия строк сами по себе не доказывают достаточность
проверок. Карту существующих гарантий см. в [TEST-COVERAGE.md](TEST-COVERAGE.md),
размещение и команды — в [руководстве наборов](../../tests/README.md).

## От поведения к проверке

Перед добавлением или изменением теста:

1. Определите ожидаемое поведение по требованиям и публичному контракту. Текущая
   реализация не является единственным источником правильного ответа.
2. Сформулируйте конкретное нарушение: что может пойти неправильно и кто это заметит.
3. Найдите существующие проверки этой гарантии, включая соседние пакеты и уровни.
4. Выберите самый дешёвый уровень, способный достоверно воспроизвести риск.
5. Определите значимые утверждения и минимальное допустимое начальное состояние.

При неоднозначном контракте сначала уточняется ожидание. Тест не должен случайно
закреплять ошибку реализации как требование.

Рассматривайте классы входов, границы, переходы состояний, no-op, отказ без записи,
конкурентность и повторное открытие **по смыслу сценария**. Этот перечень не требует
создавать все виды проверок для каждой функции. Для одинакового правила достаточно
представителей существенных классов; все сочетания параметров нужны только там,
где их взаимодействие действительно меняет поведение.

## Один владелец гарантии

Подробные варианты правила проверяются у его владельца. Дополнительный уровень
защищает собственную границу, а не повторяет весь нижележащий набор.

Например, для конфликта ревизии:

- Storage проверяет CAS и конкурентную запись в реальной SQLite.
- Core проверяет ревизию правильного владельца и атомарность предметного изменения.
- CLI проверяет передачу ожидаемой ревизии, код ошибки и потоки вывода.
- Сквозной маршрут может включать один конфликт, подтверждая работу поставляемого бинарника.

Чистый расчёт графа не требует запуска бинарника. Проверку rollback нельзя заменить
mock хранилища. Реальная SQLite в интеграции оправдана защищаемой гарантией, а не
стремлением все тесты сделать максимально похожими на production.

## Структура и русское описание

Название теста описывает условие и наблюдаемый результат: «устаревшая ревизия
отклоняется без изменения документа», а не «update работает» или «тест ошибки».
`describe` обозначает область или правило. Название табличного случая позволяет
понять из сообщения runner, какой вариант упал.

В теле различимы подготовка, проверяемое действие и утверждения. Один тест проверяет
одну связную гарантию: для атомарности нормально проверить ошибку, обе записи,
ревизии и поколение. Независимые истории разделяются; законченный пользовательский
маршрут остаётся связным в сквозном наборе.

Комментарии на русском объясняют неочевидное: почему нужен второй процесс, где
внедряется отказ, какой снимок должен увидеть читатель. Нетривиальный fixture/helper
документирует владение ресурсами, очистку, создаваемое состояние и встроенные проверки.
Комментарии «подготовка / действие / проверка» и TSDoc у каждого очевидного теста
не являются обязательной формальностью.

## Сила утверждений

- Проверяйте существенное значение, связь или изменение состояния. `ok: true`,
  наличие поля и число вызовов не заменяют проверку результата сценария.
- Ожидаемый результат независим от проверяемого алгоритма. Не получайте его вызовом
  того же алгоритма или копированием его реализации в тест.
- Отрицательный случай должен отвергать правдоподобную постороннюю ошибку:
  проверяйте предметный код, а для CLI также ожидаемый exit code и нужный поток.
  Полный текст сообщения фиксируйте, только когда его формулировка является контрактом.
- Для отказа мутации проверяйте сохранность затронутых данных; для составной записи —
  отсутствие частичного сохранения. Не проверяйте все таблицы в каждом тесте без причины.
- Вызовы внутренних функций проверяются лишь тогда, когда это выражает отдельную
  гарантию, например отсутствие повторного полного чтения графа. Такой тест должен
  переживать смену внутренних имён и не фиксировать произвольный порядок SQL-команд.
- Небольшой snapshot стабильно отображаемого результата допустим. Большие снимки
  с UUID, датами и путями не должны подменять точечные смысловые утверждения.

Пример для файла в `apps/cli/tests/integration/`, использующий существующий fixture:

```ts
import { expect, test } from "bun:test";
import { KnowledgeService } from "@relay/core";
import { withCliFixture } from "./helpers/cli-fixture";

test("устаревшая ревизия CLI отклоняется без потери актуального текста", async () => {
  await withCliFixture(async (cli) => {
    const project = cli.createProject();
    const { initial, current } = cli.withDatabase(project, (db) => {
      const knowledge = new KnowledgeService(db);
      const initial = knowledge.create("feature", { name: "Поиск" }, "author");
      const current = knowledge.update(
        "feature",
        initial.id,
        { description: "Актуальное содержание" },
        { actor: "editor", ifRevision: initial.revision },
      );
      return { initial, current };
    });

    const error = await cli.error(
      [
        "feature",
        "update",
        initial.key,
        "--description",
        "Устаревшее содержание",
        "--if-revision",
        String(initial.revision),
      ],
      4,
    );

    expect(error.code).toBe("REVISION_CONFLICT");
    const stored = cli.withDatabase(project, (db) =>
      new KnowledgeService(db).get("feature", initial.id),
    );
    expect(stored).toEqual(current);
  });
});
```

`cli.error` уже проверяет exit code, пустой stdout и форму JSON-ошибки. Повторять
эти утверждения в каждом вызове helper не нужно. Проверка конкретного кода и
сохранности предметных данных остаётся видна в самом тесте.

## Подготовка данных и независимость

Fixture создаёт минимальное валидное состояние. В тесте CLI его можно подготовить
через Runtime/Core, чтобы подготовка не выполняла десятки лишних CLI-команд.
Низкоуровневая вставка неполных сущностей допустима для проверки повреждения или
механизма Storage; её назначение должно быть явно обозначено.

Helpers имеют конкретного владельца и понятные эффекты. Они не подставляют свежую
ревизию вместо переданной, не поглощают ошибки и не выполняют скрытую бизнес-операцию.
Не превращайте fixtures в отдельный универсальный framework.

Изоляция окружения, закрытие ресурсов и синхронизация конкурентных участников
описаны в [руководстве наборов](../../tests/README.md#изоляция-и-подготовка-данных).
Случайные данные требуют воспроизводимого seed. Зависимость от времени или порядка
тестов устраняется в причине; retries и произвольный `sleep` не являются исправлением.

## Дублирование, стоимость и устаревание

Перед удалением или объединением теста назовите гарантию, оставшийся тест и
дополнительный риск удаляемого уровня. Похожая подготовка или одинаковый вызов
команды не доказывают дублирование. Перенос проверки на более дешёвый уровень
допустим, если необходимые реальные механизмы остаются проверенными.

Сначала сокращайте ненужную подготовку, процессы и повторные вычисления, затем
увеличивайте параллельность. Измеренную длительность отличайте от предположения
по исходникам; учитывайте кеш Turbo и время сборки отдельно от тестового действия.

Возраст теста не делает его устаревшим. Пересмотр нужен при отмене контракта,
замене внутренней детали без изменения поведения, недопустимом fixture или
исключении теста из штатного запуска. Старый регрессионный случай сохраняется,
пока действует его инвариант. Обновление ожиданий после падения требует объяснения
изменившегося контракта; `skip`, ослабление assert и увеличение timeout не заменяют его.

## Проверка изменения и ревью

Автор выбирает адресный набор по изменённому поведению и зависимостям. Родительский
агент и ревьювер используют общий план запусков: команда, область, состояние кода,
результат и при необходимости лог. Успех на другом состоянии кода не подтверждает
текущее изменение. На неизменившемся состоянии повтор нужен из-за конкретного
сомнения, исследования нестабильности или непокрытого риска, а не для формального одобрения.

`relay-test-reviewer` проверяет реализацию вместе с тестами, даже если diff не содержит
тестовых файлов. Его режимы: ревью изменения, аудит функции и аудит набора.
Он сопоставляет гарантию с проверкой, оценивает способность обнаружить ошибку,
дублирование, актуальность и стоимость. Полномочия включают запуск проверок и исправления.

Наличие теста, его актуальный успешный запуск и достаточность утверждений — разные
свидетельства. Покрытие строк помогает находить места для исследования, но не задаёт
универсального порога качества. Точечная проверка чувствительности теста допустима
при сложном инварианте; массовый мутационный прогон не требуется на каждое изменение.

Нагрузочные сценарии и показатели пропускной способности относятся к
[отдельному ручному исследованию CLI](CLI-PERFORMANCE.md). Их реализация и запуск
не являются автоматическим следствием найденного пробела в функциональных тестах.
