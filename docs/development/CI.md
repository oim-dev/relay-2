# Локальная проверка и CI

Перед отправкой изменений выполняйте из корня checkout:

```sh
bun run check
```

Команда проверяет закреплённые Bun и Node.js, наличие Git, выполняет
`bun install --frozen-lockfile`, затем одним Turbo-запуском проверяет форматирование,
lint, типы, конфигурацию CI, сборки и все штатные unit/integration/process/E2E наборы
на текущей ОС. При любой ошибке возвращается ненулевой код. Новые и незакоммиченные
файлы участвуют в проверке рабочего дерева.

Независимые задачи выполняются параллельно. Потребитель ожидает только необходимые
сборки; после отказа производителя его проверки не запускаются на старом `dist`.
Остальные независимые проверки продолжаются. Одна задача графа исполняется один раз.
По умолчанию одновременно работают четыре задачи:

```sh
bun run check --concurrency=2
```

Допустимы значения 1–32. Фильтры компонентов, `--affected` и перечни отдельных задач
полный `check` не принимает. Адресные команды остаются доступны для разработки,
но не заменяют полный прогон перед отправкой окончательного состояния кода.

Вывод и итог остаются в терминале. Сам check не создаёт отчётов, сводок или файлов
результата. Сборки создают обычные `dist`, Turbo использует свой кеш, а изолированные
тестовые fixtures следуют [правилам наборов](../../tests/README.md#изоляция-и-подготовка-данных).
Настоящие пользовательские службы и расширенные репликационные проверки сохраняют
отдельные явные команды; нагрузочные сценарии не входят в штатный контур.

## Один источник проверок

`package.json` компонента содержит leaf-команды: каждая выполняет только свою работу.
Unit-тесты CLI не запускают unit Core; SDK typecheck не пересобирает vendor output.
Порядок получения артефактов задан в `turbo.json` и сверяется с общим каталогом
`scripts/verification/catalog.ts`. Нативные бинарники и проверки выполняются заново;
переносимые сборки SDK/Web могут восстанавливаться из кеша.

Guard принимает для lint единый `bun --bun oxlint --deny-warnings .`, а для typecheck —
`tsc --noEmit` под Node либо `bun --bun tsc --noEmit`; дополнительные профили задаются
через `-p <tsconfig.json>` и `&&`. Новая форма quality-команды требует явного изменения
этого контракта, а не добавления скрытой сборки перед проверкой.

CI вызывает те же package scripts через `bun run ci:task <component> <task> <target>`.
Этот служебный вход не собирает отсутствующие зависимости. В CI они предварительно
получаются от единственного build job. `check` сам организует их локальную сборку.
Версии инструментов имеют источники `.bun-version` и `.node-version`.

## Добавить или изменить набор

1. Разместите тесты у владельца и объявите соответствующий `test:*` script.
2. Для новой операции или артефакта обновите каталог и зависимости Turbo.
3. Выполните `bun run ci:generate` и просмотрите изменение `.github/workflows/ci.yml`.
4. Выполните полный `bun run check`.

`verify:configuration` входит в check и CI: он обнаруживает потерянный script
существующего набора, пустой job, скрытую вложенную сборку, несовпадение prerequisites
и устаревший главный workflow. Тест графа сопоставляет реальные задачи Turbo с CI.
Самостоятельный тестовый shell-путь в reusable workflows также отклоняется.
Workflows остаются обычными YAML, доступными для ревью; генератор не эмулирует runners.

## Задания CI

Основной workflow запускается для PR, push в `main` и вручную. Push feature-ветки
не создаёт второй автоматический запуск того же PR. Новый commit отменяет устаревший
запуск. Итоговый `CI / Result` требует успеха всех обязательных jobs, включая службы;
отменённая или заблокированная зависимость не считается успешной проверкой.

- `<компонент> / Quality`: lint и types отдельными шагами на Linux.
- `<компонент> / unit|integration / <target>`: собственный непустой набор.
- `REST SDK / build / portable` и `Web / build / portable`: по одному результату JS/assets.
- `CLI|Server|Git Sync / build / <target>`: по одному executable на target.
- `<приложение> / process / <target>`: поставленный бинарник и нужные тестовому набору артефакты.
- `CLI / e2e / <target>`: пять локальных пользовательских маршрутов.
- `Repository / e2e:product / <target>`: четыре межприложенческих маршрута.
- `Native services / <target>`: настоящий менеджер на одноразовой пользовательской сессии.

Первичная матрица — Linux x64 (`ubuntu-24.04`), Windows x64 (`windows-2025`),
macOS ARM64 (`macos-15`). Существующее исполнение unit/integration на трёх ОС сохранено:
чистые тесты можно выделять из native-наборов отдельным обоснованным изменением.
У каждого target собственная цепочка build → tests; Windows-отказ не блокирует Linux.

Jobs показывают отдельно setup, восстановление зависимостей, исполнение и передачу
результата. `ci:task` добавляет время самой команды в GitHub step summary.
Кеш загрузок Bun разделён по ОС, архитектуре и lock-файлу; `node_modules` не передаётся
между runners. Бинарники передаются в tar с сохранением executable permissions.

## Сборочные артефакты и службы

Артефакт адресуется компонентом, target и commit SHA. Потребитель проверяет metadata
и архив перед распаковкой. Отсутствие, другой SHA/target или повреждение завершают job
ошибкой без скрытой пересборки. Web и SDK переносимы; executable привязан к native target.

Native-службы используют готовые CLI/Git Sync. Переменные репозитория
`RELAY_NATIVE_LINUX_RUNNER`, `RELAY_NATIVE_MACOS_RUNNER`, `RELAY_NATIVE_WINDOWS_RUNNER`
могут выбрать подходящие одноразовые runners. Preflight требует существующую пользовательскую
сессию. Ручной `Native Services` принимает target, runner и ID сборочного run того же commit.
Условия и ограничения описаны в [руководстве native-набора](../../packages/project-runtime/tests/native/README.md).

Release получает проверенные артефакты того же commit; при отсутствии подходящего
успешного CI запускает этот же reusable CI. Упаковка и публикация не пересобирают
уже проверенные бинарники. Релизный workflow отделён от обычного локального check.
