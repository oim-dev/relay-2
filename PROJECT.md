# Relay: направление новой версии и источники знаний

Документ сохраняет результат архитектурного обсуждения и контекст переписывания.
Его нужно обновлять при принятии новых решений. Описанная целевая архитектура
не означает, что соответствующие возможности уже реализованы.

## 1. Что мы делаем сейчас

В `~/projects/my/relay-2` рефакторим Relay: создаём новую реализацию на Bun,
пересматриваем технические подходы и стремимся повысить производительность.
Подготовлен каркас: монорепозиторий, приложения и пакеты-заглушки, сборка бинарников,
типизация, форматирование, lint и раздельные точки запуска тестов.

Текущий этап — перенос основного функционала и создание рабочей CLI вместе с нужными
ей предметной логикой и локальным хранением. Server, Web и MCP сейчас не реализуем
и не поддерживаем; к ним переходим только после переноса основного функционала
и появления рабочей CLI. IPC, установщик и миграция старых данных также отложены.
Git-синхронизация предусмотрена отдельным компонентом; очерёдность её реализации
определяется задачами переноса.

Исходный проект находится в `/home/gromov/projects/my/relay` (`../relay`) и служит
источником знаний о продукте, сценариях и проблемах. Примерная архитектура новой
реализации описана в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## 2. Назначение продукта

Relay — общая рабочая память проекта для людей и AI-агентов. Основные области:

- паспорт продукта, фичи, сценарии, приложения и их реализации;
- документы и библиотека знаний;
- доски, задачи, критерии приёмки, комментарии и зависимости;
- планы, этапы и релизы;
- предметная история агентской работы;
- связи, контекст, поиск и вычисляемый прогресс;
- несколько проектов и workspace-наборы.

Relay хранит знания и состояние работы. Фактические изменения кода, выполнение тестов
и выпуск программ выполняются внешними инструментами. Сохранённый статус сам по себе
не доказывает выполнение или проверку работы.

## 3. Согласованная основа

- **Turborepo** для организации монорепозитория и графа задач.
- **Bun** как runtime, менеджер зависимостей и основа сборки самостоятельных бинарников.
- Relay **устанавливается** на ПК пользователя или в среду выполнения. Основной вход —
  команда `relay` в PATH; установка и обновление являются отдельными операциями.
- CLI, Server и фоновые сервисы запускаются отдельными бинарниками согласованного выпуска.
- **Server, Web и MCP отложены** до переноса основного функционала и рабочей CLI.
  Архитектура будущего MCP пока не определена.
- Сейчас интерфейс людей и агентов — CLI. В целевой архитектуре основной интерфейс
  агента — CLI, человека — Web.
- **10+ человек над одним проектом** — базовый сценарий: независимые копии, конкурентные
  изменения, offline-работа и публикация в общий Git origin.
- Тестирование должно быть качественным, быстрым и структурированным. Наборы различаются
  по назначению; тесты поведения не подменяются фиктивными проверками заглушек.

## 4. Приложения

Сейчас в репозитории присутствуют заглушки CLI и Sync. Разработка сосредоточена на переносе
основного функционала в CLI. Server, Web и MCP добавим после этого; ниже указан целевой
состав приложений с уже намеченными границами. Место MCP в нём ещё предстоит определить.

| Каталог       | Поставка            | Целевая ответственность                                             |
| ------------- | ------------------- | ------------------------------------------------------------------- |
| `apps/cli`    | `relay`             | Предметные команды, выбор проекта, запуск компонентов и диагностика |
| `apps/server` | `relay-server`      | REST API, SSE, несколько проектов и раздача Web                     |
| `apps/web`    | Статические ресурсы | Интерфейс человека; целевая поставка вместе с Server                |
| `apps/sync`   | `relay-sync`        | Git-обмен, подготовка объединения, конфликты и доставка изменений   |

Дополнительные воркеры выделяются при появлении конкретной ответственности и необходимости
отдельного процесса. Playground — окружение разработки с изолированными проектами.

Core остаётся библиотекой, включаемой в бинарники. CLI, Server и Sync выполняют предметные

Отдельный `server-runtime` в стартовый состав не включён: HTTP-реализация принадлежит

Конкретные интерфейсы Core/Storage ещё предстоит определить.

## 6. Локальные данные и взаимодействие процессов

Обсуждаемое направление хранения — **SQLite в режиме WAL через `bun:sqlite`**.
Выбор одной общей БД пользователя или отдельных БД локальных экземпляров проектов
остаётся открытым. Схема ещё не реализована и нагрузочными измерениями не подтверждена.

```text
CLI ─────────────────────→ Core → Storage → локальная SQLite
                              ↑
Web → Server / REST ───────────┤
                              │
Sync ─────────────────────────┘
  ↕
Git origin
```

У разных участников свои локальные базы. На одном хосте несколько бинарников могут
открывать собственные соединения к одной базе. WAL допускает параллельное чтение и запись,
но активный писатель у одного файла БД только один.

Предлагаются короткие транзакции, адресные изменения и проверка исходных ревизий.
Git, сеть и подготовка тяжёлого объединения выполняются вне транзакции записи.
Синхронный API `bun:sqlite` требует учитывать блокировку вызывающего JS-потока сервера.

Для управления локальными процессами обсуждался IPC: сокет или именованный канал.
Назначение — готовность, версии, уведомление о работе и остановка. Точный транспорт,
жизненный цикл сервисов и механизм доставки изменений Server ещё не утверждены.
Предложение для обнаружения пропущенных уведомлений — сохранённые поколения данных;
Web получает уведомления через SSE. Успех локальной записи не зависит от доступности origin.

## 7. Git-синхронизация и команда

Git хранит переносимые текстовые данные проекта. Рабочий файл SQLite, WAL, SQL-индексы
и локальные привязки каталогов в обмен не входят.

Обсуждаемая модель:

1. Core сохраняет локальную операцию и поколение данных атомарно.
2. Sync независимо получает удалённые изменения.
3. Общий предок, локальная и удалённая версии используются для предметного объединения.
4. Core проверяет итоговые сущности, связи и инварианты.
5. Применение сверяет исходное локальное поколение. Новые локальные изменения требуют
   пересчитать кандидат, а не затереть актуальную базу.
6. При конкурентном отказе push повторяется транспортное согласование уже сохранённых
   изменений. Пользовательская мутация повторно не исполняется.

Предлагаемый формат — текущее состояние с отдельными записями по постоянным ID,
детерминированным экспортом и историей Git. Точный формат файлов и модель распределённых
ревизий остаются открытыми. Часы компьютеров и максимум числовой ревизии не выбирают
победителя между независимыми изменениями.

Коллизии значений одного поля, удаление против редактирования и нарушение инвариантов
требуют явной политики конфликта. Конфликт участника не должен блокировать работу всей
команды. Частоту локальных сохранений отделяем от частоты пакетной отправки в origin.

## 8. Постоянные ID и предварительные ключи

Пользователь предложил и согласовал направление: **читаемый ключ предварительный до
подтверждения назначения в общей ветке данных origin**.

- Постоянный ID сущность получает сразу. Структурированные связи опираются на ID.
- Локальные ключи выдаются последовательно и явно обозначаются предварительными.
- Если два участника создали `DOC-13`, первая принятая origin публикация закрепляет номер.
  Другая сущность получает следующий свободный предварительный ключ и публикуется заново.
- Подтверждённые назначения при обычной синхронизации не перенумеровываются.
  Удалённые назначения резервируются, чтобы ключ не начал указывать на другую сущность.
- Подтверждение ключа отделено от синхронизации содержания: документ с постоянным ключом
  может иметь новые локальные изменения.
- Потеря ответа push требует проверки origin; локальный коммит и запуск Sync недостаточны
  для подтверждения ключа.
- Постоянный адрес на основе ID доступен до первой публикации. Читаемый ключ имеет
  область действия конкретного проекта.

Core должен разрешать пользовательские текстовые ссылки в ID и показывать актуальные ключи.
Для устаревшего редактора и CLI-ввода нужна проверяемая карта ключей, чтобы перенумерация
не перенаправила запись на чужую сущность. Синтаксис хранения ссылок ещё не выбран.

Для проектов без origin предложено обозначение «локальный ключ». Точные правила позднего
подключения origin, смены общей истории и восстановления реестра ещё предстоит определить.
Гарантия закрепления предполагает сохранение канонической истории назначений.

## 9. Восстановление и миграции

Синхронизация изменяет строки существующей SQLite; пересоздавать базу при каждом обмене
не требуется. Даже полный Git-снимок можно применить как набор изменений.

Восстановление после удаления БД возможно до сохранённого в Git состояния:

- изменения только в SQLite требуют отдельной согласованной резервной копии;
- локальный Git-коммит позволяет восстановиться без origin, если сам репозиторий сохранён;
- опубликованный коммит доступен для восстановления на другой машине.

Предлагается импорт в подготовительную базу с построением индексов, сохранением ID,
ревизий и ключей, проверкой Core и подключением готового результата. Отсутствующая база
обозначается состоянием восстановления, а не готовым пустым проектом.
Скорость восстановления ещё не измерена.

Версии приложения, SQL-схемы и переносимых данных — разные уровни. Политика совместимости,
автоматических миграций, резервирования и поддержки старых баз остаётся открытой.

## 10. Тестирование и производительность

Для каркаса выбран Bun test. Организация наборов описана в [tests/README.md](tests/README.md).

- Модульные тесты проверяют правила без запуска процессов.
- Интеграционные работают с реальными изолированными БД и Git-репозиториями.
- Процессные запускают собранные бинарники и проверяют потоки, сигналы и восстановление.
- Сквозные проверяют пользовательские сценарии CLI; API/Web добавятся на следующих этапах.
- Измерения производительности выполняются отдельно от обычных быстрых тестов.

Ключевой будущий сценарий: 10+ изолированных экземпляров с собственными БД и клонами,
общим origin, конкурентными изменениями, коллизиями ключей, offline и перезапусками.
После обмена и разрешения конфликтов предметные состояния должны совпадать без потери
принятых изменений и целостности ссылок.

Нужно измерить запуск бинарников, p95/p99 операций, ожидание записи, память, размер WAL,
отзывчивость HTTP при синхронизации и восстановление разных объёмов данных. Значения SLA
и превосходство нового решения пока не установлены.

## 11. Открытые решения перед предметной реализацией

- Общая SQLite пользователя или отдельные базы локальных экземпляров проектов.
- Разделяют ли клоны/worktree одного проекта данные на одном хосте.
- Серверный стек и точный контракт REST/SSE; перенос прежнего NestJS не утверждён.
- Формат Git, модель ревизий, единица конфликтов и атомарность их применения.
- Реестр подтверждённых ключей, скрытые текстовые ссылки и контекст устаревшего клиента.
- Атомарный batch API и гарантии повторной доставки пакета.
- IPC, запуск и остановка сервисов, готовность и совместимость активных процессов.
- Установка и обновление бинарников на поддерживаемых платформах.
- Миграция существующих данных и резервирование ещё не опубликованных изменений.
