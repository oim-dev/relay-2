# Relay: направление новой версии и источники знаний

Документ сохраняет результат архитектурного обсуждения и контекст переписывания.
Его нужно обновлять при принятии новых решений. Описанная целевая архитектура
не означает, что соответствующие возможности уже реализованы.

## 1. Что мы делаем сейчас

В этом репозитории рефакторим Relay: создаём новую реализацию на Bun,
пересматриваем технические подходы и стремимся повысить производительность.
Локальные сценарии реализуются через CLI на Gunshi, предметные сервисы Core и SQLite.
В монорепозитории настроены сборка бинарников, типизация, форматирование, lint и
раздельные точки запуска тестов. Пользовательские команды и размещение данных
описаны в [руководстве CLI](docs/CLI.md).

Текущий этап объединяет локальную CLI, единый асинхронный исполнитель предметных
команд и Git-обмен независимых реплик. CLI остаётся пользовательским интерфейсом,
включая workspace и управление `relay git-sync`. Обычные команды работают локально
без Server и origin. Из первой версии переносим сценарии и предметные правила;
CLI на Commander заново не воспроизводим.
Server, Web, MCP, PostgreSQL/API, `packages/rest-sdk`, установщик и миграция старых
данных отложены. Подробное одобренное направление Git Sync сохранено в
[DESIGN](GIT-SYNC-DESIGN.md), нормативная цель реализации — в
[SPEC](GIT-SYNC-IMPLEMENTATION-SPEC.md). Наличие отдельных команд не означает
завершённую приёмку всех требований этого этапа.

Исходный проект находится в `/home/gromov/projects/my/relay` (`../../my/relay`) и служит
источником знаний о продукте, сценариях и проблемах. Границы новой
реализации описаны в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## 2. Назначение продукта

Relay — общая рабочая память проекта для людей и AI-агентов. Основные области:

- паспорт продукта, фичи, сценарии, приложения и их реализации;
- документы и библиотека знаний;
- доски, задачи, критерии приёмки, комментарии и зависимости;
- планы, этапы и релизы;
- предметная история агентской работы;
- связи, контекст, поиск и вычисляемый прогресс;
- несколько проектов и workspace-наборы.

Relay хранит знания и состояние работы. Фактические изменения кода, выполнение тестов
и выпуск программ выполняются внешними инструментами. Сохранённый статус сам по себе
не доказывает выполнение или проверку работы.

## 3. Согласованная основа

- **Turborepo** для организации монорепозитория и графа задач.
- **Bun** как runtime, менеджер зависимостей и основа сборки самостоятельных бинарников.
- **Gunshi** для CLI: описание и разбор команд, справка и расширения контекста.
  Выбрана ветка 1.x; закреплена предварительная версия `1.0.0-rc.1` и согласованная
  версия `@gunshi/plugin-i18n`. Это release candidate, а не стабильный выпуск 1.0.
- Relay **устанавливается** на ПК пользователя или в среду выполнения. Основной вход —
  команда `relay` в PATH; установка и обновление являются отдельными операциями.
- CLI, Server и фоновые сервисы запускаются отдельными бинарниками согласованного выпуска.
- **Server, Web и MCP отложены** до переноса основного функционала и рабочей CLI.
  Архитектура будущего MCP пока не определена.
- Сейчас интерфейс людей и агентов — CLI. В целевой архитектуре основной интерфейс
  агента — CLI, человека — Web.
- Командная работа — независимые копии, конкурентные изменения, offline и одна общая
  Git-ветка данных. Приёмка включает конечные сценарии **50 независимых реплик**;
  это проверка корректности, а не обещание измеренной производительности.
- Тестирование должно быть качественным, быстрым и структурированным. Наборы различаются
  по назначению; тесты поведения не подменяются фиктивными проверками заглушек.

## 4. Приложения

Локальная CLI на Gunshi предоставляет предметные команды и группу `git-sync`.
Отдельный `relay-git-sync` выполняет обмен, worker и supervisor. Корневая сборка
`build:cli` подготавливает оба компонента. Server, Web и MCP — последующие интерфейсы;
в таблице они обозначают целевую поставку, а не действующие приложения.

| Каталог         | Поставка            | Целевая ответственность                                             |
| --------------- | ------------------- | ------------------------------------------------------------------- |
| `apps/cli`      | `relay`             | Предметные команды, выбор проекта, запуск компонентов и диагностика |
| `apps/server`   | `relay-server`      | REST API, SSE, несколько проектов и раздача Web                     |
| `apps/web`      | Статические ресурсы | Интерфейс человека; целевая поставка вместе с Server                |
| `apps/git-sync` | `relay-git-sync`    | Git-обмен, конфликты, доставка, workers и supervisor                |

Дополнительные воркеры выделяются при появлении конкретной ответственности и необходимости
отдельного процесса. Playground — окружение разработки с изолированными проектами.

## 5. Пакеты и границы

| Каталог                      | Целевая ответственность                                                             |
| ---------------------------- | ----------------------------------------------------------------------------------- |
| `packages/contracts`         | Переносимые команды/результаты, command port, snapshots и процессные протоколы      |
| `packages/core`              | Предметные сценарии, инварианты, разрешение ссылок и атомарные пакеты               |
| `packages/storage`           | Локальная БД, запросы, репозитории, транзакции и технические миграции               |
| `packages/project-runtime`   | Локальный контекст, реестр, launcher/lifecycle и регистрация пользовательских служб |
| `packages/rest-sdk`          | Общий HTTP-клиент для Web и удалённого CLI; генерация из API планируется            |
| `packages/typescript-config` | Общие настройки TypeScript для библиотек, Bun и браузера                            |

Core остаётся библиотекой, включаемой в бинарники. CLI, Server и Git Sync выполняют предметные
изменения через Core. Contracts не зависит от Core, Bun, БД или React.
Приложения не импортируют исходники друг друга.

Отдельный `server-runtime` в стартовый состав не включён: HTTP-реализация принадлежит
`apps/server`. Git-синхронизация выделена из прежнего `project-runtime` в `apps/git-sync`.
Предметные writers Core возвращают Promise и используют общий `CommandExecutor`
через `CommandStore.load/commit`; реальный SQLite-порт доступен как `db.commands`.
Обычные предметные readers и чтение batch receipt остаются локальными и синхронными
через `ProjectStore`; отдельный async `getManyVersioned` возвращает прежнюю проекцию
и переносимые версии одного anchor. CLI показывает их через `get --with-versions`
в `meta.versions`; `--expected-version` и `--target-version` дополняют либо заменяют
числовые предусловия соответствующего владельца. Соединением и его закрытием
после `await` владеет приложение.
Базовый формат группового чтения и batch описан в [ТЗ CLI](CLI-GET-BATCH-SPEC.md);
единый executor и переносимые предусловия развиваются по ТЗ Git Sync.
Пользовательские сценарии описаны в
[руководстве CLI](docs/CLI.md#применить-связанный-пакет).

## 6. Локальные данные и взаимодействие процессов

Принято: **у каждого проекта своя локальная SQLite-база в режиме WAL через `bun:sqlite`**.
Предметные данные разных проектов хранятся в отдельных файлах БД. Это разделяет WAL
и блокировки записи при работе с несколькими проектами на одном ПК.
Схема имеет собственную версию; производительность требует нагрузочных измерений.

Project Runtime выбирает проект и путь к его БД. Конфигурация `relay.config.json` в корне проекта
привязывает рабочий каталог к постоянному ID. По умолчанию база создаётся и выбирается в
`RELAY_HOME/projects/<id>/project.sqlite`, где `RELAY_HOME` по умолчанию равен `~/.relay`.
Необязательный `databasePath` переопределяет это размещение; `init` сохраняет только
`version` и `projectId`.
Локальный `relay.workspace.json` содержит имена и пути каталогов независимых проектов
с обязательными собственными `relay.config.json`; удаление регистрации сохраняет данные.
Без явного пути конфигурации проверяется только текущий каталог запуска.
Автоматическое сопоставление Git-клонов
и worktree с проектами относится к последующим решениям.

```text
CLI ─────────────────────→ Core → Storage → SQLite выбранного проекта
                              ↑
Web → Server / REST ───────────┤
                              │
Git Sync ─────────────────────┘
    ↕
Git origin
```

У разных участников свои локальные базы проектов. На одном хосте несколько бинарников
могут открывать собственные соединения к БД одного проекта. WAL допускает параллельное
чтение и запись, но активный писатель у одного файла БД только один. Записи разных
проектов не конкурируют за одну SQLite-блокировку; ресурсы CPU, памяти и диска остаются общими.

Транзакции и атомарные пакеты ограничены БД выбранного проекта. Async load и чистый
расчёт отделены от короткого commit с проверкой исходных версий и предикатов.
Callback SQLite-транзакции остаётся строго синхронным; Promise вокруг command port
не разрешает удерживать её через `await`.
Git, сеть и подготовка тяжёлого объединения выполняются вне транзакции записи.
Синхронный API `bun:sqlite` требует учитывать блокировку вызывающего JS-потока сервера.

Одноразовый launcher передаёт `GitSyncRequest` через stdin `relay-git-sync --request`;
`--version` автономно проверяет выпуск компонента. Постоянный control-протокол
отдельно подтверждает конкретный instance, совместимость и readiness. Пропущенное
уведомление не теряет работу: источником истины остаётся durable outbox.
Явные `now`/refresh дополнительно имеют correlation ID: новый submit получает
`operationId` до spawn, а `requestId` используется только для ожидания/чтения.
Истёкшее ожидание не означает неготовность worker; bounded outcome с `unknown`
не подменяет подтверждение доставки или первоначальную batch receipt.

Workers принадлежат физическим локальным БД; одна БД в нескольких workspace имеет
одного владельца. Постоянных workers создаёт только долгоживущий supervisor,
восстанавливающий running-процессы и ограничивающий общий бюджет.
Runtime устанавливает пользовательский автозапуск только по явному
`service enable`: systemd --user на Linux, LaunchAgent на macOS, Task Scheduler
на Windows. Login и boot различаются; linger и повышенные права скрыто не включаются.
Без службы пользователь держит `relay git-sync supervise` в живом сеансе.
`worker start/restart` и `auto enable` требуют готового совместимого supervisor;
при его отсутствии `SUPERVISOR_REQUIRED` не меняет `mode`/`desired`. Короткий request
не создаёт постоянных демонов и не обходит Job/group cleanup. `connect`, `restore`,
`status` и ручной `now` работают без supervisor; остановленный worker заменяется
только одноразовой попыткой под lease. Native-границы уборки, включая
managed foreground process group на macOS, определены в SPEC; произвольное daemonize
custom helper не выдаётся за удерживаемое дерево.

## 7. Git-синхронизация и команда

Git хранит переносимые текстовые данные проекта. Рабочий файл SQLite, WAL, SQL-индексы
и локальные привязки каталогов в обмен не входят.

Согласованная модель:

1. Core через общий executor сохраняет эффекты, receipt и changeset одной транзакцией.
2. Git Sync независимо получает удалённые изменения.
3. Общий предок, локальная и удалённая версии используются для предметного объединения.
4. Core проверяет итоговые сущности, связи, неизменяемость и допустимость переходов.
5. Применение сверяет исходный локальный guard. Новые локальные изменения требуют
   пересчитать кандидат, а не затереть актуальную базу.
6. При конкурентном отказе push повторяется транспортное согласование уже сохранённых
   изменений. Пользовательская мутация повторно не исполняется.

Все участники используют одну общую ветку, без веток участников и отдельного
интегратора. Обычный fast-forward push публикует каноническое состояние по ID;
non-fast-forward требует новой подготовки тех же пакетов, а потерянный ответ —
проверки реального принятия. Force push не входит в протокол.
Экспорт сохраняет исходные данные, нормализованные части, тексты, адреса/резервы,
пользовательские квитанции и компактные подтверждения. Квитанция и ack имеют разные
назначения. Часы и максимум локального `revision` не выбирают победителя.
Формат, причинность и жизненные циклы подробно определяет SPEC.

Core выдаёт непрозрачный `ValidatedReplicationHistory` для проверенного пути
до точного immutable snapshot; его копия не даёт authority. Transport отдельно
проверяет Git parent/acceptance. Custom v1 исправляет только изменённые текстовые
поля существующего документа конкретной исходной boundary, сохраняя source digests,
immutable решение и receipt. Остальные эффекты changeset остаются атомарными.

Первое `connect` проверяет ветку без push/import; обмен выполняет `now`.
Новая копия из опубликованных данных создаётся `restore --remote` без прежнего connect.
Выбор origin/URL, служебный bare и самостоятельная история ветки данных объясняются
в [основном руководстве подключения](docs/CLI.md#git-синхронизация).

Конфликт одного поля или перехода удерживает весь changeset и его причинных потомков,
но независимые пакеты продолжают работу. Материалы base/local/remote сохраняются;
решение защищается fingerprint просмотренных версий. Явный `now` с оставшимся
конфликтом возвращает `SYNC_CONFLICT`, сохраняя независимо согласованные изменения.
Статус/readiness не подменяются утверждением о полной доставке.

## 8. Постоянные ID и предварительные ключи

Пользователь предложил и согласовал направление: **читаемый ключ предварительный до
подтверждения назначения в общей ветке данных origin**.

- Постоянный ID сущность получает сразу. Структурированные связи опираются на ID.
- Локальные ключи выдаются последовательно и явно обозначаются предварительными.
- Если два участника создали `DOC-13`, первая принятая origin публикация закрепляет номер.
  Другая сущность получает следующий свободный предварительный ключ и публикуется заново.
- Подтверждённые назначения при обычной синхронизации не перенумеровываются.
  Удалённые назначения резервируются, чтобы ключ не начал указывать на другую сущность.
- Подтверждение ключа отделено от синхронизации содержания: документ с постоянным ключом
  может иметь новые локальные изменения.
- Потеря ответа push требует проверки origin; локальный коммит и запуск Git Sync недостаточны
  для подтверждения ключа.
- Постоянный адрес на основе ID доступен до первой публикации. Читаемый ключ имеет
  область действия конкретного проекта.

Core разрешает пользовательские адреса в ID. CLI передаёт прочитанную привязку через
`--expected-addresses '[{"ref":"DOC-1","expectedId":"прочитанный-ID"}]'`.
После известного переназначения запись по ключу без guard отклоняется; постоянный ID
остаётся однозначным. Устойчивые Markdown ID-ссылки и запрет regexp-переписывания
текста определены в SPEC; обычное упоминание ключа остаётся текстом.

Гарантия закрепления предполагает сохранение канонической истории назначений.
Локальное подключение, восстановление и отказ от автоматической подмены общей истории
следуют контракту Git Sync.

## 9. Восстановление и миграции

Синхронизация изменяет строки существующей SQLite выбранного проекта; пересоздавать
базу при каждом обмене не требуется. Даже полный Git-снимок можно применить как набор изменений.

Восстановление после удаления БД возможно до сохранённого в Git состояния:

- изменения только в SQLite требуют отдельной согласованной резервной копии;
- локальный Git-коммит позволяет восстановиться без origin, если сам репозиторий сохранён;
- опубликованный коммит доступен для восстановления на другой машине.

`restore --remote … --branch …` создаёт подготовительную базу с сохранением ID,
переносимых версий, адресов и квитанций, проверяет её через Core и публикует привязку.
Существующая рабочая БД не заменяется. Отсутствующая база означает необходимость
явного восстановления, а не готовый пустой проект. Независимая восстановленная
реплика получает новый `replicaId` для последующих изменений.
После неопределённой публикации рабочая БД, staging и intent сохраняются вместе
с возможными поздними записями. Обычный повтор даёт `RESTORE_RECOVERY_REQUIRED`
до materializer, а не удаляет опубликованную БД и не выдаёт прежнее состояние
за результат нового remote-снимка.

Явный `restore --resume [--project-id ID]` завершает привязку фактически сохранённой
БД без fetch/материализации/ack/progress. ID берётся из выбранного конфига либо явно,
home не сканируется. Синхронный read-only validator Core проверяет данные, сохраняя
`replicaId`, поздние commits и outbox. `sourceCheckpoint: null` не заявляет новый Git HEAD.
Intent v2 запрещает старому reader v1 применять прежний rollback; сомнительное владение
означает сохраняющий отказ. Cleanup наблюдается отдельно, повтор после полной уборки
даёт `RESTORE_NOT_PENDING` (exit 3). Resume не требует supervisor; дальнейший обмен
запускается отдельными явными командами.

Версии приложения, SQL-схемы, переносимых данных и process protocol — разные уровни.
Технические миграции текущей SQLite и перенос JSON-хранилища первой версии — разные
сценарии. Будущий переход на PostgreSQL/API требует consistent snapshot, учёта pending,
Core validation, writer cutover и согласования с offline-репликами.

## 10. Тестирование и производительность

Для функциональных проверок выбран Bun test. Организация наборов, их владельцы,
изоляция и параллельность описаны в [tests/README.md](tests/README.md).

- Модульные тесты проверяют правила без запуска процессов.
- Интеграционные работают с реальными изолированными БД и Git-репозиториями.
- Процессные запускают собранные бинарники и проверяют потоки, сигналы и восстановление.
- Сквозные проверяют пользовательские сценарии CLI; API/Web добавятся на следующих этапах.
- Нагрузочные сценарии и измерения производительности выполняются только вручную
  по отдельному запросу, вне CI, `check` и `test:all`; их организация — в
  [benchmarks/README.md](benchmarks/README.md).

Ключевой функциональный сценарий — 50 независимых реплик с собственными БД и клонами,
общим origin, конкурентными изменениями, коллизиями ключей, offline, потерей ответа
push и восстановлением. Он проверяет конечную сходимость принятых данных, ID, ссылок
и receipts. Его нельзя выдавать за нагрузочное измерение 50 одновременных клиентов.
Смысловые утверждения и владельцев проверок связывает
[карта сценариев](docs/development/TEST-COVERAGE.md). Нативная CI-матрица включает
Linux, macOS и Windows; проверки генераторов не заменяют запуск на целевой ОС.

Отдельный локальный сценарий — 10+ проектов на одном ПК, каждый со своей БД:
проверяем изоляцию данных и конкурентную запись в разные проекты, измеряем суммарное
потребление ресурсов и задержки команд.

Нужно измерить запуск бинарников, p95/p99 операций, ожидание записи, память, размер WAL,
отзывчивость HTTP при синхронизации и восстановление разных объёмов данных. Значения SLA
и превосходство нового решения пока не установлены.

## 11. Открытые решения следующих этапов

- Автоматическое сопоставление клонов/worktree с локальными проектами и базами.
- Серверный стек и точный контракт REST/SSE; перенос прежнего NestJS не утверждён.
- Реальный PostgreSQL-адаптер и API с эквивалентными командами, версиями и квитанциями.
- Серверные уведомления и жизненный цикл Server/Web поверх предметного ядра.
- Установка и обновление бинарников на поддерживаемых платформах.
- Миграция существующих данных и резервирование ещё не опубликованных изменений.

не являются проверкой новой реализации.
