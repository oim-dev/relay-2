# Работа над Relay Web

Правила действуют для разработки, исследования и ревью `apps/web`. Они дополняют
[корневые инструкции](../../AGENTS.md), [стайлгайд TypeScript](../../docs/development/TYPESCRIPT-STYLEGUIDE.md),
[правила тестирования](../../docs/development/TESTING.md) и
[документации](../../docs/development/DOCUMENTATION.md).

## Обязательная подготовка

- Начни с [README](README.md), [локальной архитектуры](docs/ARCHITECTURE.md) и документа
  затрагиваемого сценария: [использование](docs/USAGE.md), [разработка](docs/DEVELOPMENT.md).
- Новый и изменяемый React-код обязан соблюдать **React Reference** и **Unit Architecture**.
  До работы загрузи установленные `react-reference` и `unit-architecture`, полностью
  прочитай их `SKILL.md` и профиль React SPA. Если загрузчика или навыка нет, используй
  [закреплённые публичные источники](docs/DEVELOPMENT.md#источники-инструкций).
  Уже прочитанное в актуальном контексте повторно не загружай; подробные главы выбирай
  по задаче. Недоступность обязательного источника сообщи как конкретный блокер.
- При REST-интеграции прочитай [контракт Server](../server/README.md#http-контракт),
  [REST SDK](../../packages/rest-sdk/README.md) и применимые главы `rest-api-codegen-ru`
  по тому же маршруту источников. Имена методов и DTO бери из текущих exports/Contracts.
- До изменения границы установи владельца, слой, фасет, потребителей и lifecycle.
  Существующий код не доказывает корректность решения. Ослабление типов, отключение
  линта или перенос предметного правила в браузер не заменяют исправления причины.

## Создание и размещение компонентов

- Каждый новый прикладной `.tsx`, включая Provider, guard и внутренний компонент,
  создавай закреплённой командой `create` через Bun из [локального шаблона](.templates/README.md).
  Сначала прочитай инструкцию TSX-генерации из React Reference, README шаблонов и все
  файлы выбранного шаблона; убедись, что целевого каталога нет.
- Не заменяй генерацию ручным созданием или копированием заготовки. Не используй
  `--overwrite`. Перенос и изменение существующего TSX не требуют перегенерации;
  системные исключения ограничены чистым запуском и связующей конфигурацией из reference.
  Адаптируй заготовку в том же изменении, удалив демонстрационные и неиспользуемые части.
- Соблюдай локальный профиль: алиасы слоёв, публичные фасеты, колокацию и направленные
  зависимости. Проверяй свёрнутый граф юнитов, включая type-only, динамические импорты,
  реэкспорты и вложенные юниты. Не добавляй пустые слои и фасеты ради симметрии.
- Vite запускается **только под Node.js** через package scripts. Bun управляет workspace
  и зависимостями. Сохраняй настройку `cssTarget`, необходимую runtime-темам Mantine.

## Данные и предметные границы

- **Текущие Contracts/Core — источник предметных правил.** Исторический Web не задаёт
  новые статусы, ограничения или вычисления. Недостающую read-проекцию согласуй с её
  владельцем; геометрия визуализации допустима, вычисление готовности вместо Core — нет.
- Используй единый `@relay/rest-sdk` через доменные адаптеры. Не добавляй параллельный
  `fetch`-transport, browser-вызов бинарника или импорты исходников других приложений.
  Генерируемый HTTP-каталог изменяется у владельца Server/SDK, не вручную в Web.
- Передавай только поля действия, постоянные ID и **исходные** guards владельца.
  Сохраняй draft и frozen command/operationKey до понятного исхода; конфликт не разрешает
  автоматически подставить новую версию. Учитывай отдельную ревизию владельца состава
  и независимость append-only комментариев. Подробности — в
  [границе записи](docs/ARCHITECTURE.md#запись-и-черновики).
- Изолируй кеш, формы и поздние ответы по серверу/проекту/адресу. SSE и reconnect
  обновляют чтения, сохраняя ввод. Продолжение страницы сохраняет исходный generation;
  `PAGE_CHANGED` не разрешает склеить разные снимки.
- Git Sync остаётся видимым в layout. Неизвестные значения не заменяй нулями, SSE
  connected не объявляй доставкой. Статус и ручной запуск проходят Server/Runtime;
  чтение requestId не должно незаметно создавать новый `now`.

## Проверка результата

- Для изменения кода выполни адресные lint, typecheck и production build по
  [разработке](docs/DEVELOPMENT.md#проверки-изменения). Проверки типов и сборки не заменяют
  архитектурное ревью и проверку пользовательского пути.
- Изменённый UX принимай в собственном headless-браузере через `agent-browser`:
  [матрица приёмки](docs/DEVELOPMENT.md#браузерная-приёмка) включает темы, ширины,
  клавиатуру, реальные записи, конфликты, SSE и изоляцию. Прямой запуск исходников
  не доказывает поставку assets внутри бинарника Server.
- Автоматические frontend-проверки выбирай и размещай по текущим
  [правилам наборов](../../tests/README.md). Не добавляй отдельный runner только из-за
  примера в skill; проверяй нужную гарантию у её владельца.
- Fixtures, порты, browser session и процессы должны быть собственными; пользовательские
  данные не используй для автоматических проверок. Артефакты сохраняй только в
  `.artifacts/YYYY-MM-DD/<имя>` от корня checkout. Закрывай только свои ресурсы.
- Перечитай итоговый diff. В передаче укажи область, команды и фактические результаты,
  генерацию нового TSX, проверенные browser-сценарии, непроверенное и оставшиеся ресурсы.
  Порядок назначения ревью остаётся в корневых инструкциях.
