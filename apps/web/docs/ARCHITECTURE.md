# Архитектура Web

Web — браузерная React SPA. Он представляет текущие данные Relay Server и собирает
пользовательский ввод для команд. Предметные правила, транзакции, разрешение ссылок
и вычисляемый прогресс принадлежат Core. HTTP API обслуживает NestJS с адаптером Fastify
под Bun; Web использует его публичный SDK. Общие границы описаны в
[архитектуре Relay](../../../docs/ARCHITECTURE.md).

```text
React screen → доменный API → @relay/rest-sdk → Server → Core
                    ↑                         │
                    └──── SSE-инвалидация ─────┘

Git Sync ← процессный клиент Runtime ← Server ← Web
```

## Профиль и владельцы

Корень клиентского приложения — `apps/web/src`. Используется профиль React SPA из
[React Reference](DEVELOPMENT.md#источники-инструкций), дополненный следующей картой
реальных владельцев. Общие определения юнита и допустимых зависимостей остаются
в Unit Architecture.

| Область                                             | Ответственность                                                                     |
| --------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `app`                                               | Запуск React, подключение готовых Providers и дерево URL                            |
| `compositions/layouts/project`                      | Каркас выбранного проекта, навигация и размещение индикаторов                       |
| `compositions/route-boundaries`                     | Разрешение адреса в предметный экран и диагностика сбоя маршрута                    |
| `compositions/screens`                              | Завершённые сценарии обзора, знаний, документов, задач, планирования и истории      |
| `compositions/widgets/git-sync`                     | Представление текущего обмена и его исходов                                         |
| `domains/project`                                   | Контекст проекта, типизированные чтения, страницы, commands, drafts и SSE lifecycle |
| `domains/knowledge`, `tasks`, `planning`, `history` | Клиентская адаптация своих сценариев, command builders и доменный UI                |
| `domains/git-sync`                                  | Чтение статуса и наблюдение ручного запроса синхронизации                           |
| `infra/relay-api`                                   | Один экземпляр SDK для текущего origin                                              |
| `ui`                                                | Тема Mantine, Markdown renderer/editor, универсальные состояния ожидания            |
| `shared`                                            | Чистые детерминированные проверки значений                                          |

Алиасы `app/*`, `compositions/*`, `domains/*`, `infra/*`, `ui/*`, `shared/*` ведут
в одноимённые каталоги `src`. Межюнитные статические импорты идут через `index.ts`,
внутренние — по относительным путям. Профиль резервирует `lazy.ts` для отдельного
динамического фасета; текущее дерево маршрутов подключает экраны статически.
Наличие фасета объявляет юнит, а не произвольный barrel внутренних файлов.

Группы `layouts`, `route-boundaries`, `screens`, `widgets` классифицируют композиции.
Сегменты `hooks`, `operations`, `types`, `ui`, `styles`, `config`, `helpers` не получают
собственной границы без отдельной ответственности. Вложенный юнит не импортирует
родителя, предков или соседних детей; родитель координирует их через публичные API.
Матрица слоёв и отсутствие циклов проверяются для всего затронутого свёрнутого графа.

## Чтение и навигация

`RelayScreen` читает контекст сервера и выбирает доступный постоянный `projectId`.
Недоступные регистрации остаются в выборе. `ProjectScope` фиксирует сервер, проект
и автора для поддерева. `ProjectLayout` размещает `Outlet`, ключ которого меняется
при смене pathname: локальное состояние редактора не переходит на другую карточку.
Маршруты и адреса для человека описаны в [использовании](USAGE.md#адреса-и-навигация).

Серверные данные находятся в SWR. `useEntity` возвращает карточку с исходным
`aggregateVersion` того же чтения. `useRead` связывает имя проекции с её параметрами
и результатом из `HttpReadParameters`/`HttpReadResults`. Каталог HTTP принадлежит
[Server](../../server/README.md#http-контракт), контракт клиента —
[REST SDK](../../../packages/rest-sdk/README.md).

`useEntityPages` читает ограниченные страницы. Для продолжения передаётся generation
предыдущего окна; несовместимые страницы не объединяются. SQL-окно не означает, что
каждый фильтр Core имеет ограниченную стоимость: особенности составных чтений остаются
у Server/Core. Обзор получает агрегаты одним чтением, а предпросмотры карточек загружает
отдельно и не выдаёт их за тот же snapshot.

Ключи кеша включают origin и projectId. SSE `connected`, включая reconnect, и `changed`
инвалидируют соответствующие чтения. Составные SWRInfinite-списки обновляются через
собственный lifecycle. События не являются журналом для восстановления каждого изменения.

## Запись и черновики

Черновик — отдельное клиентское состояние в памяти вкладки. Его ключ включает сервер,
проект и имя формы/адрес. Начальное значение сохраняется при первом открытии, вместе
с исходной карточкой и guards. Серверное обновление не переписывает это значение.
Размонтированный владелец не вправе обновить новый экземпляр той же формы.

`useCommandDraft` связывает ввод с одной командой и operationKey. Командный адаптер
сохраняет точный запрос; одновременно исполняемый запрос с тем же ключом разделяется
между вернувшимися потребителями. После потери ответа повтор сначала читает квитанцию.
До понятного исхода редактирование ввода заблокировано. Достоверный конфликт оставляет
пользовательский draft, а не подставляет свежую ревизию. Успех инвалидирует чтения
исходного проекта независимо от текущего URL.

Формы отправляют только поля конкретного действия. Область guard определяется
контрактом Core: разделы документов принадлежат проекту, этапы и membership — плану,
участие реализации — приложению. Журнал комментариев задачи независим от её содержания;
сохранение старой карточки не должно заменять журнал. Материалы истории неизменяемы.

Web не копирует предметные вычисления из прежнего интерфейса. Статус реализации
сохраняется командой, готовность задачи/плана/релиза читается у Server/Core.
Существование элемента интерфейса не создаёт отсутствующую API-возможность.

## Git Sync и визуальная среда

Индикатор синхронизации использует отдельную серверную проекцию Runtime: подключение,
worker, режим/фазу, pending, конфликты, lastSuccess, ошибку и freshness. `null` означает
неизвестное. SSE-соединение сообщает о доступности событий, не о Git-доставке.
Ручной `now` и чтение его requestId остаются разными операциями.

Раскрытая проекция конфликтов и blocked-зависимостей перечитывается после завершения
`now` и при изменении значимых полей cached status: очереди, freshness, последнего
успешного обмена или ошибки. Это учитывает доставку из CLI, которая может не менять
поколение предметных данных. Одинаковые status-снимки не запускают повторное чтение
графа. HTTP-отказ `now` с известным requestId проверяется отдельным GET исхода;
интерфейс не начинает новую операцию и не выводит пустой blocked из pending.

Тема и её Provider принадлежат `ui/themes`. CSS Modules используют семантические
переменные темы; нативный `light-dark()` сохраняется настройкой `cssTarget` в Vite.
`MarkdownView` отображает безопасный Markdown и нормализует уровни заголовков по
контексту. `MarkdownField` владеет экземпляром CodeMirror, а значение draft — форма.

Vite запускается под Node.js и создаёт готовые assets. Их размещение в поставке
принадлежит Server; браузерный модульный граф не зависит от Bun, SQLite или Runtime.
Проверка этого стыка входит в [браузерную приёмку](DEVELOPMENT.md#браузерная-приёмка).
