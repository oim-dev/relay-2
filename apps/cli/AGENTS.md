# Работа над CLI

Перед изменениями прочитай [README](README.md), [руководство CLI](../../docs/CLI.md)
и общие правила из [корневого AGENTS.md](../../AGENTS.md).

## Границы приложения

- CLI преобразует аргументы и источники ввода, выбирает локальный контекст, вызывает
  сценарий и представляет результат. Предметные фильтры, составы, проверки сохранённых
  данных и условия допустимости изменений принадлежат Core.
- Выбор проекта и пути к базе выполняет Project Runtime. Открывай БД при выполнении
  сценария, проверяй соответствие выбранному projectId и закрывай соединение при любом
  исходе. Справка и версия должны работать без проекта и чтения stdin.
- Сохраняй изоляцию вызовов runCli: окружение, рабочий каталог, потоки и конфигурация
  Gunshi передаются явно. Не изменяй глобальные process.env, cwd или console внутри вызова.
- Тексты справки, подписи и диагностики CLI размещай в `src/locales` по областям.
  Предметные ошибки остаются у владельца правила в библиотеке.

## Размещение кода

- Соблюдай [структуру CLI](../../docs/ARCHITECTURE.md#устройство-cli): в корне `src`
  остаётся только `main.ts`; сборка и запуск находятся в `app/`, контекст исполнения —
  в `execution/`, общие механизмы — в `input/`, `output/`, `pagination/` и `errors/`.
- Регистрируй группы в `commands/<область>/register.ts`; локальные преобразования,
  типы и модульные тесты располагай у владельца. Выделяй `input.ts` только при наличии
  самостоятельной ответственности ввода, а не для одинакового набора файлов во всех группах.
- Тексты групп размещай в `locales/commands/<область>.ts`; общие словари оставляй
  непосредственно в `locales/`, ресурсы Gunshi — в `locales/ru.ts`.
- Связывай группы с реестром в `app/program.ts`; общая инфраструктура не импортирует
  конкретные команды. Используй прямые импорты модулей и соседних `*.types.ts`,
  не добавляй промежуточные `index.ts` и корневые файлы-переадресации.

## Гарантии команд

- Сохраняй точный ввод: пустые значения, false, Markdown и значимые пробелы.
  Конфликты источников поля и нескольких потребителей stdin выявляй до чтения.
- Передавай исходную ревизию пользователя. Не подставляй свежую ревизию и не повторяй
  отклонённую мутацию автоматически.
- Страница и её поколение читаются в одном снимке; чтение не должно занимать блокировку
  писателя. Продолжение списка адресует тот же проект, запрос и размер страницы.
- Успешный вывод принадлежит stdout, диагностика — stderr. Сохраняй коды ошибок,
  корректный JSON и обработку закрытого stdout; неожиданные ошибки записи не скрывай.

## Выбор проверок

- Разбор ввода, форматирование и изоляцию вызовов проверяй через runCli без процессов.
  Интеграционные тесты защищают передачу данных в Core/Runtime и чтение результата.
- Процессный набор нужен для изменений поставляемого бинарника, потоков и завершения.
  Данные для проверки адаптера готовь через Core/Runtime, а проверяемое действие — через CLI.
- Адресные команды из корня: `bun run --filter @relay/cli test:unit`,
  `bun run --filter @relay/cli test:integration` и
  `bun --bun turbo run test:process --filter=@relay/cli`. Последняя подготавливает бинарник.
- Законченные пользовательские маршруты принадлежат корневому `tests/e2e`;
  подробные варианты предметного правила проверяются в пакете-владельце.
