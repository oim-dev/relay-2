# Relay CLI

`relay` позволяет работать с памятью проекта из командной строки: сохранять знания
и документы, вести задачи и планы, фиксировать намерения и результаты работы.
Командой могут пользоваться человек, AI-агент и скрипт автоматизации.

CLI работает с локальными данными выбранного проекта. Для повседневных команд
достаточно собранного бинарника; отдельный сервер и доступ к сети не требуются.
Читаемый текст удобен в терминале, а `--format json` позволяет обрабатывать результат
в других инструментах.

## Получение команды

Подготовьте исходники по [быстрому старту Relay](../../README.md#быстрый-старт).
Из корня репозитория выполните:

```bash
bun run build:cli
export PATH="$PWD/apps/cli/dist:$PATH"
relay --help
```

Сборка создаёт `apps/cli/dist/relay` для текущей платформы. Изменение `PATH` действует
в текущем терминале. После сборки бинарник можно запускать самостоятельно; Bun нужен
для разработки и повторной сборки.

## Первый проект

Перейдите в каталог проекта, знания о котором хотите вести, и выполните:

```bash
relay init --name "Мой проект" --slug my-project
relay document create \
  --name "Договорённости" \
  --body "Все изменения проходят ревью." \
  --actor developer
relay document list
```

Инициализация создаст привязку `relay.config.json` в рабочем каталоге, а данные
по умолчанию разместятся в `~/.relay`. В результате создания документа появятся
его постоянный ID, читаемый ключ и ревизия. Сохранённый документ доступен при следующих
запусках; прочитать его целиком можно командой `relay document get <ключ>`.

Для изменений указывается автор через `--actor` или `RELAY_ACTOR`. Обновление записи
принимает прочитанную локальную ревизию через `--if-revision` либо переносимый токен
владельца через `--expected-version`. Можно передать оба — проверяются оба, включая no-op.
Если редактор уже прочитал привязку ключа к ID, передайте её через глобальный
`--expected-addresses '[{"ref":"DOC-1","expectedId":"прочитанный-ID"}]'`.
Core проверяет эту привязку вместе с изменением; CLI не заменяет её актуальным ID.
Можно адресовать запись непосредственно постоянным ID. Для повторного batch Core
возвращает прежнюю квитанцию до новых адресных/CAS-проверок.

### Переносимая версия перед изменением

```bash
relay get DOC-1 --summary --with-versions --format json
relay document update DOC-1 --body-file ./rules.md \
  --expected-version 'aggregate-version-from-get' --actor human
```

Вместо `aggregate-version-from-get` подставьте `meta.versions[ID].aggregateVersion`
из первого ответа; ID находится в `data.items[0].entity.id`. Токен непрозрачен и передаётся
дословно. Он описывает владельца изменяемого содержания: для раздела документа владельцем
будет проект, для этапа — план, для материала истории — соответствующая сессия.
`product create` и `implementation create` также принимают `--expected-version` существующего
паспорта продукта либо приложения соответственно.

`get --with-versions` сохраняет прежние `data.view`, `items`, порядок, повторы, ошибки,
`generation` и effective-представление. Metadata успешных ID находится отдельно в `meta.versions`
и относится к тому же согласованному чтению; она не добавляется в raw запись или её content hash.
`--summary` сохраняет узкое чтение. В текстовом выводе отдельно показаны версия записи
и версия агрегата для `--expected-version`. Обычный `get` без флага сохраняет прежний ответ.

Для переноса между планами получите оба токена одним чтением:

```bash
relay get PLN-1 PLN-2 --summary --with-versions --format json
relay plan stage task transfer PLN-1 TASK-1 target-stage-id --target-plan PLN-2 \
  --expected-version 'source-aggregate-version' --target-version 'target-aggregate-version' \
  --reason 'Перенос в следующий этап' --actor human
```

Подставьте прочитанные токены исходного и целевого планов и ID целевого этапа.
`--target-revision` остаётся локальной альтернативой `--target-version`; при передаче
обеих форм проверяются обе. В JSON batch аналогичные поля называются `expectedVersion`
и `input.targetVersion`.

Для ввода команд по Tab подключите [автодополнение](../../docs/CLI.md#автодополнение).
`relay complete bash` создаёт скрипт для Bash; также доступны Zsh, Fish и PowerShell.

## Повседневная работа

Запускайте команды из корня проекта с `relay.config.json` или корня workspace
с `relay.workspace.json`: родительские каталоги не проверяются. Из другого каталога
передайте явный `--config`. Workspace хранит пути каталогов проектов с собственными
конфигами; нужный проект выбирается через `--project`.
Markdown удобно передавать из файла с помощью `--body-file`; путь `-` читает stdin.

У каждой группы и команды есть справка с пояснениями и примерами, например
`relay task create --help`. Предметная группа без действия тоже показывает справку.
Выбранные записи разных видов можно прочитать одним `relay get`: полное содержание
выдаётся по умолчанию, краткие карточки — с `--summary`. Связанные изменения
применяются через `relay batch`; предварительная проверка доступна с `--check`.
Общая справка пакетов — `relay batch -h`, описание JSON-полей конкретного действия —
например, `relay batch help product create`.
Успешный результат направляется в stdout, диагностика — в stderr. При использовании в скриптах проверяйте
код завершения вместе с JSON-ответом.

Подробные команды, размещение данных, правила workspace и продолжение списков описаны
в [руководстве локальной работы](../../docs/CLI.md).

## Git-синхронизация

Все пользовательские действия доступны через `relay git-sync`. Обмен выполняет отдельный
компонент `relay-git-sync` того же выпуска: установите его рядом с `relay`, в `PATH`
либо передайте точный путь через `RELAY_GIT_SYNC_BIN`. В checkout компонент собирается
командой `bun run build:git-sync`; CLI находит также его сборку в `apps/git-sync/dist`.
Справка и обычные локальные команды не запускают этот компонент.

Из каталога проекта:

```bash
relay git-sync connect --remote origin --branch relay-data-v2
relay git-sync now
relay git-sync status
relay git-sync service enable
relay git-sync auto enable
```

`connect` принимает `origin` из Git-каталога запуска, URL или путь Git-репозитория.
Один `now` обрабатывает ограниченное окно: успех не означает пустую очередь,
проверьте pending в `status`. Подключение и получение новой реплики описаны в
[руководстве Git-синхронизации](../../docs/CLI.md#git-синхронизация).
`auto enable` включает
автоматический обмен проекта и запрашивает живой worker у уже работающего supervisor.
Сначала запустите supervisor через `service enable` либо в отдельном терминале через
`git-sync supervise`; без него start/auto enable возвращают `SUPERVISOR_REQUIRED` с кодом 4.
Локальные изменения
сохраняются без ожидания Git или сети; supervisor сам обнаруживает накопленную работу.
`worker start|stop|restart` управляет процессом выбранного проекта.

`status` показывает worker отдельно от обмена. Без `--refresh` используются известные
локальные сведения; неизвестные счётчики равны `null` в JSON. В корне workspace без
`--project` перечисляются все регистрации с собственными исходами, включая недоступные.
`--all` выбирает этот режим явно; ошибки отдельных проектов дают ненулевой общий код,
сохраняя остальные результаты. Машинный формат — `--format json`.
У одного проекта и workspace одинаковая оболочка `data`: `version: 1`, `scope`
(`project` или `workspace`) и `items`. Каждый элемент содержит `name`, `path`, `ok`
и исходный статус в `data` либо причину в `error`. У одиночного выбора неизвестный
путь регистрации равен `null`; `--project` сохраняется как `name`.

### Ожидание и проверка запроса обмена

```bash
relay git-sync now --wait-ms 5000 --format json
relay git-sync request get request-id --format json
relay git-sync now --request-id request-id --wait-ms 60000 --format json
```

Подставьте `requestId` из результата либо `error.details.requestId`. Без `--request-id`
`now` создаёт новый запрос; Runtime заранее назначает его `operationId`, ещё до запуска
компонента. `now --request-id` только ждёт прежний исход и ничего не отправляет заново.
Проверку `request get` и продолжение ожидания выполняйте в том же проекте и `RELAY_HOME`.

`--wait-ms` принимает 1–90000 мс, по умолчанию 60000. `GIT_SYNC_WAIT_TIMEOUT` (код 4)
означает истечение ожидания принятого queued/running запроса. Runtime process timeout
`GIT_SYNC_TIMEOUT` (код 124) сохраняет ID, но возвращает `state: unknown`: принятие и исход
могут быть неизвестны. Истечение ожидания не означает отмену операции.

`request get` возвращает `queued`, `running`, `completed`, `failed` или `unknown` без Git
и нового submit. Код 0 этой команды означает успешное чтение состояния; успех самой
операции обозначает только `completed`. `unknown` после expiry/потери владельца не является
успехом или отменой; `now --request-id` сообщает `GIT_SYNC_OUTCOME_UNKNOWN`, не повторяя работу.
Журнал ограничен 64 активными и 128 недавними исходами, хранение — 15 минут.

`status --refresh` использует такой же протокол и принимает `--request-id` / `--wait-ms`.
В workspace `--refresh --all` имеет отдельную операцию и budget для каждой регистрации;
ожидание одного `requestId` требует выбрать конкретный проект. Обычный status без refresh
не принимает параметры ожидания.

Для конфликтов доступны `conflicts list`, `conflicts get <id>` и
`conflicts resolve <id> --input @resolution.json --actor human`. Решение также можно
передать непосредственно как JSON либо через `--input -`. В новом каталоге
`relay git-sync restore --remote <URL-или-путь>` создаёт независимую реплику без `init`
и предварительного подключения. Существующая рабочая БД не заменяется.

Если после публикации БД восстановление вернуло `RESTORE_RECOVERY_REQUIRED`, сохранённую
локальную привязку можно завершить явно:

```bash
relay git-sync restore --resume --project-id project-id
```

Подставьте постоянный ID из recovery details. При выборе существующего config ID может
определить Runtime: `relay git-sync restore --resume --config ./relay.config.json`.
`--project` по-прежнему выбирает имя регистрации workspace. `--resume` несовместим с
`--remote`/`--branch`; `--project-id` используется только в этом режиме.

Resume сохраняет принятую БД с позднейшими записями и завершает только её привязку,
без fetch и повторной материализации. `resumed: true`, `preservedExisting: true` и
`sourceCheckpoint: null` подтверждают локальное состояние; новый Git HEAD не заявляется.
Сведения о незавершённой cleanup остаются в `recovery`. После полного завершения повтор
возвращает `RESTORE_NOT_PENDING` (код 3). Дальнейшее подключение и обмен выполняются явными
`git-sync connect` / `git-sync now`.

### Кто запускает supervisor

Явная команда `relay git-sync service enable` создаёт служебную конфигурацию для текущего
пользователя и `RELAY_HOME`, регистрирует её и запускает supervisor. В ней сохраняются
абсолютный путь компонента и аргументы `supervise --home <путь>`, включая пробелы и Unicode.

- **Linux:** user-systemd, запуск при входе пользователя. Работа до входа и после выхода
  зависит от отдельно настроенного linger. Relay не включает его и не вызывает `sudo`.
- **macOS:** LaunchAgent графической сессии текущего пользователя после входа.
- **Windows:** Task Scheduler, logon task текущего пользователя с `InteractiveToken`,
  без повышения прав, с перезапуском после отказа и без ограничения времени работы.

`service status` разделяет желаемую регистрацию, фактические `registered`/`enabled`/`state`
native manager и `supervisor` с проверенной отзывчивостью, instance и выпуском. Успех
`service enable` требует подтверждённого health-ответа. Для LaunchAgent загруженность
не доказывает живость и может возвращать native `state: unknown`; отзывчивость определяется
одинаковым loopback-протоколом на всех ОС. `service disable` останавливает и удаляет только принадлежащую Relay
службу этого home, сохраняя проекты и подключения. После переноса бинарника повторите
`service enable`, чтобы обновить его точный путь.

Для контейнера или внешнего supervisor доступен foreground-вход:

```bash
relay git-sync supervise --home /var/lib/relay
```

Он передаёт потоки компонента непосредственно и завершает дочернее дерево при
`SIGINT`/`SIGTERM`. Для foreground компонент получает приватный stdin-lease: даже при
`SIGKILL` CLI закрытие pipe ядром запускает shutdown supervisor. Исходники, бинарники
и данные проектов при остановке сохраняются. Политику запуска при загрузке системы в этом режиме задаёт внешний
supervisor. Подробности каждой команды доступны через `relay git-sync --help`.

## Разработка CLI

CLI входит в монорепозиторий Relay. `bun run dev:cli` из корня пересобирает бинарник
при изменениях исходников; для выполнения команды запускайте полученный бинарник.
Предметные writers ожидают асинхронный фасад Core, который выполняет общий executor;
CLI держит рабочее соединение до завершения Promise и закрывает его при любом исходе.
Внешняя SQLite-транзакция вокруг async writer не создаётся. Составные чтения сохраняют
синхронные снимки и прежнюю пагинацию.
Проверки ввода и вывода, интеграции и поведения процесса описаны в
[руководстве тестовых наборов](../../tests/README.md).

Границы приложения приведены в [архитектуре](../../docs/ARCHITECTURE.md#устройство-cli),
а местные правила изменений — в [AGENTS.md](AGENTS.md).
